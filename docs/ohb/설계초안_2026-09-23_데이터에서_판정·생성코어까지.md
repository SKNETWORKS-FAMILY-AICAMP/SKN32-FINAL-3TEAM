## 0. 한 줄

**데이터는 코어를 막지 않는다 — 막는 것은 이음새 셋(위험도 하한 적재기 · 평가 도구 · 그래프 모양)과 판정 네 건이다.**
그래프는 **공유 판정 코어 하나 + 진입점 그래프 둘(검수 · 생성)** 로 가르고, 생성은 D-264 의 규칙 조립판을 안전선으로 삼아 **sLLM 없이** 먼저 세운다.

### 5-1. 모양 — 코어 하나, 진입점 둘 · 🔄 2판: 품목 분기는 **법별 노드 팬아웃**

                     ┌──────────────────────── core (서브그래프 · 컴파일 한 번) ────────────────────────┐

                     │                          route_laws ── Send · 해당 법만 ──┐                        │
                     │                    ┌──────────────┼──────────────┐    │                        │
                     │                    ▼              ▼              ▼    │                        │
                     │               law_ftc        law_food      law_cosmetic                         │
                     │              표시광고법      식품표시광고법     화장품법                            │
                     │              모든 전제       식품·건기식 전제   화장품 전제                          │
                     │                    └──────────────┼──────────────┘                              │
                     │                                   ▼  law_results (누적 키 · 리듀서)                │

**법 × 전제 — 누가 무엇을 계산하나**

| 법별 노드 | 다스리는 전제 | 이 노드에서 갈리는 것 (예) | 근거 |
|---|---|---|---|
| `law_ftc` 표시광고법 | **모든 전제** | 기만 · 부당비교 · 비방 — 품목과 무관하게 걸린다 | 기획서 3-2 · A-4-1 |
| `law_food` 식품표시광고법 | `식품` · `건기식_인정` · `건기식_비인정` | 별표1 1호 가목 단서 2)(인정 사항 제외) · 3호 본문(「건강기능식품이 **아닌 것**을」) — 같은 문구가 전제마다 뒤집힌다 | D-229 ① · D-242 ① |
| `law_cosmetic` 화장품법 | `화장품` | 별표5 · 기능성화장품 오인 | D-229 ⑥ 표 |

- **라우팅** — `classify` 가 품목을 가리면 `route_laws` 가 **그 품목의 법 + 표시광고법**에만 `Send` 한다. 못 가리면 셋 다 보낸다(D-229 ⑥ 「분기는 미확정이면 언제나」). **「카테고리 판별 → 다법령 라우팅」(차별점 ①)이 그래프의 엣지로 보인다**
- **비용은 1판과 같다** — `retrieve`·`encode` 는 팬아웃 **앞에서 한 번** 돈다. 법별 노드는 인코더 출력과 검색 결과를 받아 **자기 법의 조문만 거르고 적용**한다. ⛔ 법마다 검색을 다시 부르면 검색이 3~4배다 — 검토 09-21 §5-4 가 비용 판단 없이는 고르지 말라고 한 그것이다
- **팬인** — 법별 노드는 `law_results`(누적 키 · `REDUCER_KEYS` 에 한 줄) 에 `(법, 전제, 문장별 유형·근거·하한)` 을 쌓는다. `merge_laws` 가 **전제마다** 묶어 `branches` 를 만들고, **가장 보수적인 전제**(`premise_basis` · 계약초안 §6 #2)를 초기 판정으로 올린다(D-263 ①)
- **계측** — `timings` 가 법별로 쌓인다(`@timed` 그대로). 「어느 법이 느린가」를 따로 잰다 (D-77 L3)
- 🔴 **같은 전제 안에서 두 법이 다른 하한을 내면** `merge_laws` 는 **높은 쪽**을 하한으로 삼고 근거는 **합친다** — 한 광고에 두 법이 **동시에** 걸리기 때문이다. ⬜ **이 규칙은 원장에 없다.** D-227 의 `max` 는 「물어볼 수 없는 축(업종)」에 대한 것이라 다른 자리다 — 원장 등재 때 같이 적는다 (§10)
- ⛔ **법별 노드는 인코더를 부르지 않는다** — 인코더가 셋이 되면 판정기 A 가 세 벌이다 (D-99). 법이 바꾸는 것은 **조문 적용**이지 예측이 아니다
- 🚨 **필연인가 유용인가** — 법별 팬아웃이 새 **필연**을 만드는 것은 아니다. 여러 법이 한 문구에 동시에 걸린다는 **이미 있는 필연**(기획서 3-1 첫 두 줄)을 **구조로 드러내는** 것이다. 발표에서도 그렇게 말한다 (짝 문서)

### 5-2. 검수 그래프 (진입점 A)

```
 START ─▶ core ─▶ route_review ─┬─▶ certificate   A 자격형 · C 절대형 확정 (D-32 · 루프 미진입)
                                ├─▶ hold          보류 · 근거없음 · 미판정 · premise_unknown
                                ├─▶ guidance      🆕 확정 위반 중 B 실증형 — 뺄 구간 · 요건 · 실증 분기 (§8 G2)
                                └─▶ pass          전부 확정 ∧ 위험도 ≤ R1 (D-125)
                                        │
                                        ▼
                               finalize — thread 삭제 (D-129) · timings → MLflow (D-77)
```

- 🚨 **`generate`·`verify`·`search_failed` 가 이 그래프에 없다** — 검수는 문구를 안 만든다 (D-265). `candidates` 는 늘 빈 목록이고 기존 검증기 둘이 그것을 지킨다
- 🔄 2판 — `core` 안의 법별 팬아웃이 검수 경로의 **분기 구조**다. 기획서 3-1 이 「판정 경로는 거의 선형」이라 적은 자리가 여기서 바뀐다 (짝 문서)
- 🚨 **기록되는 판정 = 초기 판정**(가장 보수적 전제 · D-263 ①). 게이트 수도 이것으로 잰다. `branches` 는 화면이 고르는 선택지일 뿐이다
- 라우팅 우선순위(문서에 여러 문장이 섞일 때): **보류 > 증명서 > 지시 > 통과** — 하나라도 확정이 아니면 보류(현행 `route_after_judge` 규칙 그대로)
- 조건 칸 → 불가 사유: `C → C` · `A → A` · `B → B` · `M → hold` · `D → 걸린 것 없음(R0 후보)` (D-242 표) · 🔴 `M` 의 보류 사유코드가 정해져 있지 않다(§8 G2 에 붙인다)

## 8. ⬜ 판정 요청 — 넷

> 형식: 상황 → 용어 → 대안 → 얻는 것/떠안는 것 → 권고. **판정은 팀장 몫이다.**

### G1. 그래프를 어떻게 나누나

- **상황** — 지금은 상태 하나(`JudgeState`)에 진입점 셋의 키가 다 들어 있고, 그래프 하나 안에 검수와 재생성 루프가 이어져 있다. D-265 로 검수는 루프를 안 돈다.
- **용어** — *서브그래프*: 따로 컴파일한 그래프를 다른 그래프의 노드 하나로 끼우는 LangGraph 기능. 코어를 한 번 짜서 검수·생성 양쪽이 같은 것을 부르게 한다.

| 안 | 얻는 것 | 떠안는 것 |
|---|---|---|
| (가) 현행 — 한 상태 · 한 그래프, 라우터만 고친다 | 코드 변경이 가장 적다 | 검수 상태에 생성 키가 계속 산다 · `attempt` 가 검수에서 늘 0 인 칸으로 남는다 · 이름이 판정 전용으로 읽힌다 |
| ★ (나) 공유 코어 서브그래프 + 진입점 그래프 둘 | 코어가 코드로 하나다(D-119 · D-99) · 검수 상태에서 루프 키가 사라진다 · 생성의 재판정이 같은 코어를 부른다 | 상태가 넷으로 늘고 게이트(`REDUCER_KEYS`)를 상태마다 돌린다 · 서브그래프 상태 대응(입출력 키 매핑)을 한 번 짜야 한다 |
| (다) 진입점마다 코어를 복사 | 각자 빨리 짠다 | 판정 코어가 두 벌 — D-119 위반 |

**권고 (나)** — 루프가 빠진 검수와 루프가 사는 생성을 한 그래프에 두면, 라우터가 「검수인데 generate 로 간다」를 막는 조건을 계속 떠안는다.
⚠️ 틀릴 수 있는 지점 — LangGraph 1.2.11 의 서브그래프 상태 대응을 **이 저장소에서 컴파일해 본 적이 없다.** 첫 작업을 컴파일 확인으로 둔다.

### G2. 검수에서 확정된 B 실증형 위반은 어디로 끝나나

- **상황** — F2. 「소비자 선호도 11년 연속 1위」가 거짓·과장으로 확정되고 실증 분기(「실증하면 R1 이하 가능」)가 붙은 문서의 `outcome` 이 없다.
- **용어** — *outcome*: 문서 단위 종착(D-125). *지시*: 검수가 주는 것 — 뺄 구간 · 요건 안내 · 분기별 등급 변화(D-265 표).

| 안 | 얻는 것 | 떠안는 것 |
|---|---|---|
| (가) `hold` 로 보낸다 | 계약·DB 변경 없음 | 「모른다(보류)」와 「고쳐야 한다(확정 위반)」가 한 값 — D-127 이 「근거 불일치」를 상태에서 뺀 것과 같은 병 · 보류율이 부풀어 지표가 흐려진다 |
| ★ (나) 새 값 `guidance` — 마이그레이션 0018 에 `premise_unknown` 과 **같이** | 종착의 뜻이 하나씩 · 화면이 「지시」 카드를 그릴 신호가 선다 | 계약·DB enum·픽스처가 한 번 더 움직인다(잠금 1급) · 팀원 화면 한 갈래 추가 |
| (다) 검수 `outcome` 을 셋으로 줄이고 문장 판정만 본다 | 가장 단순 | 기존 픽스처·화면이 `outcome` 으로 분기하고 있다 — 넓게 다시 짠다 |

**권고 (나)** — 0018 을 어차피 연다(계약초안 §6 #3). 같이 넣으면 마이그레이션이 하나다.
딸린 것 — 조건 **M(맥락)** 의 보류 사유코드: 새로 두지 않고 `low_conf` 로 보낸다(맥락이 없어 확신이 없다) — 이견 있으면 같은 0018 에.

### G3. 인코더가 붙기 전, 사전에 안 걸린 문장은 무엇인가

- **상황** — F3. 사전은 울리면 진짜지만(적법 오탐 0%) 거의 안 울린다(거짓_과장 Recall 0.014).
- **용어** — *confirmed R0*: 「확정 · 특이사항 없음」. 통과가 된다.

| 안 | 얻는 것 | 떠안는 것 |
|---|---|---|
| ★ (가) `hold(low_conf)` | 미탐을 통과로 세지 않는다(D-127 · D-156) · 인코더가 붙는 날 보류가 줄어드는 것이 수로 보인다 | 인코더 전 화면은 거의 전부 「보류」 — 시연이 인코더에 묶인다 |
| (나) `confirmed R0` | 화면이 채워진다 | 사전이 못 본 위반 **대부분**이 **통과**로 나간다 — D-05 · D-130 과 정면 충돌 |

**권고 (가)** — 그리고 그 대가로 **W7(인코더 인터페이스 + harness)을 W4 바로 뒤로 당긴다.**

### G4. 9/28 단계 관문 — 생성 그래프를 어디까지 세우나 (인계 B §1 #1 · 시한 9/28)

## 10. 안 본 것 · 깔고 간 가정 (D-188)

- **실행 출력이 없다** — 이 문서의 수는 원장·파일 크기에서 읽었다. A `check` 수는 인계 2판의 **708 passed**(`84f2a86` 뒤 · 사용자 실행)가 마지막이다
- A 파생물 = B 09-22 판은 **크기**로만 맞췄다 — `derived-manifest --check` 로 해시를 본 것이 아니다
- `golden_sample` · `dict_entry` · `product_fact` 의 **A DB** 행 수는 안 쟀다 — 위 수는 B 적재 수다
- 수정쌍 245 가 파생물의 **어느 칸**에 있는지 안 열어 봤다 — D-264 가 「파생물 실측」이라 적은 것을 따랐다
- `cosmetic_*` 가 DB 에 적재되는지 안 봤다
- 세그먼트 코퍼스(철수 조건 6) · 팀원 브랜치의 최신 진척은 안 봤다 — `build/*.diff` 가 있으나 열지 않았다
- LangGraph 서브그래프를 이 저장소에서 컴파일해 본 적이 없다 (G1 ⚠️) · 🔄 2판 — **서브그래프 안의 `Send` 팬아웃**도 같다. 첫 작업(W2)에서 컴파일 + 방문 순서 게이트로 확인한다 (D-124 ②)
- 🔄 2판 — **법 ↔ 전제 대응**(표시광고법 = 모든 전제 · 식품표시광고법 = 식품·건기식 · 화장품법 = 화장품)은 기획서 3-2 그림과 D-229 표에서 옮겼다. 건기식이 식품표시광고법 밖의 법(건강기능식품법)에도 걸리는 조문이 있는지는 **이 문서에서 확인하지 않았다**
- 🔄 2판 — 「같은 전제 안에서 법 둘이 다른 하한 → 높은 쪽 · 근거 합침」(§5-1)은 **새 규칙이고 원장에 없다.** 등재 전까지 코드 주석에 `⬜` 로 박는다 (D-192)
