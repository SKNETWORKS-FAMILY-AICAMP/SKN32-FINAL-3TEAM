## 0. 재현 가능한 확인 절차 — 화면을 눈으로 읽는 것보다 이 쪽이 낫다

data.go.kr 상세 화면의 **「바로가기」 버튼**은 `fn_goUrlLink(<데이터번호>)` 이고, 그것이 부르는 것은

```
GET https://www.data.go.kr/tcs/dss/selectApiLinkUrl.do?publicDataPk=<데이터번호>
→ {"publicDataDetailPk":"uddi:…", "linkUrl":"…", "status":true}
```

- `linkUrl` 이 **원 기관 페이지** = **LINK 유형**
- `linkUrl: null` = **LINK 가 아니다** (자체 REST 엔드포인트가 있다)

REST 유형의 요청주소·파라미터·응답 모양은 상세 화면 Swagger 의 스펙에서 그대로 나온다
(`ui.specSelectors.specJson()` — 화면 표와 같은 값이다).

🚨 **「API 유형」 한 줄을 먼저 본다**는 규칙은 맞았다. 다만 화면 문구가 아니라 위 두 값으로 보면 오독이 없다.

## 2. `mfds_sanctions` — I0470 확정

인계는 다섯 후보(`I0470`/`I0480`/`I0481`/`I0482`/`I2630`)를 두고 「어느 것인가」를 남겨 뒀다. **I0470 이다.** 근거 둘이 독립적으로 같은 답을 낸다.

**① LINK 대상**

```
selectApiLinkUrl.do?publicDataPk=15059500
→ linkUrl: https://www.foodsafetykorea.go.kr/api/openApiInfo.do?…&svc_no=I0470
```

**② 출력항목 17개가 1:1**

data.go.kr 15059500 설명의 속성 나열과 식품안전나라 I0470 「출력항목」이 **순서까지 같다** —
업소명 · 업종 · 인허가번호 · 처분확정일자 · 처분시작일 · 처분종료일 · 처분유형 · 위반일자및위반내용 ·
주소 · 전화번호 · 대표자명 · 처분내용 · 위반법령 · 공개기한 · 최종수정일 · 처분기관명 · 행정처분전산키.

**호출 규약** — I-0040 과 같은 path 형이다. 🚨 다만 **serviceId 에 하이픈이 없다**.

```
http://openapi.foodsafetykorea.go.kr/api/{keyId}/I0470/{json|xml}/{startIdx}/{endIdx}
선택 파라미터  CHNG_DT(변경일자 YYYYMMDD) · DSPS_DCSNDT(확정일자) · LCNS_NO(인허가번호)
```

**필드 매핑 — 1층이 쓸 것과 가릴 것이 한 응답에 같이 온다**

| | 필드 | 쓰임 |
|---|---|---|
| 쓸 것 | `LAWORD_CD_NM` 위반법령 | 🚨 **「식품 등의 표시·광고에 관한 법률」 필터축.** S0-17-ⓑ(광고 위반 비중)를 이 필드로 센다 |
| | `VILTCN` 위반일자및위반내용 | 1층 판정라벨의 본문 |
| | `DSPS_TYPECD_NM` 처분유형 · `DSPS_DCSNDT` 처분확정일자 | 라벨·연도분포 |
| 가릴 것 | `PRCSCITYPOINT_BSSHNM` 업소명 · `ADDR` 주소 · `TELNO` 전화번호 · `PRSDNT_NM` 대표자명 | 등급 무관 즉시 마스킹 |

**남은 것**

- ✅ **2026-09-02 팀장 확인 — `FOODSAFETY_KEY` 하나로 I0470 이 열린다.** I-0040 승인으로 받은 키인데 서비스별 재신청 없이 통과했다. → 식품안전나라의 인증키는 **계정 단위**이지 서비스 단위가 아니다. 같은 근거로 I-0050 도 별도 신청이 필요 없다.
  - 🚨 **data.go.kr 은 반대다** — 거기는 **데이터셋마다 활용신청**이 따로다(`cosmetic_*` 2건이 그래서 막힌다). 같은 「오픈API」라는 말이 같은 신청 단위를 뜻하지 않는다. `style: path` / `style: query` 가 호출 규약뿐 아니라 **신청 단위까지 가르는 축**이었다.
- 🚨 **S0-17-b 는 열려 있다** — 이 소스는 **두 번 깎인다**: 업종으로 한 번(다섯 서비스가 전부 식품이다), 위반유형으로 한 번(광고는 일부다. 유통기한·이물·시설기준이 대부분). `LAWORD_CD_NM` 이 둘째를 세는 축이고, **실측 전까지 가치 A 는 가정**이다.

## 3. `cosmetic_ingredient` (15111774) · `cosmetic_restricted` (15111772) — REST, 채움

둘 다 `linkUrl: null` — LINK 가 아니라 **data.go.kr 자체 REST** 다. 키는 `DATA_GO_KR_KEY` 가 맞다.

| | `cosmetic_ingredient` | `cosmetic_restricted` |
|---|---|---|
| Base | `apis.data.go.kr/1471000/CsmtcsIngdCpntInfoService01` | `apis.data.go.kr/1471000/CsmtcsUseRstrcInfoService` |
| 오퍼레이션 | `/getCsmtcsIngdCpntInfoService01` | `/getCsmtcsUseRstrcInfoService` ← 이것 <br> `/getCsmtcsUseRstrcNatnInfoService` (배합금지국가, 별건) |
| 필수 | serviceKey | serviceKey · **pageNo · numOfRows · type** |
| 응답 | `body.totalCount` · `body.items.item[]` | 같음 |
| 출력 | INGR_KOR_NAME(표준명) · INGR_ENG_NAME · CAS_NO · ORIGIN_MAJOR_KOR_NAME(기원및정의) · INGR_SYNONYM(이명) | REGULATE_TYPE(구분) · INGR_STD_NAME · INGR_ENG_NAME · CAS_NO · INGR_SYNONYM · COUNTRY_NAME(배합제한국가) · NOTICE_INGR_NAME(고시원료명) · PROVIS_ATRCL(단서조항) · **LIMIT_COND(제한사항)** |
| 심의 | 개발 자동 / 운영 심의승인 | 같음 |

- 🚨 `type` 기본값이 **xml** 이다. `openapi.py:70` 이 `fmt: json` 일 때 `type=json` 을 붙이므로 통과한다. **fmt 를 xml 로 바꾸면 `cosmetic_restricted` 는 11번(NO_MANDATORY_REQUEST_PARAMETER_ERROR)** 이 난다 — 그 쪽은 type 이 필수다.
- 🚨 `total_of()` 가 `totalcount` 를 재귀로 찾으므로 `body.totalCount` 를 읽는다. 페이징 종료 판단 정상.
- ❗ **활용신청이 데이터셋별로 따로**다. `DATA_GO_KR_KEY` 가 있어도 이 두 건을 신청하지 않았으면 거부된다.
### 🔄 정정 — `LIMIT_COND` 는 2층 축이 아니다

이 문서의 초판이 「`LIMIT_COND` 가 2층의 화장품 쪽 축 · `PRIMARY_FNCLTY` 에 대응」이라 적었으나 **틀렸다.** `PRIMARY_FNCLTY` 는 승인된 **광고 표현**이고 `LIMIT_COND` 는 성분 **배합 제한**이다. 축이 다르다.

레지스트리가 이미 그렇게 적어 뒀다 — 둘 다 layer **「제품 사실」**, 가치 **C · D**(1층도 2층도 아니다). 그리고 `cosmetic_restricted` 의 caution 이 정확히 이 실수를 경고한다:

> ⚠️ 범위 확장 유혹을 조심할 것. 「이 성분이 들어간 제품 자체가 부적합」은 **다른 제품**이다. 기획서가 정한 경계(광고 문구 판정)를 넘으면 9주 안에 못 끝낸다.

**화장품 2층 적법라벨은 `kcia_guideline`**(광고자문 기준 해설서, 가치 A · G2)이다. 🚨 그것은 아직 **미서명**이고, 화장품 오픈API 어느 것도 그 자리를 대신하지 못한다.

## 4. 🚨 `ftc_decisions_api` (15103246) — 주소는 알아냈고, 그래서 채우지 않았다

**호출처가 공정위가 아니다.**

```
selectApiLinkUrl.do?publicDataPk=15103246
→ linkUrl: https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=cmtListGuide#ftc
```

**법제처 국가법령정보 공동활용**이다. `case.ftc.go.kr` 도 아니다 — 인계 §4-ⓑ 가 말한 그 경로와 **또 다른 셋째 경로**다.

```
요청  https://www.law.go.kr/DRF/lawSearch.do
파라미터  OC(필수, 법제처 인증값) · target=ftc(필수) · type=HTML|XML(필수)
         search(1=사건명 2=본문) · query · display(max 100) · page · sort
응답  <Ftc> … <totalCnt> · <ftc id=n>{결정문일련번호 · 사건명 · 사건번호 · 문서유형 ·
                                 회의종류 · 결정번호 · 결정일자 · 결정문상세링크}
본문  별도 호출 /DRF/lawService.do?OC=..&target=ftc&ID=<일련번호>&type=HTML
```

### 왜 `url` 을 비워 뒀는가 — 넷이 막는다

| | 막는 것 | 어디 |
|:-:|---|---|
| ① | 인증 파라미터가 **`OC`** 다. 수집기는 `serviceKey` 를 고정으로 붙인다 | `openapi.py:68` |
| ② | 키가 `DATA_GO_KR_KEY` 가 아니다. 🔄 **정정 — `.env` 이름은 이미 있다**: `LAW_OC_KEY`(`.env.example:37`, 2026-08-20 승인 완료, `law_go_kr` 와 같은 값). 막는 것은 이름이 아니라 수집기가 **style 로만 키를 고른다**는 것 | `openapi.py:107` |
| ③ | 페이징 변수가 `pageNo`/`numOfRows` 가 아니라 **`page`/`display`** 다 | `openapi.py:68` |
| ④ | 응답이 **XML 전용**이다. `total_of()` 는 JSON 만 읽어 `None` 을 내고, 종료 조건이 `len(payload) < 200` 으로 떨어진다 — **XML 은 빈 장도 200바이트를 넘어 멈추지 않는다.** 저장 파일명도 `page_0001.json` 으로 붙는다 | `openapi.py:74·131·118` |

→ 필요한 것은 이 파일의 값이 아니라 **수집기 확장 결정**이다:
`auth_param` / `auth_env` / `page_param` / `rows_param` / XML 파서 / 저장 확장자.
결정 전까지 `url: null` 이 맞다 — 「틀린 주소는 빈 칸보다 나쁘다」.

### 🔄 그런데 급한 일이 아니다

레지스트리가 이 소스를 **`scale: "증분 갱신용"`** 으로 적어 뒀다. 1층의 본체는 파일데이터 `ftc_decisions`(15103301, 5,870건)이고, **그쪽 하나로 1층이 선다.** 수집기 확장은 뒤로 미룰 수 있다.

🚨 **정작 빠진 것은 본문 API 15103247 이다.** 기획문서 1층은 의결서 경로를 **셋**으로 적어 뒀다 — 파일데이터 15103301 · 목록 15103246 · **본문 15103247**. 그런데 레지스트리에는 앞의 둘만 있고 **15103247 은 등재 자체가 없다.** 목록 API 만으로는 사건명·사건번호·결정일자뿐이라 **광고 문구가 나오지 않는다.** 증분 경로를 살릴 거면 먼저 등재·판정할 것은 이쪽이다 (D-15).

### ❗ 거버넌스 — 서명이 덮는 것과 실제로 부르는 곳이 갈린다

2인 확인이 덮는 것은 **data.go.kr 15103246**(이용허락범위 제한 없음)인데 실제 호출은 **법제처**다.
미서명 소스 `law_go_kr` 이 **같은 포털·같은 키 체계**이므로 두 판정이 서로를 가리킨다. **함께 판정하는 것이 맞다.**
