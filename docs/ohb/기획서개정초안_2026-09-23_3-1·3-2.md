## 1. 3-1 개정안 — 붙여 넣을 문안

> 아래 인용 블록 **안쪽**이 기획서에 들어갈 문안이다. `🔄 v4.2` 표지는 개정 이력(부록 C)에 한 줄 더하는 것과 짝이다.

````markdown
### 3-1. 단일 체인으로는 안 되는 이유

| 이 업무의 특성 | 단일 체인의 한계 | 경로 |
|---|---|:-:|
| 카테고리에 따라 **적용 규범 자체가 다름** | 하나의 프롬프트로 3개 법을 다 담으면 품질 저하 | 검수 · 생성 |
| 하나의 문구가 **둘 이상의 법에 동시에 걸림** | 순차 실행은 동시 적용을 표현 못 함 → **법별 노드 팬아웃–팬인** | 검수 · 생성 |
| 🔄 카테고리를 **묻지 않고** 경우별 답을 낸다 | 전제마다 다른 판정을 **한 번에 계산해 상태에 담아야** 함 | 검수 |
| 판정·근거·사례·위험도를 **누적 유지**해야 함 | 상태 관리 없이는 맥락이 끊김 | 검수 · 생성 |
| 확신이 낮으면 **판정을 보류**해야 함 | 분기 로직 필요 | 검수 · 생성 |
| 🔄 **판단 주체가 여럿이고 서로 다른 답을 낸다** — 코드 하한 · 인코더 · 조문 검색 · 문서 규칙 | 충돌 해소 규칙(3-5 래칫)이 **상태 위에서** 돌아야 함 | 검수 · 생성 |
| ★ **생성기와 판정기의 목적이 상충** | 한 프롬프트 안에서 "강하게 써라 + 약하게 써라"는 성립하지 않음. **분리된 두 노드 + 조율**이 필요 | 생성 |
| ★ **생성물이 다시 위법일 수 있고, K회 뒤에도 실패하면 그렇다고 선언**해야 함 | 종료 조건이 있는 순환 그래프. 순방향 체인으로 표현 불가 | 생성 |
| ★ **세그먼트 페르소나가 여럿이면 병렬 생성 후 통합** | 팬아웃–팬인 구조 | 생성 · 🔄 **설계** (8-3 게이트) |

> 🔄 ★ **정직하게 — 우리가 「에이전트」라고 부르는 것** <sub>(v4.2)</sub>
>
> 이 문서에서 에이전트는 **상태 그래프 위의 판단 노드**입니다 — 코드 · 인코더 · 조문 검색(RAG) · 문서 규칙, 그리고 생성 경로의 sLLM.
> **스스로 도구를 골라 부르는 LLM 에이전트가 아닙니다.** 외부 도구 호출이 0건이라 ReAct 루프를 두지 않았습니다(3-6).
>
> **다중 에이전트인 이유는 LLM 의 개수가 아니라 셋입니다.**
> ① 판단 주체가 여럿이고 **각자 다른 실패를 잡습니다** — 코드 하한은 명시된 금지 표현을, 인코더는 금지어 없는 위법을, 조문 검색은 근거를, 문서 규칙은 문장을 넘는 조합을.
> ② 그들이 다른 답을 내면 **래칫이 정합니다**(3-5) — 코드가 하한을 걸고, 인코더는 근거 스팬이 있을 때만 올립니다.
> ③ 생성기는 **그들의 채점을 통과할 때까지만** 돕니다(3-3).
>
> 🔄 **판정 경로는 이제 「거의 선형」이 아닙니다.** 카테고리를 묻지 않고 경우별 답을 내기로 하면서 **법별 팬아웃–팬인**이 생겼습니다 —
> 품목을 가리면 그 품목의 법과 표시광고법으로만, 못 가리면 세 법 모두로 보내고, 전제마다 모아 **가장 보수적인 경우를 기록되는 판정**으로 올립니다.
>
> 🚨 **그래도 필연과 유용을 가릅니다.** 법별 팬아웃은 「한 문구에 여러 법이 동시에 걸린다」는 업무의 성질을 **구조로 드러낸 것**이고,
> 검색과 인코더는 팬아웃 **앞에서 한 번만** 돕니다. **순방향 체인으로 표현할 수 없는 순환**은 생성 경로(3-3)에 있습니다.
>
> 🚨 **그리고 7-6절로 클라우드에는 판정만 올립니다.** 배포된 시스템에서 보이는 그래프 구조는 **다법령 팬아웃과 보류 분기**이고, 순환 검증은 로컬에서 생성 경로로 보입니다.
> 심사에서 *"이건 함수 호출 여섯 번 아닌가요"* 가 나오면 **먼저 인정하고** — 검수는 팬아웃과 분기, 순환은 생성이라고 경로를 나눠 보입니다(A-4).
````
