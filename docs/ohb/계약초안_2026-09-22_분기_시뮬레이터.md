# 계약 초안 — 품목 분기 · 실증 분기 (D-242 · D-263 · D-265)

> 클론 A · **2판 2026-09-23** (1판 2026-09-22) · **상태: 초안 — 팀장 확인 대기** · `app/contracts.py` 는 잠금 1급이라 이 문서로 먼저 본다
> 🔄 **D-265 반영** — 검수는 대체 문구를 내지 않는다. 1판의 「전제부 후보」와 「검증기 둘을 푼다」는 **폐기**다. 검증기는 **더하기만** 한다
> 입력 — 원장 D-242(조건 칸) · D-263(시뮬레이터) · **D-265**(검수는 판정·지시까지) · 검토 `검토_2026-09-21_판정코어_목표정합.md` §5 권고(분기 4 · 「일반」 제외)
> 🚨 화면은 이 계약의 **픽스처**를 보고 만든다(D-124) — 계약이 늦게 바뀌면 화면을 다시 짠다

## 0. 한 장 요약

```
JudgeResponse
 ├─ outcome · sentences[] · …                         ← 지금과 같다. 🔴 이것이 「초기 판정」 = 기록되는 판정 (D-263 ①)
 ├─ premise_basis: 가장 보수적인 전제의 목록            🆕 초기 판정이 깐 전제 (인정 없음 · 실증 못함)
 ├─ branches[]: Branch                                🆕 품목 분기 — 문서 단위 (D-263 ④)
 │    premise · outcome · sentences[] · verified · criteria · evidence
 ├─ sentences[i].condition: Condition | None          🆕 D-242 조건 칸
 ├─ sentences[i].substantiation: SubstBranch | None   🆕 실증 분기 — 문장 단위 주석 (D-263 ④)
 └─ candidates[]                                      ⛔ **검수에서는 항상 빈 목록** (D-265) — 전제부 후보는 생성(B)의 것
```

## 1. 새 타입

| 타입 | 칸 | 뜻 |
|---|---|---|
| `Premise` (StrEnum) | `식품` · `건기식_인정` · `건기식_비인정` · `화장품` · `실증_있음` | 분기가 까는 전제. 🚨 **「일반」은 없다** — 판별 결과일 때만 쓴다. 기능성표시식품은 주석으로만(D-229 🔜) |
| `Branch` | `premise: list[Premise]` · `outcome: Outcome` · `sentences: list[SentenceJudgment]` · `verified: bool = False` · `criteria: str` · `evidence: list[EvidenceArticle]` | 한 전제에서 계산한 판정. `criteria` = **기준 문안**(조문에서 · D-263 ②). `verified` = 인정번호 대조가 됐는가(D-263 ⑥) |
| `SubstBranch` | `unsubstantiated: RiskAssessment` · `substantiated_max: Risk` · `accepted_evidence: str` | 문장 하나의 실증 분기. 실증 시 **「낮아질 수 있음」의 상한**만 적는다 — 적법이라 쓰지 않는다 |
| `Condition` (StrEnum) | `none` · `A` · `B` · `C` · `M` · `D` | D-242 조건 칸. 평가·라벨용. 응답에는 `SentenceJudgment.condition` 으로 싣는다 |

🔄 **2판 정정 — 「업무정지 위험 → 주의」는 위험도 한 축으로 나온다.** `Risk` 의 라벨이 이미 R0 특이사항 없음 · R1 주의 · **R2 업무정지 위험** · R3 영업 상실 위험이다(D-227). 1판 논의에서 「제재 축을 따로 실어야 한다」고 했던 것은 과했다 — 계약에 `Sanction` 타입 자체가 아직 없고, 화면 문구는 `risk` 전·후만으로 그려진다. 제재 상세(별표 처분·일수)를 응답에 실을지는 **별도 안건**으로 둔다.

## 2. 기존 타입에 더하는 칸

| 타입 | 칸 | 규칙 |
|---|---|---|
| `SentenceJudgment` | `condition: Condition \| None` · `substantiation: SubstBranch \| None` | `condition=B` ⇔ `substantiation` 있음 · `condition=C` 이면 `substantiation` 없음(C 는 분기하지 않는다 · D-61) |
| `JudgeResponse` | `premise_basis: list[Premise]` · `branches: list[Branch]` | `branches` 의 전제는 서로 다르다 · 초기 판정의 전제는 `premise_basis` |
| `HoldReason` | 🆕 `premise_unknown` | 품목은 가렸으나 **인정·실증이 미상**이라 전제를 정해야 갈린다. `cat_unknown`(품목 자체를 못 가림)과 다르다. 🚨 DB `ck_judgment_hold_reason_values` 와 **같이** 고친다 — 마이그레이션 **0018**(마지막이 `20260922_0017`) |
| `Candidate` | `premise` · `rejudged` · `kind` | **생성(B) 쪽에서만.** 검수 응답에는 후보가 없다(D-265) |

## 3. 검증기 — **더하기만 한다**

| 검증기 | 어떻게 | 근거 |
|---|---|---|
| `_no_candidates_for_qualification` | **그대로 둔다** | D-59 · D-265 (검수에 후보가 없으니 풀 일이 없다) |
| `_outcome_matches_payload` | **그대로 둔다** | D-125 · D-265 |
| 🆕 `_premise_not_verdict` | `Branch.verified=False` 인 분기의 결과가 초기 판정의 `outcome` 을 바꾸지 않는다(초기 판정은 `premise_basis` 로 계산된 것이어야 한다) | D-263 ① · D-125 |
| 🆕 `_no_premise_pass_badge` | `premise` 가 비지 않은 분기에는 **「전제 없는 통과」 표시 칸이 없다** — 화면은 전제 문구를 함께 그린다 | D-263 ③ · D-05 |
| 🆕 `_condition_iff_substantiation` | `condition=B` ⇔ `substantiation` 있음 · `condition=C` 이면 없음 | D-242 · D-61 |
| 🆕 `_hold_reason_premise` | `premise_unknown` 이면 `branches` 가 비지 않는다 — 전제를 정하라면서 선택지를 안 주지 않는다 | D-263 ② |

## 5. 게이트 (계약이 서면 같이)

- `condition=C` 문장에 실증 분기가 있으면 🔴 · `condition=B` 인데 없으면 🔴
- 미검증 분기가 초기 판정을 바꾸면 🔴 · 분기에 전제가 비면 🔴
- 🔄 **검수 픽스처에 후보가 있으면 🔴** (D-265) — 1판의 「A 문장의 전제 없는 후보」 게이트를 이것으로 바꾼다
- `premise_unknown` 인데 `branches` 가 비면 🔴

## 6. 정할 것 — 여섯

| # | 무엇 | 권고 | 걸리는 것 |
