# 계약 초안 — 품목 분기 · 실증 분기 · 전제부 후보 (D-242 · D-263 · D-264)

> 클론 A · 2026-09-22 · **상태: 초안 — 팀장 확인 대기** · `app/contracts.py` 는 잠금 1급이라 이 문서로 먼저 본다
> 입력 — 원장 D-242(조건 칸) · D-263(시뮬레이터) · D-264(전제에 묶인 생성) · 검토 `검토_2026-09-21_판정코어_목표정합.md` §5 권고(분기 4 · 「일반」 제외 · 한 번 넓게 검색 후 분기별로 거름)
> 🚨 화면은 이 계약의 **픽스처**를 보고 만든다(D-124) — 계약이 늦게 바뀌면 화면을 다시 짠다

## 0. 한 장 요약

```
JudgeResponse
 ├─ outcome · sentences[] · …                         ← 지금과 같다. 🔴 이것이 「초기 판정」 = 기록되는 판정 (D-263 ①)
 ├─ premise_basis: 가장 보수적인 전제의 목록            🆕 초기 판정이 깐 전제 (인정 없음 · 실증 못함)
 ├─ branches[]: Branch                                🆕 품목 분기 — 문서 단위 (D-263 ④)
 │    premise · outcome · sentences[] · verified
 ├─ sentences[i].substantiation: SubstBranch | None  🆕 실증 분기 — 문장 단위 주석 (D-263 ④)
 └─ candidates[]: Candidate(+ premise)                🔄 전제부 후보 (D-264)
```

## 1. 새 타입

| 타입 | 칸 | 뜻 |
|---|---|---|
| `Premise` (StrEnum) | `식품` · `건기식_인정` · `건기식_비인정` · `화장품` · `실증_있음` | 분기가 까는 전제. 🚨 **「일반」은 없다** — 판별 결과일 때만 쓴다(§5 권고 2). 기능성표시식품은 주석으로만(D-229 🔜) |
| `Branch` | `premise: list[Premise]` · `outcome: Outcome` · `sentences: list[SentenceJudgment]` · `verified: bool = False` · `criteria: str` · `evidence: list[EvidenceArticle]` | 한 전제에서 계산한 판정. `criteria` = **기준 문안**(조문에서 · D-263 ②). `verified` = 인정번호 대조가 됐는가(D-263 ⑥) |
| `SubstBranch` | `unsubstantiated: RiskAssessment` · `substantiated_max: Risk` · `accepted_evidence: str` | 문장 하나의 실증 분기. 실증 시 **「낮아질 수 있음」의 상한**만 적는다 — 적법이라 쓰지 않는다 |
| `Condition` (StrEnum) | `none` · `A` · `B` · `C` · `M` · `D` | D-242 조건 칸. 평가·라벨용. 응답에는 `SentenceJudgment.condition` 으로 싣는다 |

## 2. 기존 타입에 더하는 칸

| 타입 | 칸 | 규칙 |
|---|---|---|
| `SentenceJudgment` | `condition: Condition \| None` · `substantiation: SubstBranch \| None` | `condition=B` ⇔ `substantiation` 있음 · `condition=C` 이면 `substantiation` 없음(C 는 분기하지 않는다 · D-61) |
| `JudgeResponse` | `premise_basis: list[Premise]` · `branches: list[Branch]` | `branches` 의 전제는 서로 다르다 · 초기 판정의 전제는 `premise_basis` |
| `Candidate` | `premise: list[Premise] = []` · `rejudged: RiskAssessment` | 빈 목록 = 전제 없이 성립(보수·균형안). **자기 전제로 재판정한 결과**가 `rejudged` 다(D-264) |

## 3. 바뀌는 검증기 (🔴 지금 계약과 부딪히는 곳)

| 검증기 | 지금 | 바뀐 뒤 | 근거 |
|---|---|---|---|
| `_no_candidates_for_qualification` | A 자격형 문장이 하나라도 있으면 **후보 전면 금지** | A 문장에 대해 **전제 없는 후보는 삭제안·사실 진술안만** 허용 · 기능 주장 대체안은 `건기식_인정` 전제가 붙어야 한다 | D-264 의 D-59 해석 |
| `_outcome_matches_payload` | `outcome != passed` 이면 후보 금지 | 초기 판정의 `outcome` 과 **무관하게** 후보를 낸다 — 후보마다 `rejudged` 가 통과 여부를 말한다 | D-264 (위반 문구를 고치는 것이 생성의 목적) |
| 🆕 `_premise_not_verdict` | — | `Branch.verified=False` 인 분기의 결과가 초기 판정의 `outcome` 을 바꾸지 않는다(초기 판정은 `premise_basis` 로 계산된 것이어야 한다) | D-263 ① · D-125 |
| 🆕 `_no_premise_pass_badge` | — | `premise` 가 비지 않은 후보·분기에는 **「전제 없는 통과」 표시 칸이 없다** — 화면은 전제 문구를 함께 그린다 | D-263 ③ · D-05 |

## 5. 게이트 (계약이 서면 같이)

- `condition=C` 문장에 실증 분기가 있으면 🔴 · `condition=B` 인데 없으면 🔴
- 미검증 분기가 초기 판정을 바꾸면 🔴 · 전제부 후보·분기에 전제가 비면 🔴
- A 문장의 전제 없는 후보가 기능 주장을 담으면 🔴 (사전·규칙으로 잡는다 — 완전하지 않다 · 재판정이 뒤를 받친다)

## 6. 정할 것

1. `Premise` 다섯 값 — 품목 분기 넷(§5 권고) + `실증_있음`
2. 초기 판정의 `premise_basis` 기본값 — `건기식_비인정` 과 실증 없음 (가장 보수적)
3. 검증기 두 개를 푸는 방향(§3) — 특히 A 문장의 전제 없는 후보 허용 범위
4. `judgment` 테이블의 전제부 결과 저장 칸 — 저장 경로(동의 · D-96)를 만들 때 같이(잠금 1급)
