## ① 원장이 이미 정해 둔 것 — 먼저 읽는다

**양자화의 정본 대상은 인코더가 아니라 리랭커다.**

**D-79** (배포 경계를 과금 경계와 일치시킨다):

> 🚨 **메모리 4GB 대응** — 리랭커를 **ONNX int8 양자화**한다. ★ D-77 L3가 이미
> *"리랭커 < 500ms ← 최적화 1순위"* 로 잡아 둔 자리라 **성능과 메모리가 같은 조치로 풀린다.**

**D-84 ③** (스택 정밀화 · 리랭커 크기를 후보로 연다):

> `bge-reranker-v2-m3` 는 **0.6B**(bge-m3 = XLM-R-large 계열)다. **c7i.large 가 4GB** 이고
> D-77 L3 에서 이미 **최적화 1순위**로 지목한 자리다.
> 후보 — `bge-reranker-v2-m3` 0.6B (Apache-2.0) ↔ ★ `bge-reranker-base` **0.3B** (MIT)
> → **둘 다 재고 델타를 본다.** D-77 L1 의 「리랭커 전후 델타」에 축을 하나 더 넣는다.

즉 「양자화를 할 것인가」는 **리랭커에 대해서는 이미 결정돼 있다.** 남은 것은 두 가지다 —

- **E-1 · 리랭커** — 결정은 있고 **실행이 없다.** 리랭커 자체가 아직 선정되지 않았다(0.6B ↔ 0.3B 비교군만 열려 있다). 양자화는 그 선정 뒤에 붙는 작업이다.
- **E-2 · 인코더(KURE-v1)** — **원장에 없는 새 안건이다.** 이 초안이 다루는 것은 이쪽이다.

## ② 예산의 단위 — 요청당이다 (확정)

D-77 L3 「단계별 응답시간 예산」 원문:

| 단계 | 예산 |
|---|--:|
| 문장 분할 | < 50 ms |
| 카테고리 인코더 | < 100 ms |
| 규칙 매칭 (문자열) | < 20 ms |
| **BM25 + 벡터 검색** | **< 300 ms** |
| 🚨 리랭커 | **< 500 ms** ← 최적화 1순위 |
| 위법 유형 인코더 | < 150 ms |
| **판정 소계** | **≈ 1.1 초** |
| **판정 목표** | **p95 < 3 초** |

머리말 — 「총합이 아니라 **배분**을 정해 두어야 최적화 대상이 정해진다.」

**산수로 확정된다** —

```
50 + 100 + 20 + 300 + 500 + 150 = 1,120 ms  ≈  판정 소계 1.1 초
```

각 단계가 **한 번씩** 더해져 소계가 된다. 문장당이면 소계가 문장 수에 비례해야 하는데 그렇게
적혀 있지 않다. 그리고 「문장 분할」이 이 표 안에 한 줄로 있다 — 문장 분할은 요청당 한 번
일어나는 단계다.

→ **`BM25 + 벡터 검색 < 300ms` 는 요청 1건의 배분이다.**

## ③ 실측 — 그리고 어법 위반

| 구간 | 평균 | 최대 | 표본 |
|---|---|---|--:|
| `search` 전체 | 193.3 ms | 210.4 ms | 4 |
| ↳ `encode` (KURE-v1 · CPU) | 141.8 ms (73.4%) | 181.7 ms | 4 |
| ↳ SQL + 융합 (차감) | ≈ 51.5 ms | — | — |

원시값 — `search` 191.5 / 187.0 / 184.4 / 210.4 · `encode` 118.8 / 134.2 / 132.4 / 181.7
같은 프로세스에서 이어 쟀고, 모델 로드 포함 1회차(`search` 19,896.7 · `encode` 19,403.2)는 제외했다.

🔴 **D-77 L3 는 「p50 / p95 / p99 · 평균은 쓰지 않는다 — 시연에서 터지는 것은 꼬리다」로 적혀 있다.**
   위 표는 평균이고 표본 4개다. **어법 위반이고, p95 는 미실행이다** (D-146).
   → 같은 프로세스에서 30~50회를 돌려 p50 / p95 / p99 를 내야 한다. 그 전까지 이 표를 판정
   근거로 쓰지 않는다.

## ④ 용어

- **양자화(quantization)** · 모델 내부 숫자를 32비트 소수에서 8비트 정수 같은 작은 형식으로
  바꾸는 것. 계산이 빨라지고 메모리가 줄지만 값이 거칠어져 결과가 조금 달라진다.
- **ONNX** · 모델을 프레임워크에서 떼어내 표준 형식으로 굳힌 것. CPU 서빙에 쓴다.
  D-79 가 리랭커에 대해 지정한 형태가 **ONNX int8** 이다.
- **배치 인코딩** · 문장 여러 개를 한 번에 모델에 넣는 것. 한 번씩 N 번 넣는 것보다 훨씬 빠르다 —
  모델을 준비하는 고정 비용을 한 번만 내기 때문이다.
- **`pool`** · 융합 전에 각 검색기가 후보로 가져오는 행 수. 지금 50이다.
- **재현율(recall)** · 찾아야 할 조문 중 실제로 찾아온 비율. 이 서비스는 인용을 근거로
  판정하므로, 재현율이 떨어지면 **근거 없이 통과시키는 일**이 늘어난다.
- **p95** · 100번 중 95번은 이 시간 안에 끝난다는 값. 평균보다 꼬리를 본다.

## ⑤ 대안 — E-2(인코더)에 대해

**(가) 인코더를 양자화한다** — 142ms 를 50~70ms 로 줄인다.

- 얻는 것: 문장당 인코딩이 2~3배 빨라진다. 4문장에서도 인코딩 몫이 작아진다.
- 떠안는 것 ①: **🔴 DB 의 임베딩 2,400개를 전부 다시 만들어야 할 가능성이 크다.** 양자화된
  모델이 내는 벡터는 원본과 미묘하게 다르고, 질의 벡터만 바꾸면 문서 벡터와 좌표계가 어긋나
  재현율이 떨어진다. `embed` 전체 재실행 + 골든셋 재검증이 따라온다.
- 떠안는 것 ②: 벡터 보존율을 **재 본 적이 없다.**
- 떠안는 것 ③: **원장에 없는 대상이다.** D-79 가 양자화를 리랭커에 배정해 뒀으므로, 인코더까지
  양자화하려면 그 자리에 근거를 새로 적어야 한다.

**(나) 배치 인코딩을 넣는다** — `split` 을 세우는 작업에서 문장들을 한 번에 인코딩한다.

- 얻는 것: 문장이 N 개여도 인코딩은 1회분에 가깝다. 벡터가 안 바뀌니 재임베딩·재검증이 없다.
  `split` 작업에 어차피 들어가야 하는 일이다.
- 떠안는 것: SQL 은 문장 수만큼 그대로 돈다(4문장 = 약 206ms). 배치만으로 4문장이 300ms 안에
  들어갈지는 **재 봐야 안다** — 배치 인코딩 실측이 없다.

**(다) 검색 SQL 을 한 번에 묶는다** — N 개 질의 벡터를 한 SQL 로 보낸다.

- 얻는 것: SQL 51.5ms 중 왕복·계획 수립 같은 고정비를 한 번만 낸다. (나)와 합치면 4문장이
  300ms 안에 들어갈 여지가 생긴다.
- 떠안는 것: RRF 융합이 질의별로 분리되어야 하므로 쿼리와 후처리가 복잡해진다.
  `pool=50` 이 N 배로 늘어 메모리도 N 배가 된다.
- **아직 51.5ms 의 고정비/가변비 비율을 모른다.** 고정비가 작으면 이 안은 값을 못 한다.

**(라) 예산을 재배분한다** — 리랭커가 선정되지 않았고 그 자리가 500ms 다. 검색에 더 준다.

- 얻는 것: 코드 변경 0. 4문장 773ms 는 `300 + 500 = 800ms` 안에 들어간다.
  그리고 **판정 목표 `p95 < 3초`** 는 지금도 여유가 크다.
- 떠안는 것: 🔴 **리랭커를 안 쓰기로 정해야 이 안이 성립한다.** D-77 L1-4 는 「리랭커 전후
  델타」로 그걸 **계산으로** 정하라고 했고, 그 델타를 아직 안 쟀다. 재기 전에 예산을 옮기면
  「리랭커를 쓸 것인가」를 측정 없이 결정해 버리는 것이다.
- 예산 배분을 바꾸는 것은 D-77 본문을 고치는 일이므로 **D 번호가 필요하다.**

**(마) 지금 아무것도 안 한다** — `split` 이 스텁이라 실제로 문장 하나만 돈다. 설 때 다시 잰다.

- 얻는 것: 위험 0. 발표 준비에 시간을 쓴다.
- 떠안는 것: `split` 이 설 때 예산 초과가 드러나면 그때 급하게 처리해야 한다.

## ⑥ 권고

**(나) 를 `split` 과 같은 작업에 묶고, 그 자리에서 (다)의 고정비를 재고, (가)는 하지 않는다.**

근거 —

1. **예산이 요청당이므로 2문장부터 이미 초과다.** (마)「지금 안 한다」는 성립하지 않는다 —
   `split` 이 스텁이라 증상이 안 보이는 것뿐이고, 세우는 순간 드러난다.
   **그래서 (나)는 `split` 보다 나중이 아니라 같은 작업이어야 한다** (D-99 어법 — 읽는 쪽을
   같은 작업에서 만든다).
2. **(가)의 진짜 비용은 속도가 아니라 색인이다.** 2,400개 재임베딩과 골든셋 재검증이 붙을
   가능성이 크고, 그건 발표 전에 들일 위험이 아니다. 09-14 에 파생물이 낡아 인용률이
   38.1% 로 떨어져 있던 일이 색인 축을 건드리는 일의 무게를 보여 준다.
   그리고 **원장이 양자화를 리랭커에 배정해 뒀다** — 인코더는 그 자리를 새로 열어야 한다.
3. **(다)는 (나)와 함께 재야 값이 보인다.** 배치를 넣은 뒤 남는 것이 SQL 뿐이므로, 그때
   고정비를 재면 묶을 값이 있는지 바로 나온다. 따로 볼 일이 아니다.
4. **(라)는 리랭커 델타를 잰 뒤에 놓는다.** 지금 옮기면 「리랭커를 쓸 것인가」를 측정 없이
   정하는 셈이다. D-77 이 그것을 하지 말라고 세운 층이 L1-4 다.
5. **E-1(리랭커 양자화)은 이 초안의 대상이 아니다.** 결정은 D-79 에 있고, 실행은 리랭커 선정
   뒤다. 발표 뒤 순서에 넣는다.

## ⑦ 내가 틀렸던 것 — 1차본 폐기 경위

1. **예산을 「문장당인지 요청당인지 모른다」고 열어 뒀다.** D-77 본문의 소계 산수
   (50+100+20+300+500+150 = 1,120 ≈ 1.1초)만 더해 보면 요청당임이 바로 닫힌다.
   본문을 읽지 못한 상태에서 판정을 갈라 놓은 것이 아니라, **읽고 나서도 산수를 안 해 본 것**이
   아니다 — 본문을 아예 못 읽었다. 읽을 수 있게 된 뒤에 닫혔다.
2. **양자화 대상을 인코더로 잡았다.** D-79 가 리랭커 ONNX int8 을 이미 정해 뒀고,
   D-84 ③ 이 리랭커 크기까지 후보로 열어 뒀다. 원장을 읽지 않고 안건을 세웠다.
3. **평균으로 보고했다.** D-77 L3 는 평균을 쓰지 말라고 명시한다.
4. 1차본의 권고 (라)「지금 안 한다」는 예산이 문장당이라는 잘못된 전제 위에 있었다.

★ 뿌리는 하나다 — **D 번호를 인용하기 전에 원장 본문을 읽는다 (D-100)** 를 지키지 못했다.
  이 날 다른 클론의 파일 스테이징이 살아 있는 것을 확인한 뒤에야 본문을 읽었다.

## ⑧ 다음에 잴 것

`split` 을 세우는 작업에서 아래 셋을 같이 잰다.

1. **`search` p50 / p95 / p99** — 같은 프로세스에서 30~50회. D-77 L3 어법.
2. **배치 인코딩 실측** — 문장 1·2·4·8개를 한 번에 인코딩할 때의 ms. 인코딩이 문장 수에 대해
   얼마나 완만한지가 (나)의 값을 정한다.
3. **SQL 고정비/가변비** — `pool` 을 바꿔 가며 SQL 몫을 재고, 묶음 SQL 의 여지를 본다.

그리고 별건으로 —

4. **리랭커 전후 델타** (D-77 L1-4) — (라)를 판정할 수 있게 되는 조건.
5. **양자화 시 벡터 보존율** — KURE-v1 을 양자화했을 때 코사인 유사도가 얼마나 보존되는지.
   (가)의 비용 추정이 여기서 갈린다.

## ⑨ 깔고 간 가정

- 배포 환경이 **CPU(ONNX)** 라는 것 — D-79 의 c7i.large 4GB · ONNX CPU 서빙을 그대로 받았다.
  GPU 로 서빙하면 위 표 전체를 다시 재야 한다.
- 「단순 반복 = `search` × N」 — 지금 구조에서 문장마다 `search` 를 부른다고 보았다.
  `split` 이 스텁이라 **실제로 그렇게 도는 것을 본 적은 없다.**
- 양자화 인코더의 벡터가 원본과 어긋난다는 것 — 일반적으로 그렇다고 알려진 것이고
  **KURE-v1 에 대해 재지 않았다.**
