## 3. 🚨 이어서 작업할 때 반드시 알아야 할 것

### ① 법제처가 XML 에 HTML 엔티티를 섞어 보낸다

```
<키워드>식품등의 표시&middot;광고에 관한 법률</키워드>
```

XML 이 정의하는 엔티티는 `& < > " '` 다섯뿐이다. **질의에 `·` 가 들어 있기만 하면** 파싱이 죽고,
`search()` 가 그것을 **「OC 가 승인되지 않았거나 값이 틀렸다」로 단정**했다 — 키는 멀쩡한데.
바로 앞뒤 질의가 성공하는 상황이라 다음 사람은 키를 재발급하며 시간을 쓴다.

고쳤다 — `_parse` 가 **실패했을 때만** 정규화하고, `data/raw/` 에는 원문 바이트가 그대로 간다 (D-117).
`_parse_failure` 는 **HTML 이 온 경우에만** OC 를 언급한다.

🚨 **다만 질의는 여전히 못 쓴다.** 파싱은 살았지만 서버가 `&middot;` 로 되받아 **본문검색에서도 0건**이다.
**질의에 `·` 를 넣지 마라.** 「식품등의 표시·광고에 관한 법률」 0건 / 「식품등의 표시광고에 관한 법률」 5건.

### ② 본문검색(`search=2`)은 구가 아니라 **토큰 AND** 다

「표시광고」로 잡힌 재결례 5건의 본문에 **문자열 「표시광고」는 0회**였다.
「표시」1회·「광고」1회처럼 두 흔한 단어가 각각 나온 무관한 문서들이었다.
`decc` 는 「광고」 521건 중 **496건**이 「부당한 광고」로 잡힌다 — 거의 안 걸러진다.

그대로 받으면 2,769건 중 대부분이 무관하다. **18분을 쓰고 공공기관 서버를 5,500번 두드리는 일**이고,
규약 5 가 「우리가 막히는 것으로 끝나지 않고 『공식 API 이용』이라는 근거 자체가 흔들린다」고 적어 둔 자리다.
**효율이 아니라 거버넌스로 다뤘다.**

### ③ C1 을 그대로 쓸 수 없는 자리다 — 사람이 박는 것을 **ID 에서 질의로** 옮겼다

법령은 소수·고정이라 「ID 는 사람이 박는다」가 성립한다. 판례·재결례는 **집합**이고 늘어난다.
재현성의 근거가 「ID + 시행일」에서 **「질의 + 수집일 + 그때의 실측 건수」**로 바뀐다 —
🚨 **그 실측을 남기지 않으면 재현성이 없다.** `collect_cases()` 가 표를 찍고 사실원장에 옮기는 이유다.

### ④ 파일명에 일자를 넣지 않는다 — **법령과 다르다**

법령은 개정마다 새 시행본이 나와 `{id}_{시행일}` 로 판을 구분해야 하지만,
판례·재결례는 **확정된 사건 기록이라 판이 하나뿐이다.** 규약 2 는 `save_raw()` 의 sha256 이 이미 지킨다.

🚨 처음에는 법령 관례를 **근거 확인 없이 복사**했고, 일자가 아예 없는 record 6건이 저장을 거부당하면서 드러났다
(`decc` 268809 은 `처분일자`·`의결일자` 가 둘 다 비었다). **관례는 그 근거가 적용될 때만 옮긴다.**

### ⑤ 「본문 미제공」과 「실패」를 갈랐다

`prec` 8건은 **서버 자신의 검색 인덱스**가 준 ID인데 본문 조회가 빈 봉투를 준다.
우리가 고칠 것이 없고 재실행해도 같다. 예전 코드는 이걸 실패로 세고 「위 사유를 먼저 해결하라」고 했다 —
**해결할 게 없는데 그렇게 말했다.**

판별은 **문구가 아니라 자식 요소의 유무**로 한다. `LID` 로 우회되지 않는다 —
네 건 전부 1,940바이트 상수 응답이었고 **정상 동작하는 622249 조차 그랬다**(양성 대조).

### ⑥ 🔴 **질의로 좁히기 전에 전량 규모를 먼저 잰다** (2026-09-06 확정 · 팀장)

오늘 `ftc_decisions_body` 에서 드러난 것 —

```
표시광고   1,087 | 원장에 없음      0     ← 09-02 수집은 그 질의로는 완전했다
부당광고   1,285 | 원장에 없음    490
광고       1,751 | 원장에 없음    664
(전체)     8,257
```

🚨 **실패한 것은 수집기가 아니라 질의 선택이다.** 「표시광고」가 토큰 AND 라
**「표시」가 안 나오는 광고 사건 664건을 처음부터 범위 밖에 뒀다.** 그리고 그 사실이
**4일간 드러나지 않았다** — 안 받아본 것 중에 무엇이 있는지는 볼 방법이 없기 때문이다.

**규칙** —

1. 새 소스를 붙일 때 **질의 없는 전체 건수를 먼저 잰다.** 한 번의 호출이다.
2. 전량이 감당 가능하면 **전량을 받고 선별은 `preprocess/` 가 한다** (D-92).
   `ftc_body` 는 처음부터 `--query` 없이 돌리면 전량(8,257건 · 70분)이었다.
3. 전량이 불가능하면 질의로 좁히되, **무엇을 놓치는지 함께 적는다** —
   질의별 실측표와 「전체 대비 몇 %인가」를 사실원장에 남긴다.

🚨 **질의를 바꿀 때마다 재조회하는 것이 전량 한 번보다 결국 서버를 더 두드린다.**
`ftc_decisions_body` 는 오늘이 두 번째 재조회다. 규약 5 를 효율이 아니라 총량으로 본다.

길이 임계값이 필요해 「문구로 찾지 않는다」와 축이 다르다. **설계 결정으로 올린다.**

**그리고 이 고시가 CopyLane 에 얼마나 필요한지는 따로 볼 문제다.** 성분·함량 기준이지 광고 표현 규범이 아니다.
정작 광고 규범인 **「건강기능식품의 표시기준」(`31854`, 20250829)은 `covers` 에 없다** — D-15 등재 대상이다.

## 8. 다른 클론에서 재개할 때

🚨 **클론 A · B 의 `data/raw/` 는 서로 다르다** (사실원장 「저장소 · 작업 클론」 절).

원장(`manifest.jsonl`)은 커밋되므로 **원장 행 수는 저장소의 사실이지 그 클론의 사실이 아니다** —
09-05 인계 §6 이 지적한 그 문제이고, 이번에 실물로 겪었다.

**클론 B 확인된 상태** — 게이트 37 통과 · 테스트 113건(gate 37 + http 99·3xfail + parse 14) · `.env` 키 8종 등재 ·
`ohb` == `origin/ohb` (`bf22b4b`) · `data/raw/law/` 224파일

🚨 **클론 A 의 커밋 안 된 변경은 여전히 확인 못 했다** (09-05 인계에서 넘어온 항목).
거기 앉을 때 `git status` · `git stash list` · `git log --oneline ohb --not origin/ohb` 를 봐야 한다.

🚨 **환경 주의** — Cowork 의 device 셸은 Linux VM 이라 레포의 Windows `.venv`/`uv` 를 쓰면 안 된다.
그리고 이 세션에서 그 VM 이 계속 뜨지 않아 파일을 stage/commit 으로만 다뤘다.
**문서를 쓴 뒤에는 기기 파일 크기를 확인한다** — 도구가 성공을 반환했는데 실제로 안 써진 일이 한 번 있었다.
