# 결정 요청 — 화면 계약 3건 (2026-09-03)

> 오한빈 · 브랜치 `ohb`
> **왜 이 문서가 있는가** — 팀원이 만든 화면과 우리 설계가 어긋난 자리 셋이 나왔는데, **셋 다 우리 설계에 계약이 없어서 생긴 빈칸**이다.
> 화면을 고치기 전에 **없던 계약을 먼저 쓴다.** 순서가 반대면 팀원이 두 번 일한다.
> **읽는 법** — 문제 → 대안 → 각각이 얻는 것과 잃는 것 → 권고. **결정은 팀장이 한다.**

## 계약 ③ · 사전 갱신 경로 — **가장 급하다**

### 문제

금지 표현 사전은 지금 이렇게 만들어진다.

```
고시 6범주 ──[P6] 사전 구축──> data/derived/ 사전 파일
```

`data/derived/` 는 **파생물**이다 (D-92 — *"파생물 — **사전** · 골든셋 · 페어 · 세그먼트"*). 파생물은 **언제든 다시 만들 수 있어야 하고**(기획서 4-5 원칙 ③), 다시 만들면 **이전 것을 덮어쓴다.**

그런데 운영하면 반드시 이런 일이 생긴다.

| 상황 | 예 |
|---|---|
| 새 표현이 나타난다 | 유행어·신조어 |
| **오탐이 발견된다** | 🚨 *"본 제품은 질병의 예방·치료를 목적으로 하지 않습니다"* — **우리가 붙여 준 필수 병기 문구가 금지어에 걸린다** (기획서 2-4 ②가 이미 든 예) |
| 카테고리별 예외 | 화장품에서는 되고 건기식에서는 안 되는 표현 |

운영자가 관리자 화면(`CL-A-096`)에서 이걸 고치면 — **다음 재생성 때 사라진다. 조용히.**

> **진짜 질문은 「편집을 허용할까」가 아니다.** 편집은 필요하다. 질문은 **「사람이 넣은 지식을 어디에 둘 것인가」**다.

### 대안

| | 방식 | 얻는 것 | 잃는 것 |
|:-:|---|---|---|
| **A** | **사전을 원본으로 승격** — 초판만 자동 생성하고 이후는 손으로 관리 | 화면 편집이 그대로 동작. **구현이 제일 쉽다** | 🚨 **고시가 개정돼도 자동으로 못 따라간다.** 그리고 D-92 의 파생물 정의를 깬다 — 예외를 하나 만들면 *"무엇이 파생물인가"* 가 흐려진다 |
| **B** | ★ **오버레이** — 사전은 생성물로 두고, 사람 입력은 **별도 원본 파일**에 쌓아 병합 | **재생성해도 사람 입력이 산다.** 오버레이 파일만 보면 *"사람이 무엇을 더했나"* 가 한눈에 — **그 자체가 감사 로그다.** 게이트를 붙일 수 있다 | 병합 규칙을 정해야 한다(충돌 시 누가 이기나). 파일이 하나 는다. **반나절** |
| **C** | **화면 편집을 막고 사전 변경은 PR 로만** | 새로 만들 것이 없다 | 🚨 **운영자가 오탐을 못 고친다.** 관리자 화면 4개 탭 중 2개가 죽는다 — 팀원 작업이 버려진다 |

```
[B 의 모양]
   고시 6범주 ──[P6]──> 사전 본체 (생성물 · 언제든 재생성)
                            +
   dict_overlay.yaml (손으로 쓴 원본 · 커밋 대상) ──> 병합 ──> 최종 사전
```

### 권고 — **B**

**이 프로젝트가 같은 문제를 이미 두 번 풀었다.** `registry_head/tail.yaml` → `data_sources.yaml`(D-90), `_matrix/data.js` → `판정매트릭스.html`(D-90). **세 번째로 같은 패턴을 쓰면 팀이 새로 배울 것이 없다.**
그리고 오버레이 파일이 **커밋 대상**이므로 「누가 언제 무엇을」이 git 에 남는다 — **감사 로그를 따로 만들지 않아도 된다.**

### 🚨 함께 정할 것 — 오버레이에 2인 확인을 요구할 것인가

| | 방식 | 트레이드오프 |
|:-:|---|---|
| 1 | **전부 2인 확인** | 안전하지만 **오탐 하나 고치는 데 두 사람**이 붙는다. 운영 속도가 죽는다 |
| 2 | **전부 1인** | 빠르지만 **한 사람이 금지어를 지울 수 있다** |
| ★ 3 | **추가는 1인 · 삭제/완화는 2인** | **D-09 안전 방향 단조성의 자연스러운 확장** — 넓히는 건 쉽고 좁히는 건 어렵게. 규칙이 하나 늘지만 이미 있는 원칙이다 |

## 계약 ① · 판정 표시 — 위험도와 상태를 화면에서 어떻게 가르는가

### 문제

화면이 배지 **5종**을 한 줄에 쓴다 — `높음` `주의` `없음` `판정 보류` `근거 불일치`.
앞 셋은 **위험도(정도)** 이고 뒤 둘은 **상태(신뢰)** 다. 섞으면 둘이 깨진다.

- 사용자가 「판정 보류」를 등급으로 읽는다 — *"보류는 낮음보다 안전한가?"*
- 🚨 우리가 **MAE·QWK 로 못 잰다** — 순서 없는 값이 순서형에 섞였다 (D-09 래칫은 전순서 위에서만 성립)

### 대안

| | 방식 | 얻는 것 | 잃는 것 |
|:-:|---|---|---|
| **A** | **배지 2개** — 위험도 배지 + 상태 배지를 나란히 | 축이 그대로 보인다. 구현 단순 | 🚨 **화면이 시끄럽다.** 확정일 때도 상태 배지가 떠 노이즈. 두 배지의 관계를 사용자가 해석해야 한다 |
| **B** | ★ **배지 하나 + 상태가 그 배지의 표현을 바꾼다** | **한 칸으로 읽힌다.** 목록 화면에서도 그대로 쓴다. **D-09 구조가 화면에 그대로 나타난다** | 상태별 렌더 분기 3가지 — 화면 코드가 조금 는다 |
| **C** | **상태를 배지가 아니라 별도 안내 영역으로** | 배지는 순수하게 위험도만. 가장 깨끗 | 🚨 **목록(검수 이력)에서 상태가 안 보인다** — 배지만 보고 판단하게 된다 |

```
[B 의 모양]
  확정         [높음]                 평소 배지
  보류         [높음 · 판단 보류]      회색 테두리
                                      "근거 규정상 최소치입니다. 문맥 판단은 보류했습니다"
  근거 불일치   [근거 확인 필요]        🚨 위험도를 숨긴다
```

★ **보류일 때 위험도를 보여주는 근거** — D-09 의 `max(코드 하한, 인코더 예측)` 에서 **보류는 「인코더 가산을 쓰지 않는다」는 뜻**이지 코드 하한이 사라지는 게 아니다. **위험도는 언제나 존재한다.**
★ **근거 불일치일 때 숨기는 근거** — 인용 검증 실패 = 근거가 틀렸다. **근거 없는 판정은 출력하지 않는다**(게이트 19 · D-100).
⚠️ 이름은 「판정 불가」가 아니라 **「근거 확인 필요」** — D-59 의 **합법화 불가 증명서**와 헷갈린다.

### 권고 — **B**

### 🚨 함께 정할 것 — 관리자 대시보드는 3종, 우리는 4단계

| | 방식 | 트레이드오프 |
|:-:|---|---|
| ★ 1 | **4단계 그대로 보여준다** | 정확하다. **접는 규칙이 생기지 않는다** — 규칙이 하나 늘면 두 곳이 갈라진다(D-54). 색만 3색으로 묶어 시각적으로 단순화 |
| 2 | **3종으로 접는다** | 읽기 쉽지만 **「어떻게 접는가」가 또 다른 결정**이고, 그 규칙이 사용자 화면과 갈라질 수 있다 |

## 계약 ② · 레지스트리 운영 화면 — 등급과 검증 상태의 관계

### 문제

`CL-A-058/059` 는 **소스 레지스트리의 운영 화면**이다 (근거 상세 = *"소스 상세 팝업"*). **G0~G3 는 우리 거버넌스 등급과 같은 축이고, 화면이 옳게 쓰고 있었다.**

문제는 화면이 `등급(G0~G3)` 과 `검증 상태(검증 완료·검토 중·격리)` 를 **독립된 두 필드**로 둔 것이다.
🚨 **우리 정의에서 G0 = 「미표기·미확인」이라 등급이 검증 여부를 이미 포함한다.** 그래서 **`G0 + 검증 완료`** 라는 존재할 수 없는 조합이 대표 캡처가 됐고, 화면명까지 됐다.

> 그리고 팀원이 스스로 적어 뒀다 — *"공통 등급 옵션은 **치명·높음·보통**이므로 목록의 G0~G3 등급 체계와 맞지 않는다."*
> **필터 드롭다운이 위험도 옵션을 쓰고 있다** — 한 화면에 거버넌스 등급과 위험도가 섞였다. 계약 ① 과 여기서 만난다.

### 대안

| | 방식 | 얻는 것 | 잃는 것 |
|:-:|---|---|---|
| **A** | **검증 상태 필드를 없애고 등급 하나로** | 불가능 조합이 원천 소멸. 필드가 준다 | 🚨 **`reviewed_by`(2인 확인 서명)가 화면에서 사라진다** — 우리 거버넌스의 핵심 증거다. S0-14 검토표를 따로 열어야 한다 |
| **B** | **두 필드 유지 + 조합 제약** — G0 면 검증 상태를 고를 수 없게 | 서명이 보이고 불가능 조합이 막힌다 | 화면에 제약 규칙이 생긴다. **왜 막히는지 설명하지 않으면 버그로 보인다** |
| **C** | ★ **필드 이름을 우리 필드명으로 바꾼다** — 「검증 상태」 → **「2인 확인」** (`서명 완료 / 미서명 / 이견`) | **이름이 곧 정의다.** G0 는 정의상 미서명이므로 관계가 자명해진다. **대응표가 필요 없어진다** (D-54) | 팀원이 만든 화면 문구를 바꿔야 한다. **격리(quarantine)를 따로 표시**해야 한다 |

### 권고 — **C + B 의 제약**

이름을 레지스트리 필드명(`reviewed_by`)에 맞추면 **화면↔데이터 대응표를 만들 필요가 없다.** 두 벌이 안 생긴다.

🚨 **격리(quarantine)는 검증 상태의 값이 아니다.** 등급·서명과 **독립 축**이다 — `mfds_press` 는 서명 여부와 무관하게 격리돼 있다. **별도 플래그로 표시한다.**
