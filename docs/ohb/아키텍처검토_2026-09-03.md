## 2. 🚨 반영되지 않은 것 넷

### ① 결정은 있는데 집행이 없다 — D-121 `U-USER`

```
grep -rn "U-USER" data_sources.yaml docs/00_거버넌스_집행계약.md scripts/registry_head.yaml

```

**D-51 이 이 프로젝트에 준 원칙은 「거버넌스는 문서가 아니라 코드가 강제한다」다.** 지금 D-121 은 **문서일 뿐이다.** 사용자 업로드물이 학습 경로에 들어가도 **어느 게이트도 실패하지 않는다.**

🚨 **그리고 넣을 자리가 자명하지 않다.** 레지스트리는 **생성물**(D-90)이라 손으로 못 고치고, 원본인 판정매트릭스는 **「소스 73종」의 판정표**인데 `U-USER` 는 소스가 아니다 — **축이 다르다.** (3-③ 판단 필요)

### ② 공식 산출물 3종이 커밋되지 않는다

## 3. 판단이 필요한 사항 — 우선순위

### 1순위 · 🚨 위험도 축 / 판정 상태 축 — **9/10 까지** (harness 마감)

이것을 「UI 표기 불일치」로 보면 늦는다. **라벨 스키마 문제다.**

```
위험도  = 순서형 회귀 헤드 · MAE·QWK 로 측정      (기획서 6-3 L1)
판정 보류(Abstention) · 근거 불일치(인용 검증 실패) = 상태이지 정도가 아니다
```

🚨 **순서형 라벨에 상태를 클래스로 섞으면 순서 관계가 깨지고 MAE·QWK 가 무효가 된다.** 「높음을 중간으로 본 것과 낮음으로 본 것은 같은 오답이 아니다」라는 D-77 의 근거 자체가 사라진다.
그리고 **harness 가 라벨 정의를 고정한다**(D-94). harness 마감이 **2W 말 = 9/10** 이므로 **그 전에 정해야 하고, 늦으면 재학습이다.**

**권고**

| 축 | 값 | 누가 정하는가 |
|---|---|---|
| **위험도** | 4단계 순서형 — 형사 리스크 / 과징금 / 업무정지 / 주의 | 모델 (인코더 순서형 헤드) |
| **판정 상태** | 확정 / 보류 / 근거 불일치 | 코드·그래프 (모델 아님) |

관리자 대시보드의 3종 분포는 **위험도 4단계를 접어 보여주는 뷰**로 정의한다 — 새 축이 아니다.

### 2순위 · 이진(xlsx) 산출물의 원본을 어디에 둘 것인가 — **다음 커밋 전**

| | 방식 | 얻는 것 | 잃는 것 |
|:-:|---|---|---|
| **(a)** | `docs/01_기획/` 에 xlsx 를 그대로 커밋 | 가장 싸다. 팀이 즉시 본다 | diff 가 안 보이고 **동시 편집 시 병합 불가** |
| **(b)** | 요구사항을 **YAML/CSV 로 레포에 두고 xlsx 는 생성물** | `data_sources.yaml` 과 **정확히 같은 패턴**. diff·게이트·자동 검사가 붙는다 | 왕복 도구를 만들어야 한다 (반나절) |
| **(c)** | 지금 상태 유지 (`dist/` 만) | 없음 | 🚨 **팀이 못 본다.** 8/31 사고 재현 |

### 3순위 · `U-USER` 를 어느 파일에 넣을 것인가

`U-USER` 는 **소스가 아니다.** 판정매트릭스(소스 73종 × 판정 10축)에 넣으면 매트릭스와 레지스트리의 1:1 대응이 깨진다 — **D-99 가 경계한 형태다.**

**권고** — 손으로 쓴 입력인 `scripts/registry_head.yaml` 에 **별도 블록**으로 두고, 매트릭스와 대응시키지 않는다. 그것이 축이 다르다는 사실을 구조로 말한다.
게이트는 한 줄이면 된다 — **「업로드 저장 경로가 학습·색인 코드에서 참조되면 실패」** (게이트 17번과 같은 형태).

### 4순위 · 요구사항 ID 체계가 둘로 갈렸다

| 체계 | 단위 | 출처 |
|---|---|---|
| `REQ-U-xxx` · `REQ-A-xxx` | **화면** | 팀원 v2.1~v2.2 |
| `REQ-N-xxx` · `REQ-T-xxx` · `REQ-I-xxx` | **항목** | v3.0~v3.1 |

7W 테스트가 이 ID 로 추적하는데 **단위가 다른 두 체계를 오간다.** 화면 단위 ID 는 *"REQ-U-008 을 통과했다"* 가 무엇을 뜻하는지 정의되지 않는다(항목 17개 중 몇 개?).

**결정할 것** — 화면 ID 아래 항목 번호를 붙여 `REQ-U-008-03` 으로 갈 것인가, 아니면 테스트는 비기능·신규 요구사항(항목 단위)만 ID 로 추적하고 화면은 수용 기준(05 시트)으로 볼 것인가.
※ 팀원이 만든 **05 시트가 이미 화면별 수용 기준**을 갖고 있다. 후자가 싸다.

## 5. 🚨 정리 필요 — `.git/index.lock`

내가 device 셸에서 `git status` 를 돌려 만들었고, 삭제 권한이 없어 지우지 못했다.
**커밋 전에 지워야 한다** — `del .git\index.lock`

> 이 실수는 9/3 인계 문서에 **내가 적어 둔 규칙**을 그대로 어긴 것이다. 규칙을 문서에 적는 것으로는 안 지켜진다는 증거가 하나 더 늘었다.
