## 0. 🚨 먼저 — 보안 사고 하나. D-111 이 못 막은 **네 번째 경로**

`cosmetic_*` 두 건이 403 으로 실패했고, **오류 메시지가 요청 URL 을 통째로 찍었다** — `serviceKey` 값까지. 그 문자열이 터미널·스크롤백·대화 기록에 남았다.

```python
# collect/http.py:75  ← 여기다
raise FetchError(f"{url} — {MAX_RETRY}회 시도 실패: {last_error}")
```

D-111 이 센 경로는 **화면 입력 · 셸 인자 · 키 이름** 셋이었다. **오류 메시지**는 그 셋 어디에도 없다. 그리고 이 경로는 앞의 셋과 성질이 다르다 — **사람이 실수해서가 아니라 코드가 정상 동작해서 샌다.** 실패할 때마다 샌다.

🚨 **`path` 형은 더 나쁘다.** 식품안전나라는 키가 **경로**에 있다:

```
http://openapi.foodsafetykorea.go.kr/api/{keyId}/I0470/json/1/100
```

쿼리 파라미터만 가리는 마스킹은 이쪽을 못 막는다. `mfds_*` 가 실패했다면 `FOODSAFETY_KEY` 가 같은 방식으로 샜다.

### 해야 할 것

| | 무엇 | 급함 |
|:-:|---|:-:|
| ① | **`DATA_GO_KR_KEY` 재발급** — 노출된 값은 폐기한다. data.go.kr 마이페이지에서 인증키 재발급 | 🚨 즉시 |
| ② | `http.py` 에 **URL 마스킹** — 쿼리(`serviceKey`·`OC`·`key`·`authKey`)와 **경로 키(`/api/<키>/`)** 를 둘 다 가린다. 예외 메시지·로그·print 전부 이 함수를 거친다 | 🚨 높음 |
| ③ | **게이트 신설** — `collect/` 안에서 `FetchError`·`print`·로그에 **가공되지 않은 url 변수**가 들어가지 않는지 AST 로 검사 (게이트 17 의 교훈대로 문자열이 아니라 AST) | 중 |
| ④ | 설계결정 후보 — 「키가 새는 경로는 셋이 아니라 넷이다. 넷째는 사람이 아니라 **코드가 정상 동작할 때** 샌다」 | 팀장 판단 |

## 1. 403 의 원인 — 신청 문제가 아니다. **이중 인코딩**이다

실패한 URL 의 키 부분이 이렇게 생겼다:

```
serviceKey=…UiAS%252F8A0…ikK3%252BcCC1…Wlr%252BQ%253D%253D
             ^^^^^         ^^^^^         ^^^^^ ^^^^^
```

`%25` 는 `%` 의 인코딩이다. 즉 **`%2F` 가 다시 인코딩돼 `%252F` 가 됐다.**

- data.go.kr 은 인증키를 **Encoding 용 · Decoding 용 두 가지**로 준다.
- `.env` 에 들어간 값은 **Encoding 키**다 (이미 `%2F`·`%2B`·`%3D` 를 품고 있다).
- `openapi.py:71` 의 `urlencode(params, safe='')` 가 그것을 **한 번 더** 인코딩했다.

→ **`.env` 에는 Decoding 키를 넣는다.** (`http.py:46` 의 `encode()` 는 query 를 `safe="=&?/%"` 로 다시 quote 하는데 `%` 가 safe 라 여기서는 이중 인코딩이 생기지 않는다. 원인은 `openapi.py` 쪽 하나다.)

🚨 재발급받은 뒤 **Decoding 키**로 넣는다. `.env.example` 의 `DATA_GO_KR_KEY` 주석에 이 한 줄을 넣어 두는 것이 맞다 — 다음 사람이 똑같이 밟는다.

**공통 봉투** — 두 소스가 완전히 같다:

```json
{ "<service_id>": {
    "total_count": "5378",        ← 🚨 문자열이다. int 로 캐스팅할 것

    "RESULT": {"MSG": "정상처리되었습니다.", "CODE": "INFO-000"}

```

🚨 `RESULT.CODE` 를 확인하지 않고 `row` 를 읽지 않는다. 정상은 `INFO-000` 이다.

## 3. 🚨 전처리가 먼저 다뤄야 할 것 — 문자 깨짐

`DAY_INTK_CN` 첫 건이 이렇다:

```
“식물스타놀 에스테르” 로서 2.5？3.4 g/일
                            ^
```

물결표(`~`)나 특수문자가 **`？`(전각 물음표)로 깨져** 들어온다. 원본 인코딩 변환이 잘못된 흔적이고, **우리 쪽 디코딩 문제가 아니다** — 파일에 그렇게 저장돼 있다.

같이 보이는 것:

- 따옴표가 **섞인다** — `“ ”`(전각) 와 `"`(반각) 가 한 레코드 안에 함께 온다
- 로마숫자가 섞인다 — `Ⅱ`(전각 U+2161) 와 `II`(라틴 대문자 두 개)가 **같은 뜻으로** 온다
- 빈 값이 `.` 한 글자로 온다 (`DAY_INTK_CN: "."`)

→ **정규화 규칙이 전처리 1순위다.** 승인 문구를 사전으로 쓰는데 같은 문구가 표기만 달라 안 맞으면 2층이 헛돈다.

| 규칙 | 내용 |
|---|---|
| N1 | 전각→반각 (따옴표 · 괄호 · 로마숫자 · 물음표) |
| N2 | `？` 는 **손실이다** — 복원하지 말고 **플래그를 세워 격리**한다. 추정 복원 금지 |
| N3 | 빈 값 표기 통일 — `.` · `""` · 공백 → `null` |
| N4 | 공백 정규화 후 **원문은 보존** (판정 근거로 인용해야 한다) |

### ✅ 다만 D-109 의 「자연어인지 코드인지」는 답이 나왔다
