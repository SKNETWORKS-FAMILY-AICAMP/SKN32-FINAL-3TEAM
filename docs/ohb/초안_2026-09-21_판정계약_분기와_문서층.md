## §0 한 줄

**판정은 「표현 + 제품 지위」의 함수이고(D-156), 지위를 모르면 분기해서 나란히 보여 준다(D-61 · D-229).**
그런데 지금 계약에는 **분기 결과를 담을 자리**와 **문서 수준 경고를 담을 자리**가 없다. 둘을 더한다.
요청(`JudgeRequest`)은 **바꾸지 않는다** — 이유는 §3.

## §2 원장이 정한 판정 흐름 — 한 장

```
요청 1건 = 문서 1개 (D-120)                         ← 배치는 요청 N건 = 문서 N개 (D-105 · for-loop)
  │
split ── 문장들                                     (지금 스텁 — 입력 전체가 한 문장)
  │
classify ── 품목(식품·건기식·화장품) · 자격(인정번호)   D-82 사용자에게 안 묻는다 · D-83 층 1 = 「조건」
  │          ├ 정해짐   → 그 축 하나
  │          └ 미확정   → 분기 N개 — **언제나** (D-229 ⑥)  ⛔ max 로 접지 않는다 (D-227)
  │                        건기식 분기 안에서 인정번호가 없으면 「인정 사항이면 / 아니면」 둘 (D-61)
  │                        기능성표시식품은 축이 아니라 분기 (D-229 ③)
  │
(분기마다) retrieve ── 그 품목의 코퍼스로 근거 조문      ⬜ 지금 `%s = ANY(c.category)` 가 한 값만 받는다

  │   ├ 사전 정확매칭  → **위험도 하한만**(D-123 · 구현계획 ④) — 판정을 직접 내지 않는다(D-156 ②)
  │   ├ 인코더        → 유형 · 스팬 · 확신. 스팬이 있을 때만 하한 위로 올린다(D-131)
  │   ├ 조문 단서     → 1호 가목 단서 2) · 3호 본문 — 유형 단위 코드 · 인정번호로만 열린다(D-229 ④)

(분기마다) assess_risk ── max(하한, 인코더) · 업종만 max (D-227)
  │
문서 수준 (층 3) ── 공존 규칙 R-D1 = [질병명] ∧ [섭취·사용] ∧ [호전]      D-83 ③ · D-120 · D-30 주장 원장
  │                  → 「위법 판정」이 아니라 **문서 수준 경고 + hold(rd1)** · 인코더는 문장 단위로만 (D-131)
  │
종합 ── 분기 사이 등급이 갈리는 유형이 하나라도 있으면 hold(cat_unknown) · 안 갈리면 confirmed 가능 (D-229 ⑥)
  │
outcome (D-125) ── pass · certificate(A·C) · search_failed(B) · hold
```

## §3 요청은 바꾸지 않는다 — 제가 앞서 틀린 것

앞선 답에서 「`JudgeRequest` 에 문서 경계 선언이 없다」고 했는데 **필요 없다.** D-120 표에서
단순 문구와 긴 글은 **둘 다 문서 1개**이고, 서로 다른 문구 여러 개만 **문서 N개**다 — 「추가 버튼이 곧 문서 경계」.
`POST /judge` 는 요청 하나가 문서 하나이므로 **여러 문장이면 층 3 을 건다**(모르면 긴 글 — D-120 개정분 ①의 안전한 기본값과 같다).
문서 N개는 배치(D-105)가 요청을 N번 보내는 것이다. 요청에 모드 칸을 두면 **같은 뜻을 두 곳에서 말하게** 된다.

## §4 계약에 더할 것 — 제안

### ① 문장 판정에 분기 결과

```python
class Premise(BaseModel):
    """분기의 전제 — 이 결과가 「무엇을 가정했을 때」인가 (D-61 · D-229)."""
    category: Category                      # 식품 · 건기식 · 화장품
    recognized: bool | None = None          # 건기식 분기에서만 — 인정 사항인가. 그 밖은 None

class Branch(BaseModel):
    premise: Premise
    queried: bool                           # 이 분기의 근거 조문을 조회했는가 — False 면 화면이 「근거 조문 미조회」(D-229 ⑤ · D-188)
    violations: list[Violation] = []
    infeasibility: Infeasibility | None = None
    risk: RiskAssessment = RiskAssessment()
    evidence: list[EvidenceArticle] = []

class SentenceJudgment(BaseModel):
    ...                                     # 기존 칸은 그대로 — 품목이 정해졌으면 지금처럼 이 칸들이 답이다
    branches: list[Branch] = []             # 🆕 품목 미확정이면 채운다
```

검증 규칙(계약이 거부한다):

| 규칙 | 근거 |
|---|---|
| `hold_reason == cat_unknown` 이면 `branches` 가 2개 이상 | D-229 ⑥ — 보류는 **등급이 갈릴 때만** · 갈렸다는 증거가 분기다 |
| 분기 전제가 겹치지 않는다(같은 `category`·`recognized` 두 번 금지) | D-99 |
| `recognized` 는 `category == 건기식` 일 때만 값이 있다 | D-61 — 자격 축은 건기식에서만 판정을 가른다 |
| 분기마다 `confirmed ∧ violations` 규칙(근거 필수)을 **분기 단위로** 똑같이 건다 | D-224 |

★ 문장 최상위 칸(`violations`·`risk`…)과 분기의 관계 — **품목이 정해졌으면 분기 없이 최상위가 답**,
미확정이면 **최상위는 분기들의 종합**(등급이 갈리면 `hold(cat_unknown)`)이다. 두 벌이 아니라 **요약과 내역**이다.

### ② 응답에 품목의 출처

```python
class CategorySource(enum.StrEnum):
    classified = "classified"   # 우리가 판별 (D-82)
    selected   = "selected"     # 재검수에서 사업자가 고름 — 「확인되지 않았습니다」(D-229 ④⑤)
    unknown    = "unknown"      # 미확정 → 분기

class JudgeResponse(BaseModel):
    ...
    category: Category | None = None
    category_source: CategorySource = CategorySource.unknown
```

분기표 고지(D-229 ⑤ · REQ-N-028)의 문구는 **화면·내보내기가 이 두 칸과 `branches` 로 만든다** — 응답에 고지 문장을 따로 싣지 않는다(두 벌 · D-99).

### ③ 응답에 문서 수준 경고

```python
class DocumentFlag(BaseModel):
    """층 3 — 문장 여럿이 모여서 걸린 것. **위법 판정이 아니라 경고**다 (D-83 ③)."""
    rule: str                    # "R-D1" — 규칙표의 번호 (D-83 개정분 ①)
    sent_ids: list[str]          # 조합된 문장들 — 근거는 「조합된 문장 집합」(D-131)
    violation: Violation | None  # 규칙이 가리키는 유형 (R-D1 → 질병_예방치료_표방)

class JudgeResponse(BaseModel):
    ...
    document_flags: list[DocumentFlag] = []
```

검증 — `document_flags` 가 있으면 그 `sent_ids` 의 문장 중 하나 이상이 `hold(rd1)` (D-127 사유코드 · D-83 「Abstention + 전문가 검토」).
⛔ 문장 판정의 등급을 이 경고로 올리지 않는다 — 층을 분리해 표시한다(D-83 ③).

## §7 깔고 간 가정

1. 「요청 1건 = 문서 1개」 — D-120 표와 D-105(배치 = for-loop)에서 읽었다. 배치 API 가 요청 하나에 여러 문서를 싣게 설계되면 §3 이 틀린다.
2. `Branch` 의 칸을 `SentenceJudgment` 에서 골랐다 — `verdict`·`hold_reason` 은 분기에 두지 않았다(종합은 문장 최상위가 한다). 분기마다 보류가 필요하다는 근거는 원장에서 못 찾았다.
3. R-D1 이외의 공존 규칙은 **없다**고 봤다 — D-83 이 「R-D1 하나로 시작」이라 적었다. 규칙이 늘어도 `rule` 문자열 칸이라 계약은 그대로다.
