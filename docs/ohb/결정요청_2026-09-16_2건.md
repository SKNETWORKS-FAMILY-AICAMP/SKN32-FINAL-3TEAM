## 1 · `db-up` 이 `CREATE EXTENSION` 실패를 「준비 완료」로 보고한다

### ① 무엇이 일어났나

`db-reset --yes --data` 의 ② 단계 출력 (사용자가 돌려 준 것):

```
$ docker compose exec -T postgres psql -U copylane -d copylane -c CREATE EXTENSION IF NOT EXISTS vector;
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: No such file or directory
        Is the server running locally and accepting connections on that socket?
  DB 준비 완료  127.0.0.1:5432  (pgvector 확장 포함)
```

컨테이너를 방금 띄워 아직 소켓이 안 열렸는데 psql 을 쳤다. **실패했는데 성공으로 보고했다.**

### ② 용어

- **`CREATE EXTENSION vector`** · PostgreSQL 에 pgvector 기능을 켜는 명령. 이게 없으면
  벡터 열을 만들 수 없고 `0001` 이 터진다.
- **소켓** · 같은 기계 안에서 프로그램끼리 직접 말하는 통로. 서버가 아직 준비 안 됐으면 그 통로가
  파일로 존재하지 않는다 — 위 에러가 그 말이다.
- **healthcheck** · 컨테이너가 「나 이제 받을 준비 됐다」고 알리는 장치. `docker ps` 의
  `(healthy)` 가 그것이다.

### ③ 왜 문제인가

이번에는 무해했다 — `embed` 가 2,400행을 넣었으니 `vector` 확장은 있었다(동결본 스키마가
만들었을 것으로 보지만 **확인하지 않았다**).

그러나 확장이 없었다면 `0001` 에서 터졌을 것이고, 그 사람은 **「DB 준비 완료」라고 적힌 화면을
보고** 원인을 엉뚱한 데서 찾는다.

09-13·14 에 두 팀원이 하루씩 잃은 것이 바로 이 모양이었다 — 증상이 원인과 다른 자리에서 나온다.
D-162 「에러를 삼키는 수정으로 증상만 없애지 않는다」가 걸리는 자리다.

### ④ 대안

**(가) healthcheck 대기를 넣는다** — psql 전에 컨테이너가 `healthy` 가 될 때까지 기다린다.

- 얻는 것: 원인 자체가 없어진다. 사용자가 아무것도 안 배워도 된다.
- 떠안는 것: 대기 상한이라는 `[임의]` 값이 하나 늘고, 그 값이 판정 경로에 앉는다.
  느린 기기에서 상한을 넘으면 같은 증상이 다시 난다.

**(나) psql 실패를 그대로 올리고 멈춘다 (fail-closed)**

- 얻는 것: 거짓 성공이 사라진다. D-72 의 어법과 같다.
- 떠안는 것: 「기다리면 됐을 일」에 멈춘다. `db-reset` 을 두 번 돌려야 하는 경우가 생긴다.
  `db-reset` 은 볼륨을 이미 지운 뒤라 두 번째 실행이 처음부터 다시 돈다.

**(다) 둘 다 — 대기하고, 대기 뒤에도 실패하면 멈춘다**

- 얻는 것: 정상 경로는 조용하고 비정상 경로는 안 삼킨다.
- 떠안는 것: (가)의 `[임의]` 값은 그대로 남는다. 코드가 조금 늘어난다.

### ⑤ 권고 — (다)

`[임의]` 값이 남는 것은 (가)와 같지만, 그 값을 넘겼을 때의 동작이 「거짓 성공」에서 「멈춤」으로
바뀐다. **값이 틀려도 사람을 오도하지 않는다**는 점이 (가)와의 차이다.

`[임의]` 값이 판정 경로에 있으므로 보고에 올린다 — 대기 상한은 실측 근거 없이 정하게 된다.

### 내가 틀릴 수 있는 지점

대기 상한을 넉넉히 잡으면 (가)만으로도 실패가 사실상 안 난다. 그렇다면 (다)의 추가 코드는 값을
못 한다. **실패 빈도를 재 본 적이 없다** — 이 날 한 번 봤을 뿐이다.

## 2 · `doctor` 의 낡음 판정이 판(edition)을 못 본다

### ① 무엇이 일어났나

`doctor --data --hash` 가 「팀 최신판이 아닌 파일 56개」를 냈다. 직접 재니:

```
낡은 base 56 | 판 파일로 있음 2 | 정말 없음 54
```

2건은 **같은 바이트가 같은 디스크에 다른 이름으로 있었다.**

```
page_0007.json  원장 최신 sha  a46c215c1bc009bb
09-14 행:  path page_0007__c20260914.json
           sha  a46c215c1bc009bb…   bytes 50023   supersedes page_0007.json
```

`git grep supersedes` 결과 — `scripts/load_db.py` 에만 있고 **`scripts/doctor.py` 에는 없다.**
그래서 doctor 는 같은 path 안에서만 비교하고, 승계 파일이 로컬에 있는지 보지 않는다.

### ② 용어

- **판(edition)** · 같은 이름의 원천 파일이 다른 바이트로 다시 왔을 때, 덮어쓰지 않고
  `__c<수집일>` 을 붙여 별도 파일로 앉히는 것 (`store.EDITION_MARK` · D-143).
- **`supersedes`** · 원장 행이 「이 판이 어느 파일을 대신한다」를 가리키는 칸.
- **base path** · 접미사 없는 원래 이름(`page_0007.json`).
- **offset 페이징 밀림** · 목록 API 에서 레코드 하나가 끼어들면 그 뒤 모든 페이지의 바이트가
  달라지는 현상. doctor 가 `mfds_sanctions`·`mfds_press`·`mfds_hf_ingredient_board` 를
  그렇게 표시했다 (D-149). 이 원천에서는 파일 해시로 판을 비교하는 것이 의미가 약하다.

### ③ 왜 문제인가

두 가지가 겹친다.

**하나 — 없는 것과 이름이 다른 것이 같은 🟡 로 나온다.** 56 중 2 와 54 가 성격이 완전히 다른데
구분되지 않는다. 이 날 클로드가 「집이 정본」/「다른 클론에서 56개 옮겨야」로 **네 번 말을 바꾼**
원인이 이것이다.

**둘 — doctor 가 권하는 해결이 작동하지 않는다.** 출력에 「이 기기에서 다시 받는다:
`launcher.py collect <소스id> --use U1`」이 찍히는데, 판 모드 원천에서는 다시 받아도
`__c<오늘>` 이 하나 늘고 base 는 낡은 채 남는다. **경고가 영구히 뜬다.**

근본 원인은 원장에 **두 체계가 섞여 있다**는 것이다 —

```
2026-09-02  같은 path 에 덮어씀
2026-09-06  같은 path
2026-09-08  같은 path        ← 여기까지 덮어쓰기 체계
2026-09-10  __c20260910      ← 여기부터 판 체계 + supersedes
2026-09-14  __c20260914
```

### ④ 대안

**(가) `doctor` 가 `supersedes` 를 따라간다** — 낡은 base 의 최신 sha 를 같은 폴더의 판 파일에서
찾고, 있으면 ⬜「판으로 있다」, 없으면 🟡「정말 없다」로 갈라 낸다.

- 얻는 것: 56 이 2 와 54 로 갈린다. 판정이 깨끗해진다. 다음 사람이 같은 데서 안 헤맨다.
- 떠안는 것: `supersedes` 로직이 `load_db.py` 와 `doctor.py` 두 곳에 생긴다 (D-99).
  공통화하려면 `store.py` 로 올려야 하는데, **`store.py` 위치를 아직 확인하지 않았다**
  (`scripts`·`preprocess`·`app` 밖에 있다).

**(나) `doctor` 를 그대로 두고 문서에 경고만 적는다**

- 얻는 것: 코드 변경 0. 발표 전에 건드릴 것이 없다.
- 떠안는 것: 다음 사람이 같은 데서 헤맨다. 실측: 이 날 반나절을 썼다.

**(다) 옛 체계를 정리한다** — 09-08 이전의 같은-path 행들을 판 경로로 옮겨 적어 체계를 하나로 만든다.

- 얻는 것: 원인이 없어진다. 이후 모든 축이 한 규칙으로 돈다.
- 떠안는 것: **원장을 손으로 고치는 일이다.** 20,123행 중 일부를 다시 쓰는 것이고, 원장은
  커밋되는 팀 정본이다. 되돌리기가 어렵고 2인 확인이 걸릴 수 있다. 그리고 「무엇이 바뀌었는지는
  사람이 원장에 적는다」(D-54)와 정면으로 부딪힌다.

### ⑤ 권고 — (가), 다만 발표 뒤에

판정을 깨끗하게 만드는 값이 가장 크고, `supersedes` 로직을 `store.py` 로 올리면 D-99 도 같이
지킨다. 지금 당장은 아니다 — 발표를 막는 것이 아니고, `store.py` 위치조차 아직 확인하지 않았다.

(다)는 원인을 없애는 유일한 안이지만 원장을 손으로 고치는 대가가 지금 감당할 것보다 크다.
(나)는 같은 사고가 다음 사람에게 되풀이되는 것을 그냥 받아들이는 것이라 권하지 않는다.

### 내가 틀릴 수 있는 지점

판 체계가 앞으로도 계속 갈릴 원천이 `mfds_*` 몇 개뿐이라면, (가)의 코드를 들이는 것보다
그 원천을 수집 목록에서 정리하는 쪽이 쌀 수 있다. **원천별로 판이 몇 개씩 쌓이는지 세 보지 않았다.**

### 이것과 별개로 남은 실측 한 건

`mfds_sanctions` 54 의 09-08 바이트가 다른 클론에 있는지 유실인지 갈리지 않았다.
다른 클론에서 같은 한 줄을 돌려야 한다 —

```
uv run python -c "import json,hashlib,pathlib;H=lambda q: hashlib.sha256(q.read_bytes()).hexdigest();rows=[json.loads(l) for l in pathlib.Path('data/manifest.jsonl').open(encoding='utf-8') if l.strip()];best={};[best.__setitem__(r['path'],r) for r in sorted(rows,key=lambda r:r['fetched_at'])];bad=[r for p,r in best.items() if pathlib.Path(p).exists() and H(pathlib.Path(p))!=r['sha256']];sib=lambda r:[q for q in pathlib.Path(r['path']).parent.iterdir() if q.name.startswith(pathlib.Path(r['path']).stem)];ok=[r for r in bad if any(H(q)==r['sha256'] for q in sib(r))];miss=[r['path'] for r in bad if r not in ok];print('낡은 base',len(bad),'| 판 파일로 있음',len(ok),'| 정말 없음',len(miss));print(miss[:5])"
```

⚠️ 그 클론은 `git pull` 로 `c40615f` 를 먼저 받아야 한다 — 원장 61행이 없으면 다른 수가 나온다.
