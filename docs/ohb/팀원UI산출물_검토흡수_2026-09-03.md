## 1. 그대로 흡수한 것 — 설계에 값을 더한 넷

### ① 병기 문구 크기 하한 `max(본문×70%, 13px) = 13px` ★

법정 기준(본문 70%)과 KRDS 접근성 하한(13px) 중 **큰 쪽**을 취해 에디터 슬라이더가 그 밑으로 못 내려간다.

🚨 **이것은 새 축이다.** 전처리 사양의 회피 표기는 **텍스트 축**(`특 · 효 · 능` 같은 구분자 삽입)인데, 이건 **시각적 회피 표기** — *"고지를 안 보이게 작게 넣는"* 우회다. **텍스트로는 잡히지 않고 렌더 결과로만 잡힌다.**

> 발표에서 쓸 수 있다 — *"우리는 금지 표현만 막는 게 아니라, 고지를 숨기는 방법 자체를 구조로 막습니다."*

### ② 판정 게이트 — 미판정 텍스트는 아무 데도 못 나간다 ★

새로 입력·수정한 문구는 판정을 통과해야 생성·다운로드·공유가 열리고, **대기가 하나라도 남으면 전부 잠긴다.**

기획서 3-5 **안전 방향 단조성**의 UI 측 집행이다. 불변식으로 승격할 값어치가 있다 —

> **생성물은 판정을 통과한 문장으로만 조립된다.**

이 한 줄이면 「공유 편집 권한자가 문구를 고치면 재판정이 필요한가」(팀 확인 사항 6번)도 자동으로 답이 나온다. **새 승인 절차가 필요 없다.**

### ③ 협찬 고지·필수 병기 문구를 **코드가 슬롯에 넣는다**

생성 모델이 쓰지 않는다. 기획서 3-4 제어층 원칙과 정확히 같은 방향이고, **모델이 빠뜨릴 수 있는 것을 구조에서 뺐다.**

### ④ 초안 에디터 = D-103 의 실물

상세페이지 섹션 9종 · 블로그 구조 · **성분·함량 = 사실 원장 주입 · 편집 잠금**.
기획서 2-6절 *"승인된 문구가 문서로 쌓이고 템플릿이 그 문서를 조립한다"* 가 화면으로 나왔다. `app/models.py` 의 `work_doc` · `copy_sentence` 와 대응한다.

## 2. 🚨 반드시 정해야 하는 충돌 셋

### ① 위험도 표기가 **세 곳에서 다르다**

| 출처 | 표기 |
|---|---|
| 기획서 6-3 · 4층 | **위험도 4단계 순서형** — 형사 리스크 / 과징금 / 업무정지 / 주의 |
| 사용자 UI | **배지 5종** — 높음 / 주의 / 없음 / **판정 보류** / **근거 불일치** |
| 관리자 대시보드 | **분포 3종** — 높음 / 주의 / 낮음 |

🚨 **「위험도」와 「판정 상태」는 다른 축인데 배지가 둘을 섞었다.** 판정 보류(Abstention)와 근거 불일치(인용 검증 실패)는 위험도가 아니라 **상태**다. 그리고 위험도는 순서형이라 **MAE·QWK로 재는데**, 상태를 섞으면 지표가 성립하지 않는다.

**제안** — 축을 가른다. **위험도 4단계**(순서형 · 모델이 예측) × **판정 상태 3종**(확정 / 보류 / 근거 불일치 · 그래프가 결정). 확정은 사실원장에 단일 출처로 둔다.

### ② `G0~G3` 기호가 **두 의미로 쓰인다**

우리 `G0~G3` = **데이터 거버넌스 등급**(G3 원문 자유 / G2 사실만 / G1 배제 / **G0 미표기·미확인 → 전 용도 deny**).
관리자 「판정 근거 관리」의 `G0~G3` = **근거 문서 등급**. 팀원 05 시트도 *"근거 G0~G3와 공통 등급 옵션 불일치"* 를 이미 적어 뒀다.

🚨 화면명 **`CL-A-059 판정 근거 상세 · G0 · 검증 완료`** 는 **그 자체로 모순이다.** G0 는 정의상 **미확인**이라 검증 완료일 수 없다.

**제안** — 판정 근거도 결국 레지스트리 소스이므로 **같은 축으로 통일**하고, 화면의 상태 라벨은 `검증 완료`가 아니라 **등급 승격 이력**으로 표시한다.

### ③ 관리자가 **판정 규칙을 UI에서 직접 편집한다**

`CL-A-096 기준관리` · `N27~N30`(규칙 추가 · 허용 표현 추가 · 금지 표현 추가).

🚨 **판정 근거의 단일 출처는 판정매트릭스·레지스트리이고, 승격은 2인 확인 대상이다.** UI 자유 편집은 그 게이트를 통째로 우회한다. 게이트 19번(판정 근거 존재)과 하드 제약 ⑤(`reviewed_by` 는 사람이 채운다)도 함께 무력화된다.

**제안** — 세 가지를 전제로만 연다. **감사 로그**(누가·언제·무엇을) · **원장 정합 검사**(저장 시 게이트 재실행) · **2인 확인 연계**(단독 저장 불가).

## 3. 범위 — 갈랐지 깎지 않았다

| 구분 | 화면 | 근거 |
|---|:-:|---|
| **핵심** | **31** | 기획서 8-2 MVP 범위에 대응. 이것이 없으면 end-to-end 한 바퀴가 성립하지 않는다 |
| **부가** | **27** | 제품에는 필요하나 Phase 게이트의 전제가 아니다. 7W 동결 전 여유가 있으면 붙인다 |
| **범위 밖** | **60** | 기획서 2-4 범위 · 8-2 어디에도 근거가 없다 |

### 범위 밖으로 뺀 큰 덩어리 둘

**① 매칭 7화면 + 포트폴리오 2화면** — 광고회사 ↔ 인플루언서 매칭. **기획서에 없는 새 제품 축이다.** 제품 비전으로는 살아 있어도 10주 구현 범위에는 들어갈 수 없다.

**② 관리자 백오피스 대부분** — 매출·MRR·ARPU·미수금 · 기업 계약/좌석/플랜/해지 · SLA · 약관 버전 · 이벤트 배너 · 커뮤니티 모더레이션.
🚨 **과금 정책 자체가 기획서 7-6절에서 「W2 실측 후 확정」 상태다.** 확정되지 않은 정책의 운영 화면을 먼저 지으면 **두 번 짓는다.**

> 기획서 8-3 이 이미 못박았다 — *"v2 최대 리스크는 기술이 아니라 범위다. 다 했는데 깊은 게 하나도 없다가 파이널 프로젝트 최악의 평가다."*

### 관리자에서 **핵심으로 남긴 것**

판정 근거 관리 · 기준관리(판정 규칙) · 이의제기 심사 · 품질 통계 · 대시보드 — **거버넌스의 운영 화면들**이다.
D-76 이 관리자 화면을 분리한 이유가 이것이지, 매출 대시보드가 아니다.

## 4. 요구사항 정의서에서 **덜 들어간 것** — v3.0 에서 채웠다

팀원 v2.2 는 **기능 요구사항만** 있었다. **비기능이 한 건도 없었다.** 26건을 신설했다 —

| 대분류 | 건수 | 대표 |
|---|:-:|---|
| 성능 | 3 | 응답시간 예산 · **판정 원가 : 생성 원가**(과금 경계의 근거) |
| 품질 | 3 | Phase 게이트 · **표본 30건 미만은 「측정 불가」** · 순서형은 MAE·QWK |
| 안전 | 8 | Abstention · 단조성 · 근거 제시 의무 · **13px 하한** · 고정 슬롯 · 원장 잠금 · **판정 게이트** |
| 거버넌스 | 4 | 등급×용도 집행 · raw 소비 금지 · **2인 확인** · **규칙 변경 감사 로그**(신규) |
| 데이터·보안 | 4 | 캐스케이드 삭제 · 비밀 스캔 · 노출면 · 개인정보 |
| 접근성·운영 | 4 | KRDS 최소 크기 · 대체 텍스트 · 환경 동일성 · PR 병합 |

🚨 **비기능이 없으면 7W 「서비스 테스트 계획·결과 보고서」에 잴 것이 없다.** 기능 테스트만 남는다.

**기존 6개 시트는 한 칸도 고치지 않았다.** 값·ID·출처·팀원 수정 사항 그대로 두고 3개 시트를 덧붙였다.
