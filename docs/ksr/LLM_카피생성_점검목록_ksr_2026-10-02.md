## 3. 한계점 — 설계가 풀지 못하는 것

1. **「통과」는 「위반을 못 찾았다」다.** 계약상 통과 = 확정 ∧ R0 = 확정 ∧ 위반 없음. 엔진이 아는 표현만 잡으므로 적법이 확인된 것이 아니다.
2. **화장품은 방어선이 둘뿐이다.** 판정엔진이 비어 있어 프롬프트와 코드 필터만 실제로 작동한다. 통과가 쉽게 나오는 만큼 의미가 약하다.
3. **코드 필터는 표면 형태만 본다.** 숫자·목록에 안 걸리는 「말로 풀어 쓴 새 주장」(예: 오래도록 촉촉)은 지나간다.
4. **금지어를 따로 두면 기준이 두 벌이 된다.** 화장품 금지어를 지침에서 직접 가져오는 것은 임시다 — 지침이 사전에 편입되면 사전을 읽는 쪽으로 돌려야 한다.
5. **식품·건기식도 같은 성질이다.** 사전에 없는 새 표현은 지나간다. 화장품만큼 비어 있지 않을 뿐이고, 정도는 아직 재지 않았다.
6. **통과율을 모른다.** 20개 중 몇 개가 통과하는지 실측이 없어 「3회 · 20개」가 적당한지 알 수 없다.
7. **끝까지 돌려 본 적이 없다.** 판정엔진 배선 전이라 전체 흐름은 아직 종이 위 설계다.

## 4. 정해야 하는 사항

### 4-1. 팀장님과

| # | 질문 | 메모 |
|:-:|---|---|
| 1 | **「더 탐색」 횟수 상한** | ⬜ 미정 — 상의해서 정한다 |
| 2 | 「더 탐색」 한 번을 DB 에 어떻게 적나 | 자동 3회는 `CHECK attempt BETWEEN 0 AND 2` 안에 든다. 버튼 뒤 라운드가 attempt 3 이상이면 저장이 거부된다 → 버튼 한 번을 새 실행(attempt 0부터)으로 적는 안 |
| 3 | 판정엔진 호출 방식 | 문장 모드 배선(W9)을 기다릴지, 그 전에 검수 API 를 문장 단위로 부를지 |
| 4 | 판정엔진이 새 문장에 무엇을 돌려주나 | 사전에 안 걸리는 문장이 「확정 ∧ R0」인지 「근거없음」인지 — 통과율이 완전히 달라진다. 무해한 새 문장 몇 개로 실측 |
| 5 | 화장품 지침의 사전 편입 | 요청 초안을 아직 안 썼다 (빈 낱말 19개 목록은 있음) |
| 6 | 외부 API 전송 고지 | 이용자 제품 정보가 GPT 로 나간다 → 고지·약관 |
| 7 | 규칙 조립 자리에 GPT 생성을 넣는 것 | 팀 설계에서 `assemble` 은 규칙 조립이고 sLLM 은 다듬기로만 붙는다고 적혀 있다 — 새로 쓰는 경로를 어디에 둘지 |

### 4-2. 내가

| # | 질문 | 메모 |
|:-:|---|---|
| 1 | GPT 모델 | 2~3개로 같은 시험 입력을 돌려 보고 고른다 (2-5 가 먼저) |
| 2 | 통과가 3개를 넘을 때 고르는 법 | 각도 우선 / 문자열 거리 / 전부 보여 주고 사람이 선택 |
| 3 | 화면 대기 표시 | 최악 3라운드 — 진행 상황을 보여 줄지 |
| 4 | 분기별 입력 칸 확정 | 기획서 §3 의 칸은 아직 「안」이다 |
| 5 | 화장품 결과 고지 문구 | 「화장품법 기준 검수는 제한적」을 어떻게 적을지 |

### 4-3. 이미 정한 것 (다시 묻지 않는다)

1. 최종 출력 3개 · 1회 생성 20개 · 자동 상한 3회(최대 60 후보)
2. 끝은 탐색 실패 + 「n개 찾았습니다」 + [더 탐색하기] [이대로 쓰기] [입력 고치기]
3. 다시 만들 때 탈락 사유 유형·건수만 넘긴다 (탈락 문구 원문은 안 넘긴다)
4. 건기식 · 인증 아니오 → 안내 후 식품 분기로 진행
5. 실패 시 찾은 문구(0~2개)는 보여 준다
6. 판정엔진은 팀장님 판정 코어를 그대로 쓴다
