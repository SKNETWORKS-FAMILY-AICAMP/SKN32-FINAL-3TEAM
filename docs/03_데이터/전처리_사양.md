## 1. [P2] 문자 수준 정규화 층 — D-84 ①

### 1-1. 왜 층이 필요한가

Aho-Corasick 은 **정확 문자열 매칭**이다. `치료` 는 잡아도 아래는 못 잡는다.

```
치 료   ·   치·료   ·   치+료   ·   ㅊl료   ·   治療   ·   ｃｕｒｅ
```

🚨 **온라인 광고에서 필터 회피 표기는 일상적 관행이다.** D-82 에서 경쟁 도구의 사전 매칭 한계를 지적했는데, **우리 룰 층도 같은 기술이다.** 정규화가 없으면 같은 방식으로 뚫리고, 그러면 *"선행 도구와 무엇이 다른가"* 에 답할 수 없다.

### 1-2. 🚨 비파괴가 핵심 — 파괴하면 둘이 깨진다

```
① 원문 오프셋이 깨진다   ->  하이라이트 UI · 주장 스팬 BIO 라벨이 전부 어긋난다
② 회피 표기 자체가 신호다 ->  정규화로 지워버리면 그 신호를 잃는다
```

②가 덜 알려진 쪽이다. **회피 표기가 있다는 것은 작성자가 위법성을 인지하고 있었다는 뜻**이다. 지우면 그 정보가 사라진다.

### 1-3. 계약 — `NormalizedText`

```python
@dataclass(frozen=True)
class NormalizedText:
    raw: str                  # 원문. 표시·오프셋의 기준이다
    norm: str                 # 정규화문. 매칭의 기준이다
    offset_map: list[int]     # norm[i] -> raw 의 시작 오프셋 (len == len(norm))
    evasion_flags: list[str]  # 적용된 정규화 규칙 ID — ["JAMO_SPLIT", "SEP_INSERT"]
```

> 🔄 **실물(`preprocess/normalize.py` · 10-06)** — 필드가 하나 더 있다: **`applied_rules: list[str]`**(실제로 발동한 규칙 전부 · 진단용). `evasion_flags` 는 **회피 신호로 읽어도 되는 규칙만** 담도록 뜻을 좁혔다 — N5(반복) · N6(공백)은 `applied_rules` 에만 들어간다(「대박!!!!!」은 강조이고 공백 정리는 거의 모든 문서에서 일어난다). 코드 머리말이 「사양을 고친 것 · 팀장 확인 대상」이라 적어 두었고, 확인 기록은 찾지 못했다 — ⬜ 판정 대기.
> 🚨 **이 계약을 읽는 쪽이 아직 없다**(10-06) — `NormalizedText` 를 쓰는 곳은 `tests/test_normalize.py` 뿐이다. 판정 그래프 · 사전 빌더 · 판정기 B 의 매칭은 `app/dictmatch.py` 의 `norm()`(NFKC + **공백 전부 제거** · 부분문자열 · 좌표는 `norm_with_map`)을 쓴다.

🚨 **`offset_map` 은 선택 사항이 아니다.** 보안 점검 P2-9 가 스팬을 `(offset, length)` 구조로 넘기라고 요구하고, 주장 스팬 BIO 라벨(D-30)과 하이라이트 UI 가 전부 이 좌표 위에 선다. **매칭은 `norm` 에서 하고, 결과는 `offset_map` 으로 `raw` 좌표로 되돌려 보고한다.**

### 1-4. 규칙표

| # | 플래그 | 규칙 | 예 | 구현 (10-06 · `preprocess/normalize.py`) |
|:-:|---|---|---|:-:|

> 🔄 **N3 · N4 · N7 은 설계 · 미구현(10-06)이다.** 셋 다 「사전 어휘의 문자 사이에서만」 적용해야 하는 규칙인데(아래 ⚠️ · 7장 미해결 1 · 2) 그 어휘 목록이 정해지지 않아 비워 두었다(`normalize.py` 머리말 — 하한을 전량인 척 넣지 않는다). 사전 항목 · 자격 결정 자체가 보류다(D-313).
> 따라서 **지금 정규화 층이 푸는 회피 표기는 전각 · 유사 문자(N1)와 zero-width(N2)뿐이다.** 구분자 삽입 · 자모 분리 · 한자는 풀지 못한다.

⚠️ **N4 는 과잉 적용 위험이 있다.** `비타민 C` 의 공백까지 지우면 정상 표현이 깨진다. **N4 는 사전 어휘의 문자 사이에서만** 적용한다 — 후보 어휘를 자모 단위로 펼쳐 정규식을 만들고(`치[^가-힣A-Za-z0-9]{0,2}료`), 매칭된 구간에만 적용한다. 전역 치환이 아니다.

### 1-5. `evasion_flags` 는 부산물이 아니라 피처다

> 🔄 **설계 · 미구현(10-06)** — `evasion_flags` 를 읽는 코드가 없다(위 1-3 덧줄). 위험도 가산에도 화면 문구에도 쓰이지 않는다.

★ 위험도 인코더의 **입력 피처**로 넣고 **가산 근거로 기록**한다. 안전 방향으로만 움직이므로(올리기만 한다) 기획서 3-5절의 단조성 원칙과 정합한다.

> **화면 문구 예시** — *"필터 회피로 보이는 표기(`치·료`)가 있어 위험도를 한 단계 올렸습니다."*
> 이것은 사람이 검증할 수 있는 근거다. 점수만 올리고 이유를 못 대면 D-59 의 판정 축이 흐려진다.

## 2. ★ [P11] 표면 변환 축 — 회피 표기 골든셋

### 2-1. 🚨 이것을 `TRANSFORM_RULES` 의 T11 로 넣으면 안 된다

D-84 는 *"골든셋에 「회피 표기」 축을 추가한다"* 고만 했다. **규칙표에 한 줄 더 넣는 것으로 읽으면 두 가지가 깨진다.**

| 깨지는 것 | 이유 |
|---|---|
| **주입 규약 1번** (1문장당 1규칙만) | 회피 표기는 **위법성을 만들지 않는다.** `치료` 를 `치·료` 로 바꿔도 위법 유형은 그대로 V2 다. 규칙표에 넣으면 한 문장에 T4 + T11 이 동시에 붙어 규약이 깨진다 |
| **유형별 Recall 분리 보고** (D-39 지표 1) | `rule_id` 로 규칙별 검출률을 보는데, 표면 변형이 같은 축에 섞이면 *"V2 를 못 잡은 것"* 과 *"표기를 못 뚫은 것"* 이 한 숫자가 된다. **정확히 구분해야 할 두 실패다** |

★ **의미 변환(위법성 부여)과 표면 변환(탐지 회피)은 직교한다.** 그러므로 **축을 따로 둔다.**

```
  [적법 문구] ──T4(의약품 어휘 삽입)──> [위법 문구: "치료 효과"]
                                              │
                                              ├── surface: none   →  "치료 효과"
                                              ├── surface: S2     →  "치·료 효과"
                                              └── surface: S3     →  "ㅊl료 효과"

  ★ 같은 rule_id(T4) · 같은 위법유형(V2) · 다른 surface_variant
     → 세 건의 Recall 차이가 곧 정규화 층의 성능이다
```

### 2-2. 표면 변환 축 `SURFACE_VARIANTS`

| ID | 변환 | 대응 정규화 규칙 | 실재성 |
|:-:|---|:-:|---|
| `S0` | 없음 (원형) | — | 기준선 |
| `S1` | 전각 · 유사 문자 치환 | N1 | 흔함 |
| `S2` | 구분자 삽입 (`·` `.` `+` 공백) | N4 | **가장 흔함** |
| `S3` | 자모 분리 (`ㅊl료`) | N3 | 흔함 |
| `S4` | zero-width 삽입 | N2 | 자동화 도구 산출물 |
| `S5` | 한자 · 음차 (`治療`) | N7 | 드묾 |

> 🔄 **10-06** — `S2`(N4) · `S3`(N3) · `S5`(N7)에 대응하는 정규화 규칙이 미구현이다(1-4). 이 축으로 잴 수 있는 것은 지금 `S1` · `S4` 뿐이다.

### 2-3. 골든셋 필드 추가

```
golden_sample:
    surface_variant : enum  S0 | S1 | S2 | S3 | S4 | S5     ← 신규
    surface_of      : fk    S0 원형 샘플의 id (S0 이면 null) ← 신규
```

> 🔄 **설계 · 미구현(10-06) — 이 두 칸은 DB 열로만 있다.** `db/schema.sql` `golden_sample` 에 `surface_variant`(기본값 `S0`) · `surface_of` 열과 짝 제약(`ck_surface_pairing`)이 있으나, **골든 파일(`data/derived/golden/golden.jsonl`)에는 이 칸이 없고** 표면 변형본을 만드는 코드도 없다. 적재(`scripts/load_db.py`)는 이 열에 값을 쓰지 않아 DB 의 모든 행이 기본값 `S0` 다. 2-4 의 「정규화 층 이득」은 아직 잰 적이 없다.

**주입 규약에 두 줄을 더한다.** *(설계 · 미구현 — 위와 같다)*

| # | 규약 | 이유 |
|:-:|---|---|
| 9 | **표면 변형은 S0 원형과 짝으로만 만든다** (`surface_of` 필수) | 짝이 없으면 델타를 못 잰다. 이 축의 존재 이유가 델타다 |
| 10 | 🚨 **표면 변형본과 그 S0 원형은 반드시 같은 split 에 넣는다** | 원형이 train, 변형이 test 면 그것은 누수다 — [P12] 출처 분리와 같은 축 |

### 2-4. 측정 — 이 축이 답하는 질문 하나

```
정규화 층 이득 = Recall(surface = S0)  −  Recall(surface ∈ {S1..S5})
```

★ **0 에 가까울수록 정규화 층이 제 몫을 한 것**이다. *(🔄 미측정 — 변형본이 없다 · 2-3)* D-77 L1-3(Span F1)에 축을 하나 더하는 형태이고, **정규화 코드를 끄고 한 번 더 돌리면 「층이 있어서 얼마나 벌었는가」가 그대로 나온다.**

### 2-5. 🚨 실제 회피 표기는 어디서 오는가

**합성만으로는 어떤 표기가 실재하는지 모른다.** 우리가 상상한 패턴만 방어하게 된다.

### 2-6. 🆕 회피는 문자에만 있지 않다 — **시각적 회피 표기** <sub>(2026-09-03 · UI v6.7 흡수 · D-119)</sub>

지금까지 이 장은 **문자 축**만 다뤘다 — `치·료` · `ㅊl료`. 그런데 **가장 흔한 회피는 문자가 아니다.**

```
  필수 병기 문구를 본문의 1/5 크기로 넣는다
  → 텍스트는 정상이다. 정규화로도 잡히지 않는다. 렌더 결과에만 나타난다.
```

🚨 **이 축은 전처리에서 잡을 수 없다.** 문자열이 온전하므로 `sep_norm()` 도 회피 표기 계수도 반응하지 않는다.
**막는 자리는 템플릿 층(진입점 C)이고, 방법은 탐지가 아니라 강제다.**

| | 문자 회피 표기 (2-1~2-5) | **시각적 회피 표기 (신설)** |
|---|---|---|
| 어디에 나타나는가 | 문자열 | **렌더 결과** |
| 우리 대응 | 정규화 + 계수 (탐지) | 🚨 **크기 하한 강제** (구조) |
| 규칙 | `sep_norm()` 나열 구분자 전개 | **`max(본문 × 70%, 13px)`** — 법정 기준 70% 와 KRDS 접근성 하한 13px 중 **큰 쪽** |
| 집행 | 전처리 층 | 템플릿 에디터가 **하한 밑으로 못 내려가게 막는다** |

★ **탐지가 아니라 강제인 이유** — 렌더 결과를 검사하려면 스크린샷을 판정해야 하고, 그것은 **D-104(이미지는 판정하지 않는다)** 에 정면으로 걸린다.
**만들 때 못 만들게 하면 검사할 필요가 없다.** 필수 표기 섹션의 「삭제 불가 · 항상 마지막」도 같은 형태다.

> ★ **발표에서 쓸 수 있다** — *"금지 표현만 막는 것이 아니라, **고지를 숨기는 방법 자체를 구조로 막습니다.**"*

⚠️ **골든셋 축에는 넣지 않는다.** 문자 축(`surface_variant`)과 달리 **텍스트로 표본을 만들 수 없다.** 측정은 산출물 렌더 검증(REQ-N-011)으로 하고, D-40 의 30건 기준 대상이 아니다.

|---|---|---|
| **확실성** | 확실 / 불확실 | **R2 단정 → 조건부** (T1 역방향) |
| **시제** | 과거 / 현재 / 미래 | **R1 실적 → 예상** (T9 역방향) |
| **문장유형** | 사실 / 추론 / 예측 / 대화 | **B 실증형 판정** (D-59) |

★ **발표 지표 2번(재판정 통과율 + 내용 보존율)을 규칙별로 분해해 함께 보고한다** (D-74 · 사실원장).

🚨 **AI Hub 71486 은 `NOREDIST` 다.** 이 축의 라벨러를 학습시키는 것은 되고(U1 allow · U4 allow), **그 데이터를 우리 골든셋에 섞어 공개하는 것은 안 된다.** 아래 5장이 그 경계를 다룬다.

## 5. 🚨 `provenance` · `redistributable` — 수집 시점에만 기록할 수 있다

D-71 의 전파 규칙은 이것이다.

```
데이터셋 공개 = { f | f 에 NOREDIST 가 없음 }
배포 모델 학습 = { f | f.U1 AND f.U4 }        ← 다른 축이다
```

**골든셋에 `redistributable: false` 소스에서 온 문장이 한 줄이라도 섞이면 그 골든셋 전체를 공개 배포할 수 없다.** 그리고 **섞인 뒤에는 어느 줄이 어디서 왔는지 되돌릴 수 없다.**

| 필드 | 위치 | 값 |
|---|---|---|
| `fragment_id` | 모든 문장·청크·학습샘플 | FK 필수 (D-20) · 🔄 DB 의 열이다 — 골든 **파일**에는 이 칸이 없다 |
| `provenance` | 골든셋 · 학습샘플 행 | 유래 소스 키 (`aihub_71486` 등) |
| `redistributable` | 골든셋 · 학습샘플 행 | `fragment → source` 에서 상속. **행 단위로 복사해 둔다** |

⚠️ **왜 상속값을 행에 복사하는가** — 조인으로 매번 계산하면 공개 시점에 소스가 이미 지워졌거나(D-20 캐스케이드) 등급이 바뀐 경우 답이 달라진다. **공개 판정은 그 행이 만들어진 시점의 사실로 한다.**

★ **데이터셋 공개용 뷰는 이미 있다** — `v_publishable_golden` (`redistributable = true` 필터).
