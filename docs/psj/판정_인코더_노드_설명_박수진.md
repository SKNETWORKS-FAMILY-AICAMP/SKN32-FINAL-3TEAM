## 1. 한 줄 요약

문장 하나를 받아 **위반 유형 9칸의 확률**과 **문턱을 넘은 유형 후보**를 낸다. 확정 · 보류 · 위험도는 정하지 않는다 — 그것은 `judge` · `assess_risk` 의 몫이다.

## 2. 그래프에서의 자리

```
core   split → classify → retrieve → match_dict → [encode] → 법별 팬아웃 → merge_laws → judge → …
```

| 항목 | 내용 |
|---|---|
| 노드 | 코어 서브그래프 5번 `encode` (`app/graph.py`) |
| 도는 횟수 | 법별 팬아웃 **앞에서 한 번** — 법별 노드가 따로 부르지 않는다 (D-267 · D-99) |
| 지금 상태 | **빈 노드** — 모듈(`app/encoder.py`)은 있으나 그래프에 배선되지 않았다 |
| 배선 시점 | test 결과는 나왔다(10-06). 어느 인코더를 붙일지 · 판정에서 어떻게 쓸지 팀장 판정 뒤 |

## 3. 입력과 출력

| | 내용 |
|---|---|
| 입력 | 문장 하나 (`split` 이 나눈 문장의 글자) |
| 출력 `scores` | 유형 9칸의 확률 — 칸마다 독립인 sigmoid 값 (다중 라벨 · 한 문장에 여러 유형이 설 수 있다) |
| 출력 `candidates` | `확률 >= 문턱` 인 유형만 — 유형 · 확신(확률) · 적용한 문턱 |
| 진입점 | `app.encoder.predict(text)` → `EncoderPrediction` |

| 칸 | 유형 | 상태 | 문턱 |
|:-:|---|---|---|
| 1 | 질병_예방치료_표방 | 확정 | 0.350 |
| 2 | 건강기능식품_오인 | 확정 | 0.450 |
| 3 | 의약품_오인 | 확정 | 0.450 |
| 4 | 거짓_과장 | 확정 | 0.375 |
| 5 | 소비자_기만 | 확정 | 0.475 |
| 6 | 후기_체험기_기만 | 확정 | 0.325 |
| 7 | 부당_비교광고 | 확정 (D-321 편입) | 0.900 |
| 8 | 비방광고 | 확정 (D-321 편입) | 0.800 |
| 9 | 기능성화장품_오인 | **편입 대기** | `1.01` — 확률이 넘을 수 없어 후보로 나가지 않는다 |

- 문턱은 유형마다 다르다. 값은 `label_scheme.json` 에 실려 모델과 함께 간다 — 코드에 적지 않는다.
- 위 값은 후보 A(3차 재학습 · test 채점판)의 문턱이다 — 검증 묶음(dev)에서 유형별 F1 최대로 골랐다.
- 🔴 부당 비교 · 비방은 문턱이 높아 **이 판에서는 거의 후보로 나가지 않는다**(평가 0/97 · 8/203). dev 의 두 유형 양성이 거의 합성 문구였기 때문이다.

## 5. 모델 파일 구성

앱은 `models/copylane-encoder-kcbert-final/` 을 읽는다. 저장소에는 올리지 않는다(`.gitignore` 의 `models/` · `*.safetensors`) — 학습 노트북이 낸 zip 을 받아 그 자리에 푼다.

| 파일 | 내용 | 로더 필수 |
|---|---|:-:|
| `config.json` | 모델 설정 · `id2label`(9칸의 유형 이름) | ✅ |
| `model.safetensors` | 가중치 (430MB 안팎) | ✅ |
| `tokenizer.json` | 토크나이저 | ✅ |
| `label_scheme.json` | 유형 순서 · 유형별 문턱 · 학습 기록 | ✅ |
| `tokenizer_config.json` 등 | 토크나이저 부속 | |

`label_scheme.json` 의 주요 칸

| 칸 | 내용 |
|---|---|
| `label_list` | 출력 9칸의 유형 이름 — 가중치의 출력 순서와 같다 |
| `label_thresholds` | 유형별 문턱 (9개) |
| `confirmed_labels` · `waiting_labels` | 확정 8종 · 편입 대기 1종 |
| `golden_sha256` · `banned_terms_sha256` | 학습에 쓴 골든셋 · 사전의 지문 |
| `train_by_cond` · `train_role_counts` | 조건별 학습 행 수 · 뺀 행 수 — 「M 제외」로 학습했는지 확인하는 자리 |
| `final_test` · `test_report` | 평가 분할을 채점한 모델인지 · 그 결과 |

## 6. 로더 계약 (`app/encoder.py`)

- 필수 파일 넷이 없으면 멈춘다(`EncoderUnavailable`) — 대체값으로 돌지 않는다.
- `label_list` 의 값은 전부 계약의 위반 유형(`app.contracts.Violation`)이어야 한다.
- `label_list` 와 `label_thresholds` 의 유형이 같아야 하고, `config.json` 의 `id2label` 순서와 같아야 한다. 어긋나면 멈춘다.
- 모델은 프로세스마다 한 번만 메모리에 올린다.
- 9칸 판은 로더를 고치지 않고 읽힌다 — 학습 노트북의 검증에서 저장 결과를 이 로더로 읽어 확인했다(합성 데이터 · 작은 모델).

## 7. 하는 것과 하지 않는 것

| 한다 | 하지 않는다 |

| 문장마다 위반 유형 후보와 확신을 낸다 | 확정 · 보류 · 통과를 정하지 않는다 (`judge`) |
| 유형마다 다른 문턱을 적용한다 | 위험도를 만들지 않는다 (`assess_risk` · 제재 별표) |
| | 조문 근거를 붙이지 않는다 (`retrieve` · 사전) |
| | **근거 구간(스팬)을 내지 않는다** — D-131 의 설계 출력에는 있으나 지금 모델은 문장 단위 유형만 낸다 |
| | 「주장 아님」을 따로 내지 않는다 — 9칸이 모두 조용한 것과 구별되지 않는다 |
| | 유형이 없는 위반(화장품법 제13조① 4호 등)은 내지 못한다 |
| | 품목 · 문서 단위 판단을 하지 않는다 |

### 판정 로직에 붙여 본 결과 (시제품 · test 1회 · 10-06)

규칙 판정은 `app/graph.py` 의 함수를 그대로 부르고 인코더 층만 얹었다. 조문 검색 · 위험도 하한은 없다(DB 없음). 자세한 표는 「판정 로직 × 판정 인코더 결합 — 결과보고서」(`판정로직_인코더결합_결과보고서_박수진_20261006.docx`)가 정본이다.

| 지표 | 무조건부 (규칙만 → + 인코더) | 조건부 (규칙만 → + 인코더) |
|---|---|---|
| 탐지 재현율 (확정 ∪ 보류 유형 후보) | 15.2% → **56.2%** | 17.0% → **56.9%** |
| 확정 재현율 | 0.1% → 0.1% | 2.5% → 1.7% |
| 위반을 통과로 놓침 | 0/1,780 → 0/1,780 | 0/1,570 → 1/1,570 |
| 적법 · 주장 없음(수정문구 D)이 통과 | 0/133 → 2/133 | 0/133 → 8/133 |
| 적법 문장에 위반 확정 | 0/143 → 0/143 | 0/133 → 0/133 |

- 인코더가 하는 일은 확정이 아니라 **보류 문장에 유형 후보를 다는 것**이다. 적법 수정문구도 94.0% 가 보류라, 보류됐다는 것만으로는 위반과 적법이 갈리지 않는다.
- 「규칙만」 줄은 팀장 기준선(탐지 16.1% · 17.0% · 확정 0.1% · 2.5%)과 거의 같다.
- 앱 그래프의 `encode` 노드는 아직 비어 있다 — 위 수치는 시제품의 것이고 배선 뒤 DB 로 다시 잰다.
