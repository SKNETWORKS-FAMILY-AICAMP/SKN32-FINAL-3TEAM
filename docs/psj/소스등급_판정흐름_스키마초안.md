# 소스 등급 판정 흐름 — 스키마 설계 초안

- **작성**: psj (2026-09-16)
- **상태**: 초안 · 팀장 승인 전 (`db/**` 등급1)
- **전제**: `docs/psj/판정근거_등급기준_초안.md` (L1~L4 판단 기준표)와 세트로 읽는다.
- **확정된 요구사항** (2026-09-16 팀 논의):
  - 관리자 계정 5명. 판정 근거 문서 **열람은 전원** 가능 (이미 구현됨 — `/admin/sources`).
  - **등급 변경·판정은 관리자 2인의 확인이 있어야** 확정된다.
  - 판정한 사람과 확인한 사람은 **달라야** 한다 (기존 `ck_source_four_eyes` 그대로 재사용).

## 기존 스키마가 이미 주는 것

`source` 테이블은 이미 2인 확인을 강제하는 컬럼·제약을 갖고 있다:

```sql
grade_decided_by    TEXT NOT NULL,
grade_reviewed_by   TEXT NOT NULL,
grade_decided_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
grade_evidence_url  TEXT,
supersedes          TEXT REFERENCES source(source_id) ON DELETE SET NULL,
CONSTRAINT ck_source_four_eyes CHECK (grade_decided_by <> grade_reviewed_by)
```

🚨 **문제**: 두 컬럼 다 `NOT NULL` 이다. 즉 **1차 판정만 되고 아직 2차 확인 전인 "대기 상태"를 `source` 에 직접 넣을 수 없다.** 확인 전에 저장할 곳이 없으면, 1차 확인자가 제안한 내용이 2차 확인자 눈에 보이기도 전에 등급이 확정돼 버리거나(제약 위반으로 아예 저장이 안 되거나) 별도 자리가 필요하다.

## 제안: `source_grade_proposal` (신규 테이블)

"판정 대기 중"인 제안을 별도로 담는다. `source` 자체는 **승인된 값만** 담는 정본으로 유지한다 (D-99 "명단의 정본은 하나" 원칙과 같은 결).

```sql
CREATE TABLE source_grade_proposal (
    proposal_id      BIGSERIAL PRIMARY KEY,
    source_id        TEXT NOT NULL REFERENCES source(source_id) ON DELETE CASCADE,
    -- 제안하는 새 값 (source 테이블의 판정 대상 컬럼과 1:1)
    proposed_grade   grade_t NOT NULL,
    proposed_by      TEXT NOT NULL,
    proposed_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    evidence_url     TEXT,                 -- 판단 근거 (법령정보센터 링크·고시번호 등)
    note             TEXT,
    -- 확인 결과 (승인 전엔 전부 NULL)
    status           TEXT NOT NULL DEFAULT 'pending',  -- pending / approved / rejected
    reviewed_by      TEXT,
    reviewed_at      TIMESTAMPTZ,
    reject_reason    TEXT,
    CONSTRAINT ck_proposal_four_eyes
        CHECK (reviewed_by IS NULL OR reviewed_by <> proposed_by),
    CONSTRAINT ck_proposal_status
        CHECK (status IN ('pending', 'approved', 'rejected'))
);
```

- **제안(1차 판정)**: `proposed_by`만 채워서 INSERT. `status='pending'`.
- **승인(2차 확인)**: `reviewed_by`·`reviewed_at` 채우고 `status='approved'`로 UPDATE. 같은 트랜잭션에서 `source.grade`·`grade_decided_by`·`grade_reviewed_by`·`grade_decided_at`·`grade_evidence_url` 을 이 제안 값으로 UPDATE — 이때 기존 `ck_source_four_eyes` 가 그대로 다시 검증해준다 (이중 안전장치).
- **반려**: `status='rejected'`, `reject_reason` 채움. `source` 는 안 바뀜.

## "되돌리기" — 기존 `supersedes` 재사용

새 등급을 완전히 새 `source_id`로 만들지 않고, 기존 `source` row를 UPDATE하면 **이전 등급값이 사라져 버려서** 되돌릴 수가 없다. 그래서:

- `source` 를 직접 UPDATE 하지 않고, **승인될 때마다 새 이력 row를 별도로 남긴다.**

## 제안: `source_grade_history` (신규 테이블) — 이력 전용

```sql
CREATE TABLE source_grade_history (
    history_id       BIGSERIAL PRIMARY KEY,
    source_id        TEXT NOT NULL REFERENCES source(source_id) ON DELETE CASCADE,
    grade            grade_t NOT NULL,
    decided_by       TEXT NOT NULL,
    reviewed_by      TEXT NOT NULL,
    decided_at       TIMESTAMPTZ NOT NULL,
    evidence_url     TEXT,
    proposal_id      BIGINT REFERENCES source_grade_proposal(proposal_id),
    superseded_at    TIMESTAMPTZ,           -- NULL = 현재 유효한 등급
    CONSTRAINT ck_history_four_eyes CHECK (decided_by <> reviewed_by)
);
```

- 제안이 승인될 때마다: 이전 이력 row의 `superseded_at`을 채우고, 새 row를 `superseded_at IS NULL`로 추가.
- `source.grade` 는 **`superseded_at IS NULL` 인 이력의 값과 항상 같아야 한다** — `source` 자체는 "지금 유효한 값의 캐시"로만 쓰고, 정본은 이력 테이블.
- **되돌리기** = 이전 이력 row를 다시 "현재"로 만드는 새 이력 row를 추가하는 것 (이력을 삭제하지 않는다 — D-54 "수는 원장에만" 과 같은 정신, 흔적을 지우지 않는다).

## 남은 결정 사항 (팀장 승인 요청에 포함할 것)

1. `source_grade_proposal`, `source_grade_history` 두 테이블 신설 — `db/**` 등급1
2. `source.grade` 를 이력 테이블의 파생값(캐시)으로 둘지, 아니면 이력 테이블만 두고 `source.grade` 를 뷰(VIEW)로 대체할지 — 캐시면 동기화 로직이 필요하고, 뷰면 쿼리가 복잡해진다. **캐시 방식을 제안** (기존 코드가 `source.grade` 를 이미 직접 읽고 있어서 변경 범위가 작다)
3. `dict_entry` 는 이번 스코프에 포함하지 않는다 — 2인 확인 제약이 아예 없어서 별도 논의 필요 (판정근거_등급기준_초안.md 참고)
4. `status` 를 ENUM(`grade_t` 처럼)으로 할지 TEXT + CHECK 로 둘지 — 기존 관행(`dict_entry.dict_kind` 가 TEXT인 것)을 보면 이 저장소는 혼용하는 편. 우선 TEXT + CHECK 로 초안.
