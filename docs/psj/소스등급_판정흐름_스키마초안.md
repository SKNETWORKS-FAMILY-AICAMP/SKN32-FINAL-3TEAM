# 소스 근거 등급(L1~L4) 판정 흐름 — 스키마 설계 초안

- **작성**: psj (2026-09-14, 2026-09-16 전면 재작성)
- **상태**: 초안 · 팀장 승인 전 (`db/**` 등급1)
- **전제**: `docs/psj/판정근거_등급기준_초안.md` (G0~G3 · L1~L4 정의)와 세트로 읽는다.
- **확정된 요구사항** (2026-09-16 팀 논의):
  - 관리자 계정 5명. 판정 근거 문서 **열람은 전원** 가능 (이미 구현됨 — `/admin/sources`).
  - 화면에서 **관리(제안 → 2인 확인 → 이력)하는 대상은 `evidence_tier`(L1~L4,
    근거 신뢰도)다.** `source.grade`(G0~G3)는 카피레인 개발 단계의 데이터 수집
    파이프라인이 이미 매긴 값이라 화면은 **표시만** 하고 재판정하지 않는다.
  - 판정한 사람과 확인한 사람은 **달라야** 한다 (기존 `ck_source_four_eyes` 와
    같은 원칙을 새 컬럼에도 적용).

## ⬜ 2026-09-16 정정 — 처음엔 G등급을 화면 판정 대상으로 잘못 짰었다

이 문서 첫 버전(09-14)은 `source_grade_proposal`/`source_grade_history` 를
`grade`(G0~G3) 기준으로 설계했다. 이후 확인 결과:

- `grade`(G0~G3, D-15)는 **이용조건 게이트**다 — 데이터 수집 단계에서
  `registry.require(src, use=...)` 가 실제로 참조하는 실행 가능한 값이고, 팀이
  카피레인을 개발하면서 이미 판정을 끝낸 것이다. 관리자 화면이 이걸 또 판정하면
  파이프라인이 쓰는 값과 화면이 보여주는 값이 따로 놀 위험이 있다.
- `evidence_tier`(L1~L4)는 **근거 신뢰도**다 — 운영 중에 판정 근거를 볼 때
  "이 소스가 얼마나 공신력 있는가"를 참고하는 값이고, 처음부터 이게
  `/admin/sources` 화면이 다루려던 대상이었다 (목업 화면 문구가 L1~L4였다).

그래서 이 문서는 **`evidence_tier` 를 2인 확인 대상으로, `grade` 는 읽기 전용
표시값으로** 재설계한다.

## `source.evidence_tier` (신규 컬럼) 먼저 추가

```sql
CREATE TYPE evidence_tier_t AS ENUM ('L1','L2','L3','L4');

ALTER TABLE source
    ADD COLUMN evidence_tier      evidence_tier_t,
    ADD COLUMN tier_decided_by    TEXT,
    ADD COLUMN tier_reviewed_by   TEXT,
    ADD COLUMN tier_decided_at    TIMESTAMPTZ,
    ADD COLUMN tier_evidence_url  TEXT,
    ADD CONSTRAINT ck_tier_four_eyes
        CHECK (tier_decided_by IS NULL OR tier_decided_by <> tier_reviewed_by);
```

- `grade` 쪽 4-eyes 컬럼(`grade_decided_by` 등)은 **그대로 둔다** — G등급은 여전히
  수집 파이프라인이 매기는 값이라 건드리지 않는다. L등급용 컬럼을 별도로 둬서
  두 판정 흐름이 서로 섞이지 않게 한다.
- 전부 nullable로 시작 — 기존 소스 73종에 L등급 소급 판정이 필요해서, 우선
  비워두고 점진적으로 채우는 쪽을 제안한다.
- 판단 기준표는 `판정근거_등급기준_초안.md` "확인 순서" 절 참고.

## 기존 스키마가 주는 문제 (G등급과 동일)

`grade_decided_by`/`grade_reviewed_by` 가 `NOT NULL` + `CHECK` 조합으로
2인 확인을 강제하듯, `evidence_tier` 도 같은 문제를 안는다 — **1차 판정만 되고
2차 확인 전인 "대기 상태"를 `source` 에 직접 저장할 곳이 없다.**

## 제안: `source_evidence_tier_proposal` (신규 테이블)

"판정 대기 중"인 L등급 제안을 담는다. `source.evidence_tier` 는 **승인된
값만** 담는 정본으로 유지한다.

```sql
CREATE TABLE source_evidence_tier_proposal (
    proposal_id      BIGSERIAL PRIMARY KEY,
    source_id        TEXT NOT NULL REFERENCES source(source_id) ON DELETE CASCADE,
    proposed_tier    evidence_tier_t NOT NULL,
    proposed_by      TEXT NOT NULL,
    proposed_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    evidence_url     TEXT,                 -- 판단 근거 (법령정보센터 링크·고시번호 등)
    note             TEXT,
    -- 확인 결과 (승인 전엔 전부 NULL)
    status           TEXT NOT NULL DEFAULT 'pending',  -- pending / approved / rejected
    reviewed_by      TEXT,
    reviewed_at      TIMESTAMPTZ,
    reject_reason    TEXT,
    CONSTRAINT ck_tier_proposal_four_eyes
        CHECK (reviewed_by IS NULL OR reviewed_by <> proposed_by),
    CONSTRAINT ck_tier_proposal_status
        CHECK (status IN ('pending', 'approved', 'rejected'))
);
```

- **제안(1차 판정)**: `proposed_by`만 채워서 INSERT. `status='pending'`.
- **승인(2차 확인)**: `reviewed_by`·`reviewed_at` 채우고 `status='approved'`로
  UPDATE. 같은 트랜잭션에서 `source.evidence_tier`·`tier_decided_by`·
  `tier_reviewed_by`·`tier_decided_at`·`tier_evidence_url` 을 이 제안 값으로
  UPDATE — `ck_tier_four_eyes` 가 그대로 다시 검증해준다 (이중 안전장치).
- **반려**: `status='rejected'`, `reject_reason` 채움. `source` 는 안 바뀜.

## 제안: `source_evidence_tier_history` (신규 테이블) — 이력 전용

새 L등급을 완전히 새 `source_id`로 만들지 않고 기존 row를 UPDATE하면 이전
등급값이 사라져 되돌릴 수 없다. 그래서 승인될 때마다 새 이력 row를 남긴다.

```sql
CREATE TABLE source_evidence_tier_history (
    history_id       BIGSERIAL PRIMARY KEY,
    source_id        TEXT NOT NULL REFERENCES source(source_id) ON DELETE CASCADE,
    tier              evidence_tier_t NOT NULL,
    decided_by       TEXT NOT NULL,
    reviewed_by      TEXT NOT NULL,
    decided_at       TIMESTAMPTZ NOT NULL,
    evidence_url     TEXT,
    proposal_id      BIGINT REFERENCES source_evidence_tier_proposal(proposal_id),
    superseded_at    TIMESTAMPTZ,           -- NULL = 현재 유효한 등급
    CONSTRAINT ck_tier_history_four_eyes CHECK (decided_by <> reviewed_by)
);
```

- 제안이 승인될 때마다: 이전 이력 row의 `superseded_at`을 채우고, 새 row를
  `superseded_at IS NULL`로 추가.
- `source.evidence_tier` 는 **`superseded_at IS NULL` 인 이력의 값과 항상
  같아야 한다** — `source` 자체는 "지금 유효한 값의 캐시"로만 쓰고, 정본은
  이력 테이블.
- **되돌리기** = 이전 이력 row를 다시 "현재"로 만드는 새 이력 row를 추가하는
  것 (이력을 삭제하지 않는다 — D-54 "수는 원장에만"과 같은 정신).

## `source.grade`(G0~G3) — 화면에서는 표시만

- 화면(`/admin/sources`, 상세 페이지)은 `grade` 컬럼을 **읽기만** 한다 —
  목록·필터에 계속 노출하되, 제안·2인확인·이력 대상에서는 뺀다.
- `grade`는 카피레인 데이터 수집 파이프라인(`load_db.py`, `registry.require()`)이
  이미 판정을 끝낸 값이라, 화면에서 재판정하면 파이프라인이 실제로 쓰는 값과
  화면이 보여주는 값이 따로 움직일 위험이 있다 — 그래서 관리 대상에서 제외한다.
- 기존 `source.grade`, `grade_decided_by` 등 4-eyes 컬럼·제약은 그대로 유지.

## 남은 결정 사항 (팀장 승인 요청에 포함할 것)

1. `source.evidence_tier` + 4-eyes 컬럼 5종 신설 (`ALTER TABLE source`) —
   `db/**` 등급1
2. `source_evidence_tier_proposal`, `source_evidence_tier_history` 두 테이블
   신설 — `db/**` 등급1
3. `source.evidence_tier` 를 이력 테이블의 파생값(캐시)으로 둘지, 아니면 이력
   테이블만 두고 뷰(VIEW)로 대체할지 — **캐시 방식을 제안** (기존 코드 패턴과
   일관성 유지)
4. `evidence_tier` 를 `NOT NULL` 로 강제할지 — 기존 소스 73종 소급 판정 필요.
   **우선 nullable로 시작하는 안 제안**
5. `dict_entry` 는 이번 스코프에 포함하지 않는다 — 별도 논의 필요
   (판정근거_등급기준_초안.md 참고)
6. `status` 를 ENUM으로 할지 TEXT + CHECK 로 둘지 — 기존 관행(`dict_entry.dict_kind`
   가 TEXT)을 따라 우선 TEXT + CHECK 로 초안
7. **`source.grade`(G0~G3)는 화면 관리 대상에서 제외, 표시만** — 데이터 수집
   파이프라인이 이미 매긴 값이라 재판정하지 않는다는 전제에 팀장 동의 필요
