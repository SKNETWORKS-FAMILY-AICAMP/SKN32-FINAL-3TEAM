> **작성자** 오한빈 (팀장) · **2026-09-12 밤** · 근거 **D-50 · D-87 · D-94 · D-99 · D-119 · D-124 · D-176 · D-181 · D-187 · D-190 · D-205**

> **이 문서는 무엇인가** — 팀 5인이 **같은 환경에서, 서로의 완성을 기다리지 않고** 일하기 위한
> 경계(seam)의 목록이다. 각 경계마다 「무엇이 오가나 · 어떤 형식인가 · 무엇이 지키나」 셋을 적는다.
>
> **이 문서가 아닌 것** — 🚨 **수치는 여기 없다.** 게이트 수·행 수·일정 수는
> `docs/00_사실원장.md` 가 단일 출처다 (D-54). 게이트 **목록**은 `docs/00_거버넌스_집행계약.md`,
> 결정의 **근거**는 `docs/00_설계결정기록.md` 다. 여기 적힌 D 설명은 요약이고 정본이 아니다.
>
> **이 문서가 낡는 자리** — §9 에 적어 뒀다. 낡을 자리를 모르는 문서가 가장 조용히 낡는다.

## 0. 한 줄

**계약은 이미 절반이 서 있다.** 비어 있는 것은 **설정 · 파이프라인 파생물 · 실험** 세 경계이고,
셋 다 같은 병이다 — **경계가 `dict` 다.** 그리고 `dict` 경계는 오류를 안 낸다.

★ 이 저장소가 사흘 동안 세 번 밟은 모양이 그것이다 — `paragraph`·`item`(09-12 오전) ·
`fuse()` 의 어휘 점수(오후) · `part`(밤 · D-199). **셋 다 생산자는 있고 소비자가 없었고,
셋 다 조용했다.** 팀이 다섯이 되면 이 모양은 다섯 배로 난다.

## 2. 병목 셋 — 무엇이 막고, 무엇으로 끊나

병목을 **없앨 수는 없다.** 데이터는 커밋 안 하고(D-19), 그래프는 한 사람이 지고(D-50),
GPU 는 계정이 하나다(D-94). ★ **끊는다는 것은 「그 병목이 안 풀려도 남이 일할 수 있게」다.**

### 2-1. 🔴 데이터 — `data/**` 가 커밋되지 않는다

| | |
|---|---|
| **왜 막나** | D-19 로 미커밋 → 기기마다 다르다 → 게이트 7개가 CI 밖 → 새 클론은 화면을 띄워도 빈 DB 다 |
| **이미 선 절단** | 골든 픽스처 **judge 9 · generate 2 · compose 3** 과 `GET /fixtures/{kind}/{name}` (D-124). 화면·BFF 는 **DB 없이 모든 분기를 그린다** |
| 🔴 **비어 있는 것 ①** | D-124 가 *"골든 픽스처를 실제 파이프라인 출력으로 갱신하는 규칙을 함께 둔다"* 라 적었는데 **그 규칙도 명령도 없다.** 픽스처는 손으로 만든 것이고, 코어가 자라면 **조용히 낡는다** — 화면은 낡은 모양에 붙는다 |
| 🔴 **비어 있는 것 ②** | **`/search` 에는 픽스처가 없다.** DB 가 없으면 503 이다. 화면이 이 진입점을 부른다면 데이터 병목이 화면까지 그대로 온다 |

**끊는 법 둘**

1. **픽스처 재생성 명령** — `launcher.py fixtures --write` (가칭). 데이터가 있는 기기에서
   실제 파이프라인 출력으로 픽스처를 다시 쓴다. **게이트는 「픽스처가 계약을 통과하는가」가
   아니라 「픽스처가 파이프라인 출력과 같은 모양인가」를 본다.**
   🚨 지금 `GET /fixtures/{kind}/{name}` 는 **계약을 통과시켜** 낸다(`model_validate_json`) —
   모양은 맞는데 **낡은 것**은 그대로 통과한다 (D-188 — 무탐은 안심시킨다).
2. **계약 한 줄 — 화면은 `/search` 를 부르지 않는다.** 판정 응답의 `EvidenceArticle` 이
   근거 조문을 이미 담는다(`contracts.py`). `/search` 는 **사람이 조문을 찾는 도구**이지
   화면의 데이터 경로가 아니다. ⬜ **이것은 판정이다** — 관리자 화면(ssm·psj)이 조문 검색을
   요구하는지 나는 화면설계서를 안 봤다 (§8).

### 2-2. 🔴 LangGraph — 그래프는 한 사람이 지고, 상태에 B·C 가 없다

| | |
|---|---|
| **왜 막나** | T4 는 팀장 단독 SPOF (D-50 · D-94 가 *"실험을 분배해도 구조는 여전히 한 사람"* 이라 적었다). 그래프 본체는 **4.2 (9/29~10/7)** |
| **이미 선 절단** | 스텁 배선 완료 — **모델도 판정 로직도 없이 end-to-end 한 바퀴가 돈다** (D-124). 라우터는 그래프 없이 단독 테스트하고, 컴파일본은 방문 순서만 본다 |
| 🔴 **비어 있는 것** | **진입점 B·C 가 상태에 없다.** `docs/02_설계/LangGraph_상태_스키마.md` §개정(D-181)이 넷을 지목했다 — `페르소나 목록(팬아웃)` · `키워드 선별 결과` · `후보 N=3` · `프론티어 점수`. 이름도 `JudgeState` 라 판정 전용으로 읽힌다 |

⛔ **여기가 ksr·lse 를 실제로 막는 자리다.** 둘의 배정이 「유저 화면 + 유저 BFF · **AI 광고 생성**」인데,
그 진입점의 상태가 없다. 계약(`GenerateResponse`·`ComposeResponse`)은 이미 서 있으므로
**화면은 그릴 수 있다** — 막히는 것은 **BFF 가 코어에 무엇을 넘기고 무엇을 돌려받는가**의 안쪽이다.

**끊는 법** — 상태를 **지금 넓히되 값은 스텁으로** 둔다.

    JudgeState  →  PipelineState (이름부터 고친다 — D-181 이 지적한 오독 자리)
                   B·C 키를 **지금** 추가한다. 값이 비어도 **키가 있으면 계약이 선다**
                   `to_response()` 가 계약을 만들어 내보내므로 **화면은 상태를 몰라도 된다**

★ **키를 늦게 더하는 비용이 실물로 있다** — 0008 이 `chunk` 에 열 둘을 더했을 때
`v_current_chunk` 가 낡아 검색이 통째로 503 이 났다(0009). **뒤에 더하는 필드는 읽는 쪽을
낡게 만든다.** 상태도 같다.

팀장이 한 번 돌려 유형별 F1 의 **폭**을 원장에 적는다. 폭을 모르면 다섯 개의 수를 못 읽는다.

## 3. Pydantic 을 어디에 넣고, 어디에 안 넣나

🚨 **「Pydantic 도입」은 「전부 Pydantic 으로 바꾼다」가 아니다.** 경계마다 답이 다르다.

| # | 경계 | 넣나 | 무엇으로 | 왜 |
|:-:|---|:-:|---|---|
| 1 | HTTP 계약 | ✅ **이미** | `app/contracts.py` | D-124. 추가할 것은 **OpenAPI 스냅샷 게이트** 하나 (§6) |
| 4 | **설정** | 🆕 **넣는다** | `pydantic-settings` · `app/settings.py` **하나** | `dsn()` 네 벌을 한 벌로. 타입·기본값·검증이 한 곳에 |
| 5 | **파이프라인 파생물** | 🆕 **넣는다 (범위 제한)** | `preprocess/records.py` — `ChunkRecord` 부터 | **지금 흐르는 경로만.** `part` 가 샌 자리가 정확히 여기다 (D-199) |
| 6 | **실험 설정** | 🆕 **넣는다** | `ExperimentConfig` | D-94 의 「설정 하나」에 형식을 준다 |
| 2 | **그래프 상태** | ❌ **안 넣는다** | `TypedDict` 유지 | 근거 넷 — 아래 §4 |
| 3 | DB | ❌ 안 넣는다 | `db/schema.sql` 이 정본 | 겹치면 **세 벌**이 된다 (파일 · 문서 부록 · pydantic). D-99 |

### 🚨 #5 에 범위를 거는 이유

파생물을 **전부** 모델로 바꾸면 `preprocess/` 20여 파일이 한 번에 흔들린다.
★ **값이 입구에서 출구까지 흐르는 최소 경로를 먼저 만든다** — `law_article → chunk → embed → DB`
하나만 모델로 잇고, 나머지는 그 경로가 값을 하는 것을 본 뒤에 한다.
⬜ 나머지 파생물의 범위는 **판정 대상**이다 (§8).

## 4. 그래프 상태에 Pydantic 을 쓰지 않는 이유 — 근거

LangGraph 공식 문서가 `StateGraph` 의 `state_schema` 에 Pydantic `BaseModel` 을 쓸 수 있다고
적으면서, **한계 넷**을 같이 적는다.

| | 공식 문서가 말하는 것 | 우리 맥락에서 무슨 뜻인가 |
|:-:|---|---|
| ① | *"그래프의 출력은 pydantic 모델의 인스턴스가 아니다"* | 나가는 쪽은 어차피 `to_response()` 가 계약으로 만든다 — 여기서는 손해가 작다 |
| ② | *"런타임 검증은 **첫 노드의 입력에서만** 일어나고, 이후 노드나 출력에서는 일어나지 않는다"* | 🔴 **치명이다.** 우리가 잡고 싶은 것은 **중간 노드가 상태를 잘못 채우는 것**인데, 정확히 거기서 안 돈다 |
| ③ | *"pydantic 의 검증 오류 트레이스는 **어느 노드에서 났는지 말하지 않는다**"* | 🔴 **D-51 과 정면으로 충돌한다** — *"오류는 고치는 법을 보여준다."* 노드 이름 없는 검증 오류는 고치는 법을 안 보여준다 |
| ④ | *"pydantic 의 재귀 검증은 느릴 수 있다. 성능이 중요하면 dataclass 를 고려하라"* | D-77 예산표가 판정 전체 <500ms 를 건다. ⬜ **우리 상태 크기에서 얼마나 느린지는 안 쟀다** |

★ **그래서 검증은 상태가 아니라 경계에서 한다.** `to_response()` 가 `JudgeResponse` 를 만들 때
Pydantic 이 검증하고, **그 지점은 노드가 특정된다** — ③이 사라진다.
🚨 그리고 상태 안쪽은 이미 **게이트가 지킨다** — 리듀서 키 검사(잘못된 annotation 이 append 대신
조용히 덮어쓰는 것)와 라우터 단독 테스트가 `tests/test_graph_routers.py` 에 있다 (D-124).

⬜ **뒤집힐 수 있는 자리** — ②·④는 LangGraph 판이 올라가면 달라질 수 있다.
**스택 핀을 올릴 때 이 절을 다시 읽는다** (D-205 — 설계·탐색은 자유롭게, 결정은 실측과 검증으로).

## 5. 충돌 방지 — 누가 무엇을 고치나

🚨 **경계가 서면 충돌은 「같은 파일을 두 사람이 고칠 때」만 남는다.** 그 자리를 미리 가른다.

| 영역 | 소유 | 남이 고치려면 |
|---|---|---|

### 🔴 진짜 위험 둘

1. **`uv.lock`** — 두 사람이 각자 의존성을 더하면 lock 충돌이 **팀 전체로 번진다.**
   `pyproject.toml` 이 이미 경고를 적어 뒀다 (*"지금 LangGraph·GPU 패키지까지 넣으면 재 lock 이
   반복되고 lock 충돌이 팀 전체로 번진다"*). ✅ **게이트가 이미 있다** — CI 의 `uv sync --frozen`
   이 lock 을 고쳐 통과시키는 길을 막는다.
2. **`app/templates/` 공유 파일** — 화면 넷이 한 레이아웃을 쓰면 거기서 매일 충돌한다.
   ⬜ **소유자를 정해야 한다** (§8).

| 설정 | ⬜ **없다** | 전부 |

| 실험 | ⬜ **없다** | 전부 |

### 🆕 넷째 축 — 계약 축

인계 09-12 §3-① 이 **상태가 네 곳에 사는데 축을 잇는 검사는 둘뿐**이라 적었다.

    저장소(커밋)  ──  pytest -m gate     ✅ D-89
    기기(data/)   ──  doctor --data      ✅ D-89
    DB            ──  ❌ 없다             D-187
    문서(주장)     ──  ❌ 없다

🆕 **다섯째가 하나 더 있다 — 계약(OpenAPI).** FastAPI 가 `openapi.json` 을 자동 생성하므로
**스냅샷을 커밋해 두고 diff 하면** 계약 변경이 커밋에서 보인다. 지금은 `contracts.py` 를 고치면
**아무 데도 안 튄다** — 4명이 그것을 보고 있는데도.

**제안** — `tests/test_openapi_snapshot.py` · 게이트. 스냅샷이 다르면 실패하고,
**고칠 방법은 스냅샷을 갱신하는 커밋을 같이 올리는 것**이다. 그러면 계약 변경이
「조용한 수정」이 아니라 **리뷰 대상**이 된다.
🚨 이것이 2026 년 관행으로 자리 잡은 것(스펙 스냅샷 diff · 스펙에서 클라이언트 생성 ·
스펙 기반 계약 테스트) 중 **우리 규모에 맞는 최소 조각**이다. Schemathesis 같은 퍼징까지는
지금 안 간다 — 진입점 셋 중 둘이 아직 501 이다.
