# LoRA sLLM vs GPT API 프롬프트 엔지니어링 — 비교 실험 기획서

- **작성**: lse (2026-09-29) · 실행 보조: Claude Code
- **이어받는 문서**: `docs/lse/sLLM_파인튜닝_결과서_2026-09-22.md` (LoRA 1·2차 실행 결과)
- **상태**: 계획 단계 — 아직 실행 전 (오늘은 기획서만).

## 1. 왜 이 비교를 하는가

`sLLM_파인튜닝_결과서_2026-09-22.md`가 확인한 것: LoRA(Qwen2.5-1.5B, 821쌍 학습)는
**규칙주입 계열 문구엔 100% 정답을 맞히지만, 완전히 새로운 문구는 핵심 내용을 날려버린다**
("당뇨병 환자도 안심하고 드실 수 있는 치료 효과" → "치료에 도움을 줄 수 있음"). 이게
"LoRA가 데이터가 적어서 그런 건지" 아니면 "1.5B짜리 작은 모델의 한계인지"를 아직
모른다 — 데이터 틀 다양성을 늘리는 다음 라운드(§8, 결과서)에 자원을 쏟기 전에, **같은
태스크를 GPT-4o-mini(프롬프트 엔지니어링만, 파인튜닝 없음)로 돌려서 비교하면 그 답이
갈린다**:

- GPT도 똑같이 핵심 내용을 날린다 → 이건 모델 크기·사전학습 지식의 문제가 아니라
  **태스크 자체가 원래 이 정도 난이도**라는 뜻. 데이터 늘리는 것보다 프롬프트/후처리
  설계가 더 급함.
- GPT는 안 그런다 → LoRA(1.5B)가 작아서/데이터가 적어서 일반화를 못 하는 것 —
  데이터 틀 다양성 보강이 맞는 방향이라는 근거가 하나 더 생김.

즉 이 실험의 목적은 "뭐가 더 좋은 모델이냐"가 아니라, **다음에 시간을 어디에 써야
하는지 결정하기 위한 진단**이다.

## 2. 비교 설계 — 공정하게 맞추는 것 / 못 맞추는 것

**맞추는 것** (LoRA §5-1 실행과 동일 기준):
- 같은 held_out 121건(`docs/lse/train_pairs.jsonl`)을 입력으로 쓴다 — LoRA가 이미
  이 121건에 대한 생성 결과를 갖고 있어(노트북 §6 출력) 나란히 비교 가능.
- 같은 출력 스키마 요구: `app.contracts.RewriteSet`(`body`/`mandatory_note`/`placement`)
  JSON, 같은 채점 기준(`RewriteSet.model_validate_json`으로 스키마 통과 여부).
- 같은 system 지시문 취지(위반 제거, JSON만 출력) — LoRA 학습에 쓴 `SYSTEM_PROMPT`를
  그대로 재사용.

**못 맞추는 것 (그래서 명시해 둘 것)**:
- LoRA는 821쌍으로 **가중치 자체가 바뀐** 모델이고, GPT는 **가중치를 안 건드리고
  프롬프트만** 다르다 — 애초에 다른 종류의 개입이라 "순수 비교"는 불가능하다. 이 실험은
  "동일 선상 비교"가 아니라 "각자 최선을 다했을 때 뭐가 이 태스크에 더 맞는가"를 보는
  것이다.
- GPT는 학습 데이터를 "본 적"이 있는지 알 수 없다(사전학습 데이터에 이 법령·사례가
  섞여 있을 가능성 — 확인 불가). 결과 해석할 때 이 점을 감안한다.

## 3. 실험 조건 — GPT 쪽 2가지 변형

| 조건 | 프롬프트 구성 |
|---|---|
| **GPT zero-shot** | LoRA와 동일한 `SYSTEM_PROMPT` + `위반 문구/위반유형/근거`만. 예시 없음. |
| **GPT few-shot** | zero-shot 프롬프트 + train에서 뽑은 예시 3~5개(입력→출력 쌍). 예시는 provenance(규칙주입/실사례)·violation_types를 고르게 섞어서 선정 — 한쪽으로 치우치면 LoRA가 걸렸던 "틀 암기"를 프롬프트로 그대로 재현할 위험이 있음(§6 참고). |

**모델**: `gpt-4o-mini` (비용 대비 충분 — 아래 §5 비용 추정).

## 4. 평가 지표 — 자동 3종 + 사람 눈검수 소량

LoRA 때는 "정답과 토씨 하나 안 틀리고 일치"가 오히려 과적합 증거였다(결과서 §5-1
해석 참고) — 그러니 이번엔 "정답과 일치하는가"보다 **"핵심 내용을 지키면서 위반만
지웠는가"**를 직접 재는 지표를 쓴다.

1. **스키마 통과율** (자동) — `RewriteSet.model_validate_json` 성공 여부. LoRA는
   121/121(100%) — GPT도 시스템 프롬프트로 JSON을 강제하니 이 지표는 변별력이 낮을
   것으로 예상(둘 다 높게 나올 듯). 참고 지표로만 쓴다.
2. **핵심 명사구 보존율** (자동, 새로 만듦) — 입력 문장에서 위반 관련 수식어(수치·
   최상급·완화구 등 이미 T-rule이 다루는 패턴)를 뺀 "핵심 주장어"가 출력에도 남아있는지
   문자열 포함 여부로 체크. `preprocess/inject.py`의 `core()` 함수(핵심주장 추출)를
   재사용할 수 있는지 먼저 확인 — 없으면 간단한 버전을 새로 짠다. LoRA가 "당뇨병 환자도
   안심" 사례에서 실패한 게 바로 이 지표로 잡힌다.
3. **출력 템플릿 다양성** (자동) — `docs/lse/sLLM_파인튜닝_결과서_2026-09-22.md` §2-1의
   "고유 틀 비율" 계산과 같은 방식(핵심주장을 `{}`로 치환한 뒤 고유 문자열 수를 셈).
   LoRA가 "OOO에 도움을 줄 수 있음"으로 획일화됐다는 걸 숫자로 보여줬던 방법 그대로
   GPT에도 적용 — GPT도 똑같이 한 패턴으로 수렴하는지 확인.
4. **사람 눈검수** (수동, 15~20건 표본) — 자동 지표 3종이 못 잡는 것(문법 자연스러움,
   법적으로 말이 되는 교정인지)을 held_out에서 provenance·violation_types 고르게 뽑아
   직접 읽어본다. LoRA 검수 때 썼던 방식(§5-1 실패 사례 표) 그대로.

## 5. 비용·시간 추정

- `gpt-4o-mini`: 대략 입력 \$0.15 / 출력 \$0.60 (1M 토�큰당, **실행 직전 OpenAI 가격
  페이지로 재확인** — 여기 적은 값은 기획 시점 참고치일 뿐 확정값 아님).
- 콜 수: held_out 121건 × 2조건(zero/few-shot) = **242콜**. 프롬프트당 입력 ~200~500
  토큰(few-shot은 예시 포함이라 더 큼), 출력 ~80토큰 안팎(JSON 짧음) — 총 토큰이
  수만 단위라 **예상 비용은 1천 원 미만**(자릿수 기준 참고치, 실측 필요).
- LoRA는 로컬 GPU 추론이라 API 비용 없음 — 이미 노트북에 121건 결과 있음(재실행 불필요).

## 6. 예상되는 함정 — 미리 적어 둔다

- **few-shot 예시 선정이 결과를 왜곡한다**: 예시를 규칙주입(T1류) 위주로 고르면 GPT도
  "~에 도움을 줄 수 있음" 패턴에 끌려갈 수 있다 — LoRA가 왜 과적합됐는지 그대로
  재현하는 셈이라, 그게 나오면 "few-shot 자체의 문제"인지 "GPT의 한계"인지 헷갈린다.
  → 예시 선정 시 T2(다양한 틀)·실사례(ftc_stage) 비중을 의도적으로 높인다.
- **GPT가 사전학습 때 관련 법령·사례를 봤을 가능성**: 결과가 좋게 나와도 "프롬프트
  엔지니어링이 잘 통했다"인지 "GPT가 이미 알고 있었다"인지 못 가른다 — 결과 해석에
  한계로 명시한다.
- **held_out 121건 중 옛 결과서가 지적한 "틀고정 계열"이 대다수**(injected_golden
  95src 기반)라, 자동지표 평균이 그쪽에 쏠려 실사례(ftc_stage, 3건)의 신호가 묻힐 수
  있다 → provenance별로 결과를 나눠서 집계한다(전체 평균만 보지 않는다).

## 7. 실행 계획 (다음 단계 — 오늘은 안 함)

1. `.env`에 `OPENAI_API_KEY` 추가(커밋 금지 — `.gitignore`에 이미 `.env*` 있음).
2. `docs/lse/`에 GPT 호출 스크립트 작성 — held_out 121건 × 2조건 돌려서
   `gpt_results.jsonl`로 저장(입력·출력·조건 태그).
3. 평가 스크립트 작성 — §4의 자동지표 3종을 LoRA 결과와 GPT 결과 양쪽에 동일하게 돌림
   (LoRA 결과는 이미 노트북 출력에 있으니 거기서 재추출).
4. provenance별(규칙주입/실사례) × 조건별(LoRA/GPT zero/GPT few) 비교표 작성.
5. 사람 눈검수 15~20건.
6. 결과서 작성 — `docs/lse/sLLM_vs_GPT_비교_결과서_<날짜>.md` (이번 기획서 §1의 진단
   질문에 답하는 형태로: "데이터를 늘려야 하는가 vs 프롬프트/후처리를 손봐야 하는가").

## 8. 이 문서가 안 정하는 것

- gpt-4o 같은 상위 모델과의 비교는 범위 밖(비용·시간상 1차는 4o-mini만).
- GPT 결과를 실제 서비스에 채택할지 여부 — 이 실험은 진단용이지 배포 결정이 아니다.
- `mandatory_note`/`placement` 채점 — LoRA와 마찬가지로 이번 held_out도 `body`만
  실값이라 두 필드는 이번 라운드에서도 검증 못 한다.
