## 1. 한 줄 요약

lse 가 만든 **1단계(위반 제거 sLLM) → 후처리 → 관문**은 D-264 의 규칙 조립 4종과 주장 원장(D-30)에 거의 1:1 로 대응한다.
`assemble` · `claim_ledger`(W9 · 지금 비어 있음)에 **규칙 부품부터** 넣고, sLLM 은 규칙이 못 만든 문장에만 뒤에 붙이는 순서를 제안한다.

## 2. 팀 설계 ↔ lse 부품 대응

| 팀 설계 (D-264 · D-30 · D-32 · D-119) | lse 부품 | sLLM 필요 |
|---|---|---|
| **삭제안** — 위반 구간을 뺀다 | 1단계가 질병 · 의약품 · 체험기 · 과장 구간만 지운다 | 예 (문장마다 구간이 다르다) |
| **사실 진술 치환** — 원산지 · 원료 · 제조 · 용량만 남긴다 | 1단계 + 후처리 `repair_ingredients`(원료명 잘림 · 오타를 원문 표기로) | 예 + 규칙 |
| **인정 문구 슬롯** — 식약처 인정 기능성 · 기능성화장품 공식 문구 | 후처리 `to_approved_claim`(인정 문구 14 + 화장품 8 범주) · 조건 `condition` | **아니오(규칙만)** |
| **실증 유지안** — 실증 필요 표현은 유지 + 조건 | 후처리 조건 메뉴(실증 자료 · 내수성 시험 · 함량 병기 · 순위 근거) | **아니오(규칙만)** |
| **주장 원장**(D-30) — 원문에 없는 새 주장 거부 | 관문 `new_words` · `ingredient_truncated` · `unapproved_claim` · `COSMETIC_CONCEPT` · 후처리 `label_check` | **아니오(규칙만)** |
| **합법화 불가 증명서**(D-32) | 1단계 `infeasible`(위반 유형 이름으로 사유) | 예 |
| **재판정**(D-119) | `rejudge.py` — 판정 코어(`build_review`)에 다시 넣는다 · 위반 유형이 붙으면 탈락 | 아니오 |
| 출력 3종 세트(D-33) `RewriteSet` | 1단계 출력 JSON 이 같은 꼴(`body` · `mandatory_note` · `placement`) | — |

→ **절반 이상이 sLLM 없이 규칙만으로 돈다.** 이 부분은 D-270 과 부딪히지 않고 W9 에 바로 쓸 수 있다.

## 3. 제안하는 연결 순서

```
진입점 B  keyword_screen → assemble → claim_ledger → rejudge → frontier
                              │
             ① 규칙 조립 (sLLM 없음)
                · 인정 문구 슬롯 · 실증 유지안 · 사실 진술(원문에 사실 구가 그대로 있을 때)
             ② (10/13 이후 · 팀장 판정 시) sLLM 1단계 — 규칙이 후보를 못 만든 문장만
                · 삭제안 · 사실 진술 치환 → 후처리(원료명 수리 · 조건)
                              │
             claim_ledger ← lse 관문 + label_check (원문에 없는 낱말 · 원료명 · 기능 거부)
             rejudge      ← 판정 코어 그대로 (D-119 · 판정을 새로 쓰지 않는다)
```

- **①만으로도 이득** — 인정 문구 슬롯 · 실증 유지 · 주장 원장 검사는 순수 파이썬이다(GPU 없음 · 결정적).
- **②는 선택** — 3B LoRA(어댑터 v12) · RTX 3080 기준 문장당 약 3~4초 · VRAM 약 7GB(bf16). 서빙은 D-47(vLLM 개발 · GGUF 데모) 틀을 따른다.

## 4. 인터페이스 (lse 함수 기준)

```
입력:  sentence(문장) · violation_types(판정 코어가 준 유형) · product(품목 · 선택)
출력:  outcome ∈ {candidate, hold, infeasible}
       rewrite = RewriteSet(body, mandatory_note, placement=None)   # candidate 일 때
       infeasible = 위반 유형 이름                                  # infeasible 일 때
       reasons = [관문 · 후처리 사유]                               # hold 일 때
       repairs = [후처리가 고친 내역]
```

현재 구현: `docs/lse/persona_pipeline_e2e.py` 의 `run_one(model, tok, text, labels)` — 앱으로 옮길 때는 모델 로드를 분리한 순수 함수로 다시 감싼다.

## 6. 한계 · 위험

- **실전 살리기 40%** — 살릴 수 있는 문구의 절반 이상이 보류로 간다(사람 검토).
- **v12 는 관문 의존이 크다** — 기능성 주장을 적극적으로 써서, 위반 포장 0 은 `label_check` 덕분이다.
- **N=3 · K=2(D-34) 미충족** — lse 는 후보 **하나**를 낸다. 보수 · 균형 · 공격 3안은 아직 없다(페르소나는 대상 고객 축).
- **표본** — 실제 광고 87개 · 살릴 수 있는 20개 — 1~2개 차이는 우연과 가르기 어렵다.
- **데이터** — 학습 정답 · 정답표 v2 모두 Claude 초안 · 법률 검토 전.
- **판정 코어** — 인코더 연결(W7) 전이라 재판정은 「위반 후보면 탈락」만 가린다(통과 보증 불가).

## 7. 팀장 판정이 필요한 것

1. **①(규칙 부품)을 W9 `assemble` · `claim_ledger` 에 넣을지** — 넣는다면 `docs/lse/stage_gate.py` · `postfix.py` 를 `app/` 아래로 옮겨 단일 위치(D-99)로 둔다.
2. **②(sLLM)를 10/13 게이트 이후 붙일지** — 붙인다면 「규칙이 못 만든 문장만」(D-264 「sLLM 은 뒤에」) 범위로.
3. **N=3 요구(D-34)** — sLLM 1안 + 규칙 조립 안을 합쳐 3안을 채울지, 1안으로 시작할지.
4. **관문 규칙 소유** — lse 관문의 금지어 · 질병어 목록과 팀 금지 사전(D-311)이 따로 논다. 하나로 합칠지.
