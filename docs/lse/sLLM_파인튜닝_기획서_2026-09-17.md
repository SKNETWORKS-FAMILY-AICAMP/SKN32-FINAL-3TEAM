## 1. sLLM이 생성해야 할 것 — 화면·계약에 이미 정의돼 있다

내가 만든 화면(`review.html`·`generate.html`)과 계약(`app/contracts.py`)이
정확히 이 sLLM의 출력 목표를 이미 정의해뒀다 — 새로 설계할 필요가 없다.

```python
class RewriteSet(BaseModel):
    """출력은 3종 세트다 (D-33) — 의결서 시정 형태가 정확히 이것이다."""
    body: str                       # 본문
    mandatory_note: str | None      # 필수 병기 문구
    placement: str | None           # 배치 지시

class Candidate(BaseModel):
    """리스크–소구력 프론티어의 한 점 (D-31). 단일 답을 주지 않는다.
    🚨 N=3 · K=2 (D-34) — 보수안 / 균형안 / 공격안.
    """
    label: str
    rewrite: RewriteSet
    residual_risk: Risk
    appeal_retention: float
```

즉 sLLM의 태스크는: **위반 소지가 있는 광고 문구(+ 위반 유형·근거) → 위험도가
서로 다른 재작성 후보 3개**(보수안·균형안·공격안, 각각 본문/필수병기문구/
배치지시)를 생성하는 것. 이 산출물은 `review.html`의 "재작성 제안"과
`generate.html`의 "카피 생성" 양쪽에서 같은 형태로 쓰인다.

🔴 **중요한 단서**: `RewriteSet` 독스트링이 "의결서 시정 형태가 정확히
이것"이라고 못 박아뒀다 — 즉 이 3분 구조(본문/필수병기문구/배치지시)는
내가 지어낸 게 아니라 **실제 공정위·식약처 의결서가 위반 사업자에게
내리는 시정명령의 형식 그대로**다. 그 말은 이미 수집된 의결서 원문
(`ftc_decisions_body`, `mfds_hf_ingredient_board`) 안에 이 형태의 실제
사례가 들어있을 가능성이 높다는 뜻 — 아래 데이터 절에서 이어간다.

## 2. 모델 후보

**소형 생성모델(sLLM)**로 좁히는 이유 — 판정(분류)과 달리 이건 **문장을
새로 만들어내는 태스크**라 encoder-only로는 안 되고, 그렇다고 대형 모델을
로컬에서 풀파인튜닝할 리소스는 없다. LoRA/QLoRA로 로컬 1대에서 돌릴 수 있는
크기(1.5B~3B)로 좁힌다.

| 후보 | 특징 | 이 태스크 적합성 |
|---|---|---|
| **`Qwen2.5-1.5B-Instruct`** (1순위 제안) | Apache-2.0(상업 이용 제약 없음), 한국어 포함 다국어 instruction 성능 준수, 가장 가벼워 반복 실험에 유리 | 라이선스가 깨끗해 **클라우드 에디션(D-66) 상업화 가능성**과 충돌 없음. 먼저 이걸로 사이클을 돌린다 |
| `Qwen2.5-3B-Instruct` | 1.5B보다 품질↑, 여전히 로컬 QLoRA 가능 | 1.5B 결과가 부족하면 스케일업 옵션 |
| `EXAONE-3.5-2.4B-Instruct` | LG, 한국어 특화 사전학습이라 문체 품질 기대 | **라이선스 확인 필요** — EXAONE 라이선스가 상업적 이용에 제약을 두는 버전이 있었다. 비교군으로만 실험하고, 채택 전 라이선스 조항을 반드시 재확인한다 |

**제안**: `Qwen2.5-1.5B-Instruct`로 먼저 사이클을 돌리고(라이선스 안전 +
가장 가벼움), 품질 비교용으로 `EXAONE-3.5-2.4B-Instruct`를 곁들인다 — 단,
후자는 라이선스 확인 전까지 "실험용"으로만 표시한다.

## 3. 데이터 — 지금 확보된 것으로 먼저 시작

`golden_sample`(팀 공식 학습셋)은 아직 0건이다. 멘토님 지시대로 기다리지
않고 아래 두 갈래로 먼저 시작한다.

### 3-1. `transform_pair` — 이미 스키마에 있는 병렬쌍 (1차 후보)

```sql
CREATE TABLE transform_pair (
    before_text  TEXT NOT NULL,   -- 결함이 있는(또는 원본) 문구
    after_text   TEXT NOT NULL,   -- 시정된(또는 변형된) 문구
    rule_id      TEXT             -- TRANSFORM_RULES T1~T10 (양방향 — 주입/시정)
);
```

`TRANSFORM_RULES`는 "정방향(주입)/역방향(시정) 양방향"(D-74, `docs/03_데이터/
전처리_사양.md`)으로 설계돼 있다 — 즉 이 표를 **역방향(시정)** 으로 읽으면
"위반 문구 → 교정 문구" 지도학습 쌍 그대로다. sLLM 1차 파인튜닝(Seq2Seq
형태: input=`before_text`, target=`after_text`)에 바로 쓸 수 있다.

⬜ 적재기가 없는 8개 테이블 중 하나로 이미 파악돼 있다(`docs/ohb/검토_
2026-09-10_전수.md`) — 즉 **이 표도 아직 로컬에 비어있을 가능성이 높다.**
착수 전에 `launcher.py inventory`로 먼저 확인한다.

### 3-2. 의결서 원문에서 직접 — "시정" 문구를 정규식으로 뽑기 (2차, 조사 필요)

`RewriteSet`이 "의결서 시정 형태 그대로"라는 단서를 따라가면, 이미
16,506건 확보된 `ftc_decisions_body`(원장 기준) 원문 안에 실제 시정명령
텍스트가 들어있을 가능성이 있다. `preprocess/mfds_hf.py`의 `body_lines`/
`fields`가 이미 의결서를 구조화된 필드로 쪼개는 로직을 갖고 있어 — 여기서
"시정" 관련 필드(있다면)를 추출하는 게 되는지 먼저 조사가 필요하다. 되면
`transform_pair`(합성)보다 **실제 사례라 더 신뢰도 높은 2차 데이터**가 된다.

**1차 제안**: 3-1(`transform_pair`)부터 시작 — 이미 정제된 쌍 형태라
바로 쓸 수 있다. 3-2는 "실행 계획" 조사 단계로 남긴다.

## 4. 전처리 전후 비교 — 기존 코드 재사용

`docs/lse/일반사용자_계정테이블_초안_2026-09-16.md`와 같은 날 검토했던
`preprocess/mask.py`(PII 마스킹)를 그대로 쓴다.

- **전(Raw)**: `transform_pair.before_text`/`after_text` 그대로 — 기관명·
  인명이 남아있을 수 있음.
- **후(Processed)**: `mask.apply_policy()` 적용 — 인명·기관명·주소 마스킹.

**비교 가설**: 생성 태스크에서는 마스킹이 성능 지표(생성 품질)에는 큰
영향이 없을 것 — 오히려 **모델이 실제 기관명·인명을 그대로 외워
재생산하는 걸 막는(개인정보 유출 방지) 안전 장치**로서의 의미가 더 크다.
그래서 이번엔 "성능 비교"보다 "안전성 비교"(마스킹 안 한 모델이 학습
데이터의 실명을 생성물에 그대로 뱉어내는지 샘플링해서 확인)를 같이 본다.

## 5. 실행 계획 (착수 시)

1. `launcher.py inventory`로 `transform_pair` 로컬 실물 확인
2. 없으면 — 팀에 공급 경로 문의, 또는 `preprocess/` 파이프라인을 직접
   돌려 소량 합성(단, 이건 팀 스키마 소유라 임의 적재 전 확인 필요)
3. `ftc_decisions_body`에서 "시정" 관련 필드 추출 가능성 조사 (3-2)
4. Raw / Masked 두 벌로 소량(수백 쌍) 데이터셋 구성
5. `Qwen2.5-1.5B-Instruct` LoRA 파인튜닝 — input: 위반 문구(+위반유형),
   target: `RewriteSet` JSON(본문/필수병기문구/배치지시)
6. 생성물이 실제 `RewriteSet` 스키마로 파싱되는지(형식 정확도) +
   원문 그대로 베끼지 않는지(마스킹 효과) 확인
7. 결과를 이 문서 뒤에 이어 붙여 팀에 공유

## 6. 이 문서가 안 정하는 것

- N=3(보수안/균형안/공격안) 각각을 어떻게 하나의 입력에서 서로 다르게
  생성할지(프롬프트 분기 vs 3회 샘플링 vs 조건부 생성) — 착수 후 실험.
  `residual_risk`/`appeal_retention` 수치 산정 방식도 마찬가지.
- 판정 인코더(수진님 담당)와의 연결 지점 — 실제 파이프라인에서는 판정
  인코더가 위반 유형을 먼저 판별한 뒤 그 결과를 이 sLLM 입력으로 넘기는
  구조가 될 텐데, 그 인터페이스는 두 담당자가 각자 진행 후 맞춘다.
- 팀의 정식 채택 여부 — 팀 파이프라인이 갖춰진 뒤 팀 전체가 낼 결론이고,
  이 프로토타입이 그 결정을 대체하지 않는다.

## 7. 실행 결과 (2026-09-17, 개인 Colab 프로토타입 1차)

### 7-0. §3 계획과 실제로 다르게 간 지점 — 왜

계획(§3-1·3-2)은 `transform_pair`나 `ftc_decisions_body`의 실제 시정문
텍스트를 쓰려 했는데, 착수해보니 둘 다 막혔다:

- `transform_pair` — `launcher.py inventory` 확인 결과 이 기기엔 원본
  수집 데이터가 **13개 소스 전부 0건**(원장에만 있고 이 기기엔 없음).
- `ftc_decisions_body` — `LAW_OC_KEY`로 인증 자체는 성공(`scripts/
  law_api_smoke.py`로 확인)했지만, `target=ftc` 쿼리는 검색어를 뭘 넣어도
  ("공정"처럼 반드시 걸릴 단어까지) 0건 — **이 키 계정이 공정위 대상
  접근 권한 자체가 없는 것으로 추정**된다. 원인 확인은 이 문서 범위 밖 —
  키 원소유자에게 별도 확인 필요.

그래서 **입력(위반 문구)은 오늘 실제로 수집한 진짜 데이터로, 출력(교정
문구)은 직접 작성**하는 절충안으로 바꿨다:

- `collect/openapi.py cosmetic_ingredient`(15111774, 화장품 원료성분정보,
  `apis.data.go.kr` REST 타입 — 식품안전나라 시간대 제한과 무관해서
  바로 됐다)로 실제 원료명 300건 수집(`data/raw/cosmetic_ingredient/`).
  가지열매추출물·구멍쇠미역추출물·마시멜로뿌리추출물 등 **실존 성분명**.
- 위반유형은 `docs/03_데이터/수집전처리_기획.md`의 실제 V0~V8 taxonomy와
  법조문 인용을 그대로 썼다(지어낸 분류가 아님).
- 교정 문구(`RewriteSet`)만 내가 직접 작성 — 실제 병렬 말뭉치가 확보되기
  전까지는 이 부분이 "합성"이라는 걸 숨기지 않는다.
- 참고로 `mfds_hf_ingredient` 등 식품안전나라 계열 API는 `FOODSAFETY_KEY`
  인증까지는 됐지만 **09시~19시 시간대 제한**(ERROR-503)에 걸려 오늘 낮엔
  못 받았다 — 권한 문제가 아니라 시간 문제라 별도 조치 불필요, 저녁 이후
  재시도하면 된다.

### 7-1. 데이터셋

`docs/lse/`가 아니라 로컬 개인 작업 폴더에 둔 `train_pairs.jsonl` —
"입력(위반 문구+위반유형) → 출력(RewriteSet JSON)" 쌍. 1차 15개 → 데이터
양 효과를 보려고 2차에 20개 더 얹어 **35개**(학습 30 · held-out 5)로 확장.
팀 원장(`data_sources.yaml`)에는 올리지 않았다 — 개인 프로토타입이라
§0에서 정한 대로 팀 공식 흐름과 분리해 둔다.

### 7-2. 실행 환경·모델

- Google Colab, T4 GPU (로컬 노트북은 8GB RAM·GPU 없음이라 부적합 —
  본문 로컬 CPU 실측으로 확인 후 이동 결정).
- `Qwen/Qwen2.5-1.5B-Instruct` + LoRA(`r=8, alpha=16`, `q/k/v/o_proj`
  타겟) — 전체 15억 파라미터 중 **0.14%(2,179,072개)**만 학습.
- 프롬프트는 채팅 템플릿(system+user+assistant)으로 구성하고, **정답
  (assistant) 토큰에만 loss를 걸었다**(질문 부분은 라벨 마스킹 `-100`).

### 7-3. 결과 — 데이터 15개 vs 35개 비교

| | 1차 (15개, 학습 13) | 2차 (35개, 학습 30) |
|---|--:|--:|
| 학습 loss | 1.44 | **0.87** |
| held-out 성공 | 2/2 | **5/5** |
| 학습 스텝 | 30 | 70 |

두 번 다 held-out(학습에 안 보여준) 예시에서 `RewriteSet` 스키마
(`body`/`mandatory_note`/`placement`)로 파싱되는 JSON을 스스로 생성했다.
2차 예시 중 하나:

```
입력: 목어석가루 함유 치약, 잇몸질환을 치료하는 의약품급 효과
생성: {"body": "목어석가루를 담은 치약입니다.",
       "mandatory_note": "본 제품은 잇몸 질환 치료용 의약품이 아닙니다.",
       "placement": "효능 표현 바로 아래"}
```

### 7-4. 이 결과가 증명하는 것 / 안 하는 것

- **증명하는 것**: 모델 선정 → 데이터 구성 → LoRA 파인튜닝 → 학습에 안 쓴
  입력에 대한 생성 → 계약(`RewriteSet`) 스키마 검증까지, **BFF가 만든
  화면·계약과 실제로 맞물리는 사이클 하나가 끝까지 돈다.** 데이터를
  늘렸을 때 loss·성공률이 함께 개선되는 것도 확인했다.
- **증명하지 않는 것**: 품질·일반화. 학습 데이터가 30개뿐이라 이건
  "패턴을 몇 개 배웠다"이지 "잘 작동하는 모델"이 아니다. 정식 채택
  가능성 판단에는 §3의 실제 병렬 말뭉치(`transform_pair` 또는 의결서
  시정문)가 확보된 뒤 재학습이 필요하다.

### 7-5. 남은 것

- `LAW_OC_KEY`의 `target=ftc` 권한 문제 — 원소유자에게 확인 요청.
- 저녁 시간대(19시 이후)에 `mfds_hf_ingredient`/`mfds_sanctions` 등
  식품안전나라 API 재시도 — 특히 `mfds_sanctions`의 `VILTCN`(위반일자
