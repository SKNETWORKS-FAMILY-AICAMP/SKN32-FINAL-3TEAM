## 1. 한 장 요약

| | |
|---|---|
| **스택** | PostgreSQL 16 + **pgvector** (별도 벡터DB를 쓰지 않는다 — D-41) |
| **ORM/마이그레이션** | SQLAlchemy 2.0 + Alembic |
| **테이블** | 19개 + 뷰 3개 + 열거형 14종 |
| **설계의 축** | 모든 파생물이 `fragment_id` 하나에 매달린다 — 소스를 지우면 문장·청크·벡터·사전·골든셋이 함께 사라진다 |
| **엔진 선택 근거** | MySQL이 아닌 이유는 취향이 아니라 D-20(캐스케이드 삭제)에서 도출됨(D-95) |

### 1-1. 실측 검증 결과 (PostgreSQL 16.13에서 DDL을 실제로 실행)

**① 제약 5종이 전부 위반을 거부했다**

| # | 제약 | 시도한 것 | 결과 |
|:-:|---|---|:-:|
| 1 | `ck_source_four_eyes` | 판정자와 확인자를 같은 사람으로 | ✅ 거부 |
| 2 | `ck_golden_injected_not_holdout` | 주입본을 평가 split에 | ✅ 거부 |
| 3 | `ck_segment_k_anon` | 5명짜리 세그먼트 생성(k-익명성 미달) | ✅ 거부 |
| 4 | `ck_chunk_tokens` | 900 토큰 청크(리랭커 상한 512 초과) | ✅ 거부 |
| 5 | `ck_sentence_span` | 오프셋 역전(start > end) | ✅ 거부 |

**② 캐스케이드 삭제로 9개 테이블이 전부 0이 됐다** (소스 회수 요청 대응 검증)

```
DELETE FROM source WHERE source_id='t_src';

            삭제 전   삭제 후
fragment          1  ->  0
document          1  ->  0
sentence          1  ->  0
chunk             1  ->  0
chunk_embedding   1  ->  0     ← 벡터까지 함께 사라진다 (D-41 선택의 이유)
dict_entry        1  ->  0
sanction_rule     1  ->  0
golden_sample     1  ->  0
transform_pair    1  ->  0
```

이 초록불이 "거버넌스를 코드로 강제했다"는 증거다 — 소스 제공처에서 "쓰지 마세요" 회신이 오면
한 줄(`DELETE FROM source`)로 전체 파생물이 회수된다. 데이터가 쌓인 뒤에는 이 삭제 경로를
설계로 되돌릴 수 없다(D-20) — 그래서 처음부터 이렇게 짰다.

## 2. 설계 원칙 — 8가지, 전부 결정 근거가 있다

| # | 원칙 | 스키마 구현 | 근거 |
|:-:|---|---|---|
| 1 | 등급은 소스가 아니라 추출물의 속성 | `fragment.grade`가 독립 컬럼 — 소스 등급을 상속하지 않는다 | D-18 |
| 2 | 소스 회수 요청에 응할 수 있어야 한다 | 모든 파생 테이블에 `fragment_id ... ON DELETE CASCADE` | D-20 |
| 3 | 벡터도 함께 사라져야 한다 | `chunk_embedding`을 같은 인스턴스에 — 별도 벡터DB면 불가능 | D-41 |
| 4 | 2인 확인은 문서가 아니라 제약 | `CHECK (grade_decided_by <> grade_reviewed_by)` | D-66 |
| 5 | 위험도는 블랙박스 점수가 아니다 | 별표를 관계형 테이블로 — 코드가 직접 조회 | 기획서 3-4 |
| 6 | 데이터 재배포와 모델 배포는 다른 축 | `golden_sample.provenance`·`redistributable` | D-71 |
| 7 | 시정이 의도대로 됐는지 잰다 | `certainty`·`tense`·`sent_type` 3축 | D-74 |
| 8 | 정규화는 비파괴 | `raw`/`norm`/`offset_map` 3열 분리 | 전처리 기획 4-2 |

## 3. 개체 관계 개요

```
                        ┌──────────┐
                        │  source  │  ← data_sources.yaml 과 동기화
                        └────┬─────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
    source_constraint   source_use   collect_manifest
                             │
                        ┌────▼─────┐
                        │ fragment │  ← 등급이 갈리는 지점 (D-18)
                        └────┬─────┘
       ┌───────────┬─────────┼──────────┬───────────┬──────────┐
       ▼           ▼         ▼          ▼           ▼          ▼
   document    dict_entry  chunk   sanction_rule  product   golden_sample
       │                     │      penalty_rule   _fact          │
       ▼                     ▼      penal_clause                  ▼
   sentence          chunk_embedding                      transform_pair
       │                  (pgvector)
       └────────────────────┐
                            ▼
                      golden_sample
```

세로 화살표는 전부 `ON DELETE CASCADE`다 — 위에서 하나를 지우면 아래가 통째로 사라진다.
`segment`·`dataset_manifest`는 집계·메타 테이블이라 `fragment`에 매달리지 않는다.

## 4. 테이블 명세 (19개, 7개 그룹)

### 4-1. 거버넌스 (4개)

| 테이블 | 역할 | 핵심 제약 |
|---|---|---|
| `source` | 소스 레지스트리 — `data_sources.yaml`의 DB 표현 | `decided_by <> reviewed_by`, `BY` 플래그면 `attribution` 필수 |
| `source_constraint` | 제약 플래그 (1:N) | 11종 열거형 — `NOREDIST`·`NOSTORE`·`QUERYLOG`·`PREAPPROVAL`·`NOTRAIN` 등 |
| `source_use` | U1~U4 허용 여부 | 전파 규칙은 애플리케이션 계층에서 적용 |
| `collect_manifest` | 수집 이력·재현성 | `sha256` 동일하면 스킵, `event`로 삭제 이벤트도 기록 |

### 4-2. 원문·문장 (2개)

| 테이블 | 역할 | 주의 |
|---|---|---|
| `document` | 문서 단위(의결서 1건·법령 1건) | `superseded_at IS NULL`이 현행 |
| `sentence` | 문장 + 비파괴 정규화 | `raw`/`norm`/`offset_map` 3열, `evasion_flags`(회피 표기 자체가 위법 신호)를 피처로 사용 |

### 4-3. RAG (2개)

| 테이블 | 역할 | 주의 |
|---|---|---|
| `chunk` | 조·항 단위 청크 | `token_count <= 512` — 리랭커 상한 |
| `chunk_embedding` | pgvector | `vector(1024)` — 실제 임베딩 모델 차원은 확인 후 확정 |

### 4-4. 위험도 — RAG가 아니라 관계형 (3개)

| 테이블 | 담는 것 |
|---|---|
| `sanction_rule` | 행정처분 기준 [별표] — 위반유형×차수 → 처분종류·값 |
| `penalty_rule` | 과징금 고시 — 부과기준율·정액·가중·감경 |
| `penal_clause` | 벌칙 — 징역·벌금 상한(R4 근거) |

**왜 벡터가 아닌가** — 별표를 평문화해 임베딩하면 ① 표 구조가 깨져 "차수"와 "일수"의 대응이
사라지고 ② 검색 결과가 확률적이라 같은 입력에 다른 위험도가 나올 수 있다. 벡터에는 "이
별표가 규정하는 내용" 요약 문장만 넣어 검색 진입점으로 쓰고, 실제 값은 `v_risk_lookup` 뷰를
코드가 직접 조회한다.

### 4-5. 사전·제품 사실 (2개)

| 테이블 | 역할 | 주의 |
|---|---|---|
| `dict_entry` | 금지·허용·질병인접·완화금지 사전 | `exact_match` — 정확매칭만 위험도 하한 자격, 근사매칭은 인코더와 동등 취급 |
| `product_fact` | 인정 기능성 문구 | A 자격형 판정(D-59)의 근거 — `recognition_no`가 대조 키 |

### 4-6. 골든셋·학습 (2개)

`golden_sample`이 이 스키마에서 열이 가장 많은 테이블이다 — 라벨 축 4개, 측정 축 3개, 출처
추적 2개.

| 축 | 컬럼 | 근거 |
|---|---|:-:|
| 위법 유형(다중) | `violations violation_t[]` | |
| 3요소 | `three_elem JSONB` | |
| 불가 사유 | `infeasibility` A/B/C | D-59 |
| 위험도 순서형 | `risk` R0~R4 | |
| 측정 축 | `certainty`·`tense`·`sent_type` | D-74 |
| 주장 스팬 | `claim_spans JSONB` | D-30(주입 좌표에서 자동 생성) |
| 출처 추적 | `provenance`·`redistributable` | D-71 |

`ck_golden_injected_not_holdout` 제약 — 주입(합성)본이 평가 split에 들어가는 것을 DB가
거부한다. 평가는 실사례 홀드아웃으로만 해야 하는데, 이게 사람이 실수하기 가장 쉬운 지점이라
DB 레벨에서 막는다.

### 4-7. 세그먼트·재현성 (2개)

| 테이블 | 핵심 |
|---|---|
| `segment` | `member_count >= K_MIN` CHECK — k-익명성 미달 군집은 생성 자체가 차단 |
| `dataset_manifest` | `source_set_version` — 값이 바뀌면 재학습 트리거, `unmeasurable[]`에 30건 미만 유형 기록 |

## 5. 이 스키마의 범위 — 무엇이 빠져 있나

원 문서(DDL v1.1)가 명시한 대로, 이 18~19테이블은 **거버넌스·데이터 층**만 다룬다. 아래는
**별도 설계**로 관리된다:

- **인증**(USER·SESSION·`org_id`) — D-66·D-67·D-68, `app_account` 등 런타임 스키마 쪽
- **판정/생성 런타임** — `work_doc`·`copy_sentence`·`judgment`·`batch_run` 등 (`app/models.py`,
  D-103) — 위 18~19테이블과는 별개 스키마 파일(`db/schema.sql`)로 관리
- **셀러 프로필** — 미착수

## 6. 현재 적재 상태 (2026-09-17 실측)

🚨 **설계와 적재는 다른 축이다.** 위 스키마는 마이그레이션까지 끝나 있고 제약도 실측
검증됐지만, **이 기기 기준으로 실제 데이터 행 수는 0건**이다(`source`·`document`·`sentence`·
`chunk`·`chunk_embedding`·`dict_entry`·`sanction_rule`·`golden_sample` 전부). 원인은 스키마
결함이 아니라 §4의 원천 데이터(수집 데이터 보고서 참고)가 이 기기에 아직 적재되지 않은
것 — 설계 산출물로서는 완결됐고, 다음 단계는 **적재**다.
