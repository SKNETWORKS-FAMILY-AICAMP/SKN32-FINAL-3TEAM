# 3팀 회의록 2026-10-15

판정 로직이 기획서와 달리 사전 하나로만 확정·보류를 내고 있어, 사전·인코더 등 판정 코어를 병렬로 돌려 합산하는 로직부터 다시 만들고 그 뒤에 테스트하기로 했다. 배포는 인코더 확정 전이라도 웹페이지를 외부에서 접속할 수 있게 먼저 올린다.

## 1. 판정 로직

**결정: 판정 파이프라인 로직부터 기획 아키텍처대로 새로 완성하고, 그 뒤에 테스트해서 사전 보강과 로직 수정 중 무엇이 필요한지 가린다.** 잘못된 로직 위에서 다른 걸 고쳐 봐야 로직이 바로잡히면 결과가 달라지기 때문이다.

현재 상태 (한빈)

- 사전은 단어 매핑 방식이다. 사전은 개편이 필요하고, 로직은 짜던 중이었다.
- 원래는 사전과 인코더를 병렬로 돌릴 계획이었고, 위험도는 max(사전, 인코더)로 기획했다.
- 인코더가 근거 스팬을 달지 못한다는 걸 뒤늦게 알았다. 지금은 사전만 확정·보류를 정하고, 사전에서 걸러지면 그대로 끝난다.

지적 사항 (멘토)

- 판정 코어는 split·classify·retrieve·인코더 등 다섯 단계인데, retrieve와 인코더 쪽이 구현되지 않았다. 현재 로직이 기획서와 다르다.
- 원래 구상은 사전·학습된 인코더·코드 규칙이 각자 판정한 뒤 결과를 취합하는 것이다. 예: 2대 1이면 위반.
- 입력 문장을 두 번 훑을 필요는 없다. 텍스트 기반이라 결과가 같다.
- 사전이 부족한 게 문제인지 로직이 문제인지는 복합 결과를 봐야 알 수 있다.
- 원인 파악을 위해 백엔드 코드에 print를 넣어, 어떤 함수에서 어떤 데이터로 걸렸는지 콘솔에서 확인한다.
- 인코더의 역할은 위반 문장으로 학습해 "얼마나 위반에 가까운지" 확률을 내는 것이다. 어느 법 조항인지 못 짚고 DB 유사도만 찾는다면 쓸모가 있는지 다시 봐야 한다.

확인할 것: 질병 치료제 이름(당뇨 치료제 류)을 넣었을 때 의약품 오인으로 판정되는지 (한빈: 사전으로 나올 것).

## 2. 위험도 산정

**방향: 근거 스팬이 없어도 위험도를 낼 수 있게, 판정 코어 각 단계의 결과에 가중치를 줘서 합산한다.** 인코더를 위험도 100% 기준으로 쓰지 않는다.

- 현재 위험도는 행정처분 수위 기준(예: 의약품 오인은 더 높음)이다. 인코더로는 하한(최소 R1)만 정할 수 있고, R2·R3로 올리려면 근거가 필요한데 그게 없다.
- 멘토 제안: 판정 코어 다섯 단계를 병렬로 돌리고, 걸린 단계에 가중치를 준다. 단순하게 단계당 20%도 가능하며, 사전·인코더에 더 큰 가중치를 준다.

| 사전 | 인코더 | 위험도 |
| --- | --- | --- |
| 걸림 | 걸림 | 높음 |
| 안 걸림 | 일부 걸림 | 중간 |
| 통과 | 통과 | 0% |

## 3. 검수 화면 보강

**제안: 검수에서 문구가 다 잘려 나가면, 간단하게라도 대체 문구를 생성해서 보여준다.** 카피 생성 기능과는 별개다. 입력했는데 "다 잘렸다"만 나오면 사용자 입장에서 아쉽다.

- 예: '위암을 예방하는 양파즙'처럼 전부 걸리는 경우 → 생성으로 보강하는 로직 추가.

## 4. 카피 생성

**생성·후보 선정 로직은 그대로 간다.** 선정 이유가 인코더 점수로 명확하다는 평가다. 다만 버려지는 후보와 유형 기준을 화면에 더 보여주자는 의견이 나왔다.

현재 구조 (소라)

- LLM을 쓰므로 로그인이 필요하다. 품목을 고르고, 건기식은 기능성 여부를 체크한다.
- GPT가 20개를 생성한다. 사용 장면·대상·사실 등 각도를 나눠 서로 다른 내용이 나오게 했다.
- 위반 후보가 없는 것 중 "가까운 구간에서 각도가 다르고 글자가 덜 닮은 것"을 인코더 점수로 골라 3개를 올린다.
- '다른 문구 탐색하기'를 누르면 생성 엔진에서 새로 20개를 만든다. 그래서 다시 로딩이 걸린다.

의견 (멘토)

- 20개까지 필요한지, 로딩이 판정 로직 때문에 긴 건지 확인한다.
- 생성 쪽에도 로딩 표시를 넣는다.
- 보수·균형·공격이 무슨 기준인지 고객이 궁금해할 수 있다. 그래프를 키우고 점으로 탈락 후보를 보여주면 "이건 탈락될 만했네"가 보여 신뢰도가 오른다.
- 위·옆 탭 구성이 낯설다. 이제부터 UI/UX를 디테일하게 고도화한다.

## 5. 재생성 모델

**재생성은 학습 데이터가 너무 적다. 1만 건 정도는 있어야 한다.** 현재 학습된 모델과 완전히 새 데이터로만 학습한 모델을 나란히 비교해 차별점으로 써도 좋다는 의견이다.

## 6. 보류 비율과 목 항목

**보류 비율은 현재 91%다. 최대한 낮추면 61%, 안전하게는 83%까지 가능하다.** 위반 탐지율도 그 수준이라, 잡기는 잡지만 잡은 것이 모두 보류로 들어가는 상태다.

- 여기서 보류는 "시스템이 판정을 못 한다"가 아니라 "사용자가 확인해 보라"는 뜻이다.
- 전체 약 8천 건 중 목 항목이 달린 건 약 700건(약 10%)이다. 멘토 의견: 비율이 이 정도면 목 항목을 그렇게 중요하게 볼 필요는 없다.
- 위반·비위반 탐지는 잘 되지만, 위험도 확정에 목 항목이 필요했던 것이다 → 2절의 가중치 방식으로 대신한다.
- 멘토 질문: 인코더가 DB 벡터 유사도로 찾는다면, 가장 가까운 사례의 법 조항으로 근거를 알 수는 없는가?

## 7. AWS 배포

**목표: 인코더·sLLM 확정을 기다리지 말고, 껍데기만이라도 웹페이지를 외부에서 접속할 수 있게 먼저 올린다.** 세팅할 것이 은근히 많기 때문이다.

- 현재: 계정을 받아 인스턴스 생성과 기본 설정까지 마쳤다. 터미널 접속 가능.
- 다음: Ubuntu에 프로그램을 올려 외부 접속을 연다. 인코더와 sLLM은 그 뒤에 싣는다.
