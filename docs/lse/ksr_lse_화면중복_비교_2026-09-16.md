> 🚨 **이 문서는 병합을 하지 않는다.** 소라님이 부재중인 상태에서 파일별 완성도만
> 비교해 남겨 둔다 — 실제 병합·채택 판단은 소라님·한빈님 확인 후에 한다.

## 발견 경위

오늘(2026-09-16) `lse`에서 사용자 화면 4종(AI 광고 생성·매칭·마이페이지·도움말) +

**2026-09-13~14에 소라님이 이미 사용자 화면 9종을 구현해 둔 커밋 2개**가 있었고,
`lse`·`main` 어느 쪽에도 병합된 적이 없었다.

- `d38d85a` (2026-09-13 23:15) — 사용자 화면 9종 구현
- `ceac2de` (2026-09-14 00:17) — 검수 이력을 DB에 연결 (lse 쿼리 + ksr 화면)

**`ksr`는 현재 `lse`보다 70커밋 뒤처져 있다** — `app/contracts.py`·`app/models.py` 등
백엔드가 그 사이 크게 바뀌었을 수 있어, 화면 코드를 그대로 옮기면 안 맞을 자리가
있을 수 있다 (예: `compose.html`이 쓰는 `ComposeResponse.sections`).

## 파일별 완성도 비교

### `review.html`(ksr) vs `index.html`(lse) — 검수
- **ksr가 훨씬 완성도 높음.** 골든 픽스처 9건으로 위험도 카드·근거조문·원문 하이라이트
  (`evidence_span` 좌표로 3조각 자르기, P2-9 지키며 문자열 조립 안 함)까지 실제로 그린다.
- lse는 텍스트박스 하나 + 픽스처 링크 목록뿐 (오늘 "엔진 없이 폼 만들면 장식"이라 판단해
  의도적으로 최소로 둠 — 그런데 ksr는 같은 제약 안에서 훨씬 멀리 갔다).

### `generate.html` — 카피생성
- **ksr가 훨씬 완성도 높음.** 제품/키워드 입력, 리스크–소구력 프론티어 SVG 산점도
  (좌표는 `_frontier()`가 파이썬에서 계산 — 차트 라이브러리 없이), 후보 3안 카드까지 있음.
- lse는 픽스처 링크 목록뿐.

### `compose.html`(ksr) vs `draft-setup.html`+`draft-editor.html`(lse) — AI 광고 생성
- **ksr가 실제 섹션 골격을 서버에서 그린다** (`ComposeResponse.sections` 순서대로,
  "광고" 표시 섹션이 구조적으로 강제됨 — D-93·D-164).
- lse는 "아직 없다" 골격만.
- ⚠️ `ComposeResponse`가 70커밋 전 계약이라 지금 `app/contracts.py`와 다를 수 있음.

### `history.html` — 이력
- **양쪽 다 DB 연결됨, 구현 방식이 다르다.**
  - ksr: `Judgment` × `CopySentence` 조인으로 **실제 판정 문구 원문**까지 보여준다.
    lse는 이 조인이 없어서 **판정된 문구 자체를 화면에 안 보여준다** — 오늘 놓친 부분.
  - lse: verdict 필터·페이지네이션(20개 단위)·클릭 상세 토글(`?open_id=`)이 있다.
    ksr는 필터·페이지네이션이 없고, 상세는 "판정 결과 화면으로 이동하는 링크"로 대체.
  - **서로가 서로에게 없는 걸 갖고 있다** — 합치면 원문 표시 + 필터/페이지네이션 다 되는
    버전이 나올 수 있음.

### `help.html` — copylane 소개
- **거의 동일한 해법.** 둘 다 `?tab=faq` 쿼리스트링으로 JS 없이 탭을 서버가 고른다.
  독립적으로 같은 결론에 도달한 것으로 보인다.
- ksr는 "사용방법" 안에 실제 3단계 설명(검수→카피생성→매칭)까지 채워 넣음(§8 STEP).
  lse는 "아직 없다" placeholder만.

### `mypage.html`
- ksr: 프로필·광고 기본값·계정 탭 3개, 폼은 있으나 "저장 안 됨" 명시 + POST 라우트 존재.
- lse: "아직 없다" placeholder만.

### `_nav.html`(ksr) vs `_topnav.html`+`_sidebar.html`(lse) — nav 구조
- **두 사람이 완전히 독립적으로 같은 아키텍처 결론에 도달했다** — 상단 pill(구역) +
  왼쪽 세로 사이드바, JS 없이 서버가 현재 경로로 활성 상태를 고른다.
- 차이는 구현 위치뿐: ksr는 Jinja `{% set section = ... %}`로 템플릿 안에서 계산,
  lse는 Python `_render()` 헬퍼가 라우터에서 계산해 넘긴다.
- ksr 사이드바 라벨: "검수 및 카피생성"(work)·"copylane 소개"(about)·"AI 광고 생성"(adgen) —
  **lse가 오늘 붙인 "매칭" pill·"고객센터" 사이드바 하단 버튼이 ksr에는 없다**
  (애초에 그 화면들을 안 만들었으므로).
- 둘 다 `body { max-width: none }` 오버라이드가 필요한데, **lse는 오늘 이걸 놓쳤다** —
  지금 lse 사용자 화면은 `base.css`의 52rem 제한에 걸려 데스크톱에서도 좁게 보일 수 있다
  (직접 화면으로 확인 필요). ksr는 화면마다 `<style>`로 이미 풀어 뒀다.

### `landing.html`(ksr만 있음)
- 로그인 전 첫 화면. "지어낸 사용량 수치"를 프로토타입에서 일부러 뺀 것까지 확인함(D-147).

### lse에만 있는 것
- `matching.html`, `cs.html`, `segments.html`, `login.html`, `signup.html`,
  `_pagination.html`(history 필터·페이지네이션 공통 부품).

## 병합 시 검토가 필요한 지점 (제안 — 결정 아님)

1. **`/` 경로 충돌** — ksr는 `/`=홈, lse는 `/`=검수. 어느 쪽을 `/`로 할지부터 정해야 함.
2. **`app/routers/user.py` 전체가 사실상 다시 짜야 할 정도로 갈린다** — 함수명·라우트
   구조·헬퍼(`_frontier()`, `_render()`)가 다름.
3. **`ComposeResponse` 등 ksr가 의존하는 계약이 70커밋 전 버전** — 최신 `app/contracts.py`와
   맞춰봐야 함.
4. **history는 두 구현을 합치는 게 이득으로 보임** (ksr의 원문 조인 + lse의 필터/페이지네이션).
5. **nav는 어느 구현을 베이스로 할지만 정하면 됨** — 아키텍처는 이미 같은 결론.
6. lse가 오늘 만든 매칭/고객센터/로그인·가입 골격은 ksr에 없으므로 그대로 가져가면 됨.
