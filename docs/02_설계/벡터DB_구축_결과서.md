> 🔴 **GraphDB 는 쓰지 않는다** — 이 프로젝트에는 그래프 데이터베이스가 없다. 「그래프」는 판정 흐름(LangGraph)을 가리키고 저장소는 관계형 + 벡터다(§2). 조문 사이의 관계(법 → 조 → 항 → 호 → 목 · 별표)는 관계형 칸과 인용 좌표로 든다

> 앞 판 — [`데이터베이스_저장소_설계_2차.md`](데이터베이스_저장소_설계_2차.md) §4 · §5(09-28). 이 문서는 벡터 쪽을 따로 떼어 그 뒤에 바뀐 것까지 적는다

## 2. 왜 별도 벡터DB · GraphDB 를 두지 않았나

- **삭제가 따라가야 한다** — 원천을 지우면 그 원천에서 나온 청크와 벡터가 함께 사라져야 한다(데이터 거버넌스의 요구). 같은 인스턴스에 두면 외래키 캐스케이드가 그대로 걸린다. 벡터DB 를 따로 두면 두 저장소의 삭제를 맞추는 코드가 생긴다(D-41)
- **검색 질의가 거버넌스 조건을 든다** — 모든 검색 질의가 「이 원천을 이 용도로 써도 되는가」의 조인을 든다(`tests/test_retrieve.py` 가 본다). 한 인스턴스라 한 SQL 로 된다
- **GraphDB 가 풀 문제가 없다** — 조문의 구조는 깊이가 정해진 나무(조 · 항 · 호 · 목)이고 판정에 필요한 것은 「이 문장의 근거가 어느 좌표인가」다. 경로 탐색 질의가 없다
- 대가 — 청크가 수만 단위를 넘으면 전용 벡터DB 보다 느릴 수 있다. 지금 규모(수천)에서는 해당하지 않는다

## 3. 저장 구조

| 표 | 무엇 | 요점 |
|---|---|---|
| `chunk` | 조문 청크 | 인용 단위 `text` 와 검색 문맥 `context` 를 갈랐다 · 조 · 항 · 호 좌표 · 쪼갠 조각 번호 · 법 축 `law` · 원천 조각으로의 외래키 |
| `chunk_embedding` | 벡터 | `embedding vector(1024)` · `model_id` · `input_sha256` — 청크 삭제에 캐스케이드 |
| `chunk.tsv` | 어휘 검색용 생성 칸 | GIN 인덱스 |

- **임베딩 입력은 `context + text`** 다(`scripts/embed.py` `embed_input()`). `context` 는 조 제목 + 항 본문이고, 별표는 별표 제목 + 상위 항목이다 — 짧은 목록 청크가 벡터 상위를 차지해서 바꿨다(09-24)
- **모델 이름을 코드에 상수로 두지 않는다** — 질의를 인코딩할 때 `chunk_embedding.model_id` 를 DB 에서 읽어 저장된 벡터를 만든 그 모델을 쓴다. 질의 벡터와 저장 벡터가 다른 모델이면 거리는 뜻이 없는 수가 된다
- **입력 해시를 벡터마다 적는다** — 재임베딩을 중간에 멈추면 두 벡터 공간이 한 표에 섞인다. 검색 코드가 「일부만 비어 있음」을 섞임으로 보고 막는다
- **차원이 한 곳에만 있다** — 스키마 · 문서 · 마이그레이션의 1024 가 같은지 게이트가 본다
- **법 축** — 청크의 법은 법 ID 로 정한다(이름의 낱말로 정하지 않는다). 값은 넷이다(D-271)

## 5. 검색 구조

```
질의 문장 ─┬─ 벡터 갈래   KURE-v1 임베딩 → 코사인 거리 순
           └─ 어휘 갈래   조사 · 어미를 깎은 검색어 → tsv 일치 순
                  │
     (화면 검색)  └─ 순위 융합(RRF) → 상위 5
     (판정 그래프) └─ 법마다 폭만큼 받음 → 법별 노드가 자기 법만 거른 뒤 융합
```

| 설정 | 값 | 출처 |
|---|--:|---|
| 후보 폭 `pool` | 50 | 탐침으로 연다 — 바꾸는 것은 결정이다 |
| 상위 `top_k` | 5 | `[설계]` 기획서 5-6 · 법별 노드에서 법마다 쓰는 것은 `[임의]`(받을 개수는 판정 대기 — D-291 ⬜) |
| 융합 상수 `rrf_k` | 60 | `[문헌]` |

- **순위는 섞고 점수는 안 섞는다**(D-193) — 벡터 거리와 글자 일치 점수를 더하려면 근거 없는 가중치가 필요하다. 순위 융합은 순위만 쓰므로 가중치가 없다. 뒤집은 근거는 측정이다 — 벡터 단독으로는 정답 조문이 6 위 · 19 위 · 50 위 밖이었다(09-12)
- **넓게 한 번 찾고 법별로 거른다**(D-291) — 종전에는 전역 상위 5 를 세 법이 나눠 썼다. 지금은 법마다 폭만큼 받고, 갈래마다 **먼저 거른 뒤** 섞는다(섞은 뒤 거르면 순위가 부풀었다). 법 필터로 따로 찾은 것과 후보가 같다 — 124 / 124(원장 09-25 ㊲ · ㊳ · 잰 날 09-28 · 질의 31 × 법 범위)
- 🚨 `[임의]` 값이 판정 경로에 하나 있다 — 법별 노드가 문장마다 받는 근거 수(5). 지금 판정은 사전 적중으로 서고 검색 결과는 함께 붙는 근거라, 이 값이 확정 여부를 바꾸지는 않는다(붙는 근거 조문이 달라진다)

### 6-2. 응답시간 (원장 10-02 ⑨ · 🚨 **클론 A** · CPU · 문장 100 개 · 예열 제외)

| 검색 한 번의 안쪽 | p50 | p95 | 비중(p50) |
|---|--:|--:|--:|
| 임베딩(한 문장) | 246.8 ms | 378.5 ms | 73.4% |
| 벡터 질의 | 67.8 ms | 89.2 ms | 20.2% |
| 어휘 갈래 | 4.7 ms | 84.0 ms | 1.4% |

- 검색 시간의 약 3/4 이 **임베딩 계산**이다. 문장 20 개를 한 번에 묶어도 12% 만 준다 — 호출 횟수가 아니라 계산량이다
- 벡터 질의는 문장당 68 ms 다(인덱스 없음 · 순차 스캔). 원고 20 문장이면 벡터 질의만 약 1.4 초다
- 판정 전체의 91 ~ 98% 가 검색이다(원장 10-02 ⑧) — 원고 10 문장 안팎에서 목표(p95 3 초)를 넘는다
- 🚨 개발 기기의 수다. 배포 기기 · 동시 요청 · 인코더와 리랭커가 붙은 뒤는 재지 않았다
