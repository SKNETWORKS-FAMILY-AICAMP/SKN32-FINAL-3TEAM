## 2-1. 이음매 설계 — 버그는 기능 안이 아니라 **경계**에서 난다

### 왜 기능이 아니라 이음매인가

[`00_병렬작업_계약.md`](../00_병렬작업_계약.md) §1 이 경계 아홉을 표로 세어 뒀고, **여덟은 끊었는데 #5 하나가 🔴 맨 `dict`** 입니다. 그 문서 자신의 진단이 이겁니다 — *「경계가 `dict` 다. 그리고 `dict` 경계는 오류를 안 낸다.」* **사흘에 세 번 밟았다**고 적혀 있습니다.

⛔ **16건을 미리 다 설계하지 않는 이유**는 D-134 가 실물입니다 — Django 이식을 「이식 순서 ①~⑦」까지 설계해 놓고 **D-135 로 통째로 되돌렸습니다.** 설계가 틀려서가 아니라 **팀 합의라는 입력이 뒤에 왔기 때문**입니다. 층 3(⑦⑧⑨)은 지금 설계하면 재지 않은 수 위에 서고, 그건 `[임의]` 를 판정 경로에 넣는 일입니다 (D-201).

★ **그래서 여기서 설계하는 것은 경계 하나와 항목 넷입니다** — 경계 #5, 그리고 층 0·1 의 ①②③④. 전부 **재지 않고도 설계할 수 있는** 것들입니다.

### A. 🔴 먼저 — **설계 구멍 하나를 찾았습니다**

`retrieve` 노드가 **검색 결과를 둘 자리가 상태에 없습니다.**

| 확인한 것 | |
|---|---|
| `SentenceJudgment.evidence` | ✅ 있습니다 (`list[EvidenceArticle]`) |
| `JudgeState` 의 중간 키 | 🔴 **없습니다** — `sents` 다음이 바로 `sentences` 입니다 · 🔄 ✅ **09-13 `evidence` 누적 키가 섰다**(`REDUCER_KEYS` 에 있다) |
| `sentences` 의 리듀서 | `Annotated[list[...], operator.add]` — **append 전용** |

⛔ **그래서 「retrieve 가 `sentences` 를 미리 만들고 judge 가 채운다」가 안 됩니다.**

1. `SentenceJudgment` 는 `verdict` 가 **필수**인데 retrieve 시점엔 모릅니다
2. `verdict=unjudged` 로 만들어 넣으면 — 리듀서가 `operator.add` 라 **judge 가 덮어쓰지 못하고 뒤에 붙입니다.** 문장 수가 **두 배**가 됩니다
3. 🚨 **오류가 안 납니다.** 계약 검증도 통과합니다 — `unjudged` 도 유효한 `Verdict` 이니까요. D-124 ③이 *「리듀서 키를 따로 본다」*고 적어 둔 그 사고입니다

**같은 자리에 하나 더** — 노드 docstring 이 *「`search()` 가 내는 `state` 를 버리지 않는다. `hold` 로 보내는 근거가 `state.vector` 다」*라 적었는데 **`SearchState` 를 담을 키도 없습니다.**

#### 결정 초안 — 중간 키를 하나 세운다

    # app/graph.py  🔄 contracts.py 가 아니다 — 아래 「어디에 두나」 참조
    class SentEvidence(BaseModel):
        # retrieve 가 낸 것 — judge 가 sent_id 로 짝짓는다.
        # 🚨 EvidenceArticle 과 다른 물건이다 — 이쪽은 아직 판정에 안 붙은 후보다.
        sent_id: str
        articles: list[EvidenceArticle] = Field(default_factory=list)
        # 🔴 검색이 무엇을 할 수 있었나 — retrieve.SearchState 를 그대로 옮긴다
        vector: str          # "ok" 이거나 못 돈 이유
        lexical: str         # LEXICAL_OK | LEXICAL_NO_TERMS
        pool: int
        pool_vector: int
        pool_lexical: int
        # 🔴 part_total > 1 이면 이 근거는 조문의 「일부」다 (0011 · D-199)
        partial: bool = False

    # app/graph.py — JudgeState
    evidence: Annotated[list[SentEvidence], operator.add]    # 🔴 누적 키

> 🔄 **실제로 선 모양은 다르다** (2026-09-21 대조 · `app/graph.py` `SentEvidence`) — `BaseModel` 이 아니라 얼린 `dataclass` 이고,
> `vector`·`lexical` 은 **bool** 로 접혔다(이유 문자열은 노드에서 안 나른다 — `/search` 의 `SearchState` 에만 있다) ·
> `pool` 은 두 갈래 후보 수의 합 · `pool_vector`·`pool_lexical`·`partial` 칸은 없다(일부 조문은 `EvidenceArticle.chunk_id` 로 따라간다).

🔄 **어디에 두나 — `contracts.py` 가 아니라 `graph.py` 입니다.**
`contracts.py` 는 **4명이 보고 붙는 계약**이고 등급 1 **잠금**입니다. 그런데 `SentEvidence` 는
**그래프 내부 상태**라 BFF 도 화면도 안 봅니다. 계약에 두면 **네 사람이 읽어야 할 심볼이 하나 늘고
쓰는 사람은 없습니다.** `graph.py` 는 팀장 **기본 담당**(등급 2)이라 잠금 판정도 필요 없습니다.
★ 그래서 이 항목은 **⬜ 판정에서 빠집니다** — 아래 G 표에서 뺐습니다.

⛔ **`REDUCER_KEYS` 에 `"evidence"` 를 같이 넣습니다** — 게이트가 그 표를 돕니다. 넣는 것을 잊으면 **리듀서 없는 누적 키**가 되어 정확히 위 2번 사고가 납니다.

| 대안 | 왜 안 골랐나 |
|---|---|
| retrieve 와 judge 를 **한 노드**로 | 계측(`timings`)이 뭉쳐 「검색이 느린가 판정이 느린가」를 못 가릅니다 (D-77 L3) |
| `dict[sent_id, ...]` 를 상태에 | `operator.add` 가 dict 에 안 먹습니다. 커스텀 리듀서는 **게이트가 볼 표가 하나 더** 늡니다 |
| 문장마다 서브그래프 (Send) | 팬아웃은 진입점 B 에 이미 있습니다(`keywords`·`adapted`). A 에 지금 넣으면 **팬아웃 규약이 두 벌**이 됩니다 |

### E. 층 1 ③ — `sanction_rule` 적재기

#### 🔴 스키마를 읽다 하나 나왔습니다 — **2인 확인이 우회됩니다**

    CONSTRAINT ck_sanction_four_eyes
      CHECK (verified_by IS NULL OR reviewed_by IS NULL OR verified_by <> reviewed_by)

⛔ **둘 다 `NULL` 이면 통과합니다.** 적재기가 두 칸을 안 채우고 넣으면 **2인 확인 없이 제재 규칙이 들어갑니다.** 병합 셀 파싱이라 2인 대조를 걸어 둔 자리인데(스키마 주석이 그렇게 적었습니다), CHECK 은 *「둘이 같으면 안 된다」*만 말하고 *「둘이 있어야 한다」*는 말하지 않습니다 — **D-170 「통과만 하는 게이트」** 입니다.

> ✅ **2026-09-13 (b) 로 섰다** (2026-09-21 대조) — 0013 이 `v_risk_lookup` 을 `verified_by`·`reviewed_by` 가 **둘 다 있는 행만** 보이게 다시 만들었고,
> 아래 「틀릴 수 있는 지점」의 짝으로 `doctor` 가 **2인 확인 대기 행 수**를 센다(`scripts/doctor.py`).
>
> ⬜ **판정 초안** — 셋 중 하나입니다.
> **(a)** CHECK 을 `verified_by IS NOT NULL AND reviewed_by IS NOT NULL AND <>` 로 조인다 → 마이그레이션 0013. **적재기가 2인 확인 전에는 아무것도 못 넣습니다**
> **(b)** 뷰(`v_risk_lookup`)에서 `verified_by IS NOT NULL` 을 걸러 낸다 → 적재는 되고 **읽히지 않습니다**
> **(c)** 그대로 두고 적재기가 지킨다 → **사람이 지키는 규칙**입니다 (D-117 이 안 된다고 적은 것)
>
> ★ **권고는 (b)** 입니다. (a)는 「파싱해 넣어 두고 사람이 확인」이라는 순서 자체를 막습니다. (b)는 **넣되 안 보이게** 해서 그 순서를 살리고, `v_risk_lookup` 이 0행을 내는 것이 **「확인이 안 끝났다」를 그대로 말합니다.**
> ⛔ **내가 틀릴 수 있는 지점** — (b)는 표에 미확인 행이 쌓이는 것을 허용합니다. 그 행을 세는 자리가 없으면 「확인 대기 몇 건인가」를 아무도 모릅니다. (b)를 고르면 `doctor` 에 그 수를 세는 검사가 같이 와야 합니다.

| 그 밖 | 설계 |
|---|---|
| **부분 실행** | 전량 실행인데 DB 가 선언보다 많으면 **실패로 끝냅니다** (D-196) |
| **`risk_level` 매핑** | 별표의 처분(시정명령 / 업무정지 N일 / 과징금)을 `R0~R4` 로 옮기는 규칙에 **출처 태그**를 답니다. `[임의]` 면 보고에 올립니다 (D-201) |
| **선언과 대조** | 등재 표에 없는 `fragment_id` 가 DB 에 있으면 멈춥니다 (D-187) |
| **범위** | 광고와 무관한 제재는 **적재하지 않습니다** (D-183) |

✅ **완료 판정** — `v_risk_lookup` 이 0행이 아니다 · 적재 뒤 DB 가 선언과 같다 · **2인 확인 안 된 행은 뷰에 안 나온다**.
