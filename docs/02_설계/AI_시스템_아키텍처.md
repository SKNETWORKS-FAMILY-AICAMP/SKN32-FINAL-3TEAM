## 1. 한 장 요약

| 물음 | 답 |
|---|---|
| 어떤 꼴의 멀티 에이전트인가 | **파이프라인형** — 도구 호출형(ReAct · MCP)이 아니다. 외부 도구 호출이 0 건이라 붙이지 않았다(D-11 · 기획서 3-6) |
| 에이전트에 해당하는 것 | 법마다 하나씩 선 **법별 판정 노드 셋**(표시광고법 · 식품표시광고법 · 화장품법)과 그 앞뒤의 공통 노드 |
| 협업 방식 | **팬아웃 – 팬인** — 검색은 한 번 하고, 품목에 맞는 법 노드로 동시에 보낸 뒤 한 곳에서 모은다(D-267) |
| 그래프 수 | 코어 서브그래프 1 + 진입점 그래프 3(검수 · 생성 · 조립) — 판정 코어는 하나다(D-266) |
| 지금 도는 것 | **검수 경로 전체** — 사전 적중 기반 규칙 판정으로 끝까지 돈다 |
| 지금 비어 있는 것 | 인코더 노드 · 문서 규칙 노드 · 생성 경로의 노드 여섯(§5) |
| 틀 | LangGraph 1.2.11 · FastAPI · PostgreSQL 16 + pgvector(사실원장 「스택 핀」) |

## 2. 그래프 셋과 코어 하나

```
core     (서브그래프)  split → classify → retrieve → match_dict → encode
                       → [법별 팬아웃: law_ftc · law_food · law_cosmetic]
                       → merge_laws → judge → assess_risk → premise_branches → doc_rules
review   (진입점 A)   core → route_review → certificate · guidance · hold · passed     ← 루프 없음
generate (진입점 B)   keyword_screen → assemble → claim_ledger → rejudge → (루프) → frontier · search_failed
compose  (진입점 C)   상태만 정의 — 범위 밖
```

- **코어를 하나만 두는 까닭** — 검수가 내는 판정과 생성이 자기 후보를 다시 판정할 때의 판정이 같은 코드여야 한다. 생성 경로의 `rejudge` 는 판정을 새로 쓰지 않고 코어를 부른다(D-266)
- **검수 그래프에 루프가 없는 까닭** — 검수는 문구를 만들지 않는다(D-265). 종전에는 실증형 위반을 재생성 루프로 보냈는데 그 가지를 검수에서 걷어 냈다
- **코어를 노드로 끼우는 방식** — 컴파일한 서브그래프를 그대로 끼우면 부모의 누적 키가 두 번 쌓였다(실측). 그래서 넣을 키 · 꺼낼 키를 표로 든 함수 노드가 코어를 부른다(`app/graph.py` 머리말)

## 3. 코어 노드 — 무엇을 하고 어디까지 구현됐나

| 순서 | 노드 | 하는 일 | 상태 |
|:-:|---|---|:-:|
| 1 | `split` | 원고를 문장으로 나눈다(`app/sentsplit.py`) | ✅ · 분할 정확도는 미측정(정답 셋이 없다) |
| 2 | `classify` | 품목을 정한다 — 주어지면 그대로, 없으면 미확정 | ✅ 주어진 값만 · 문구로 판별하는 것은 없다 |
| 3 | `retrieve` | 조문 검색 — 벡터와 어휘 두 갈래를 법마다 폭만큼 넓게 **한 번** 받는다(D-291) | ✅ |
| 4 | `match_dict` | 사전 매칭 — 금지 표현 사전의 적중과 원문 좌표를 낸다(`app/dictmatch.py`) | ✅ |
| 5 | `encode` | 인코더 — 문장마다 위반 유형 후보와 신뢰도 | ⬜ **빈 노드** |
| 6 | `law_ftc` · `law_food` · `law_cosmetic` | **법별 노드** — 자기 법의 검색 결과와 사전 적중만 거른다 | ✅ |
| 7 | `merge_laws` | 법별 결과를 문장 단위로 모은다 | ✅ |
| 8 | `judge` | 문장 판정 — 확정 · 보류 · 근거 없음 · 미판정(§4) | ✅ 규칙판 |
| 9 | `assess_risk` | 위험도 하한 — 제재표에서 읽는다 · 두 법이 걸리면 높은 쪽(D-272) | ✅ |
| 10 | `premise_branches` | 품목 분기 — 전제마다의 판정을 미리 계산한다(§6) | ✅ |
| 11 | `doc_rules` | 문서 단위 규칙(의무 문구 유무 등) | ⬜ 빈 노드 |

- 🔴 **빈 노드는 비어 있는 것이지 값을 지어내지 않는다** — 자리에 무엇이 올지 적어 두고 상태를 그대로 넘긴다. 그럴듯한 값을 넣으면 그 값이 화면으로 흘러가고, 진짜가 붙을 때 무엇이 바뀌었는지 알 수 없다
- 인코더 모듈(`app/encoder.py`)은 저장소에 있으나 그래프의 `encode` 노드에 배선되지 않았다. 3차 재학습 결과를 받은 뒤 배선한다

### 3-1. 법별 팬아웃 — 라우팅 규칙

| 품목 | 보내는 법 노드 |
|---|---|
| 식품 · 건강기능식품 | 표시광고법 + 식품표시광고법 |
| 화장품 | 표시광고법 + 화장품법 |
| 미확정 | 셋 다 |
| 그 밖(의료기기 · 의약외품 등 전용법 품목) | 표시광고법만 — 통과를 내지 않고 「미검수 법」 고지를 단다(D-271) |

- 검색과 인코더는 팬아웃 **앞에서 한 번** 돈다. 법마다 다시 부르면 검색 비용이 법 수만큼 는다(D-267)
- 건강기능식품법은 노드가 없다 — 참고 전용이라 위반 근거로 보내지 않는다(D-271)
- 법별 노드 ↔ 법 축의 대응표가 어긋나면 모듈을 읽어 들일 때 멈춘다 — 법이 늘었는데 한쪽만 고치면 그 법은 근거 없이 판정되기 때문이다(D-220)

## 4. 판정 — 인코더가 붙기 전의 규칙

문장 하나의 판정은 넷 중 하나다.

| 판정 | 언제 |
|---|---|
| 미판정 | 사전을 훑지 못했다 — 못 본 것을 본 것처럼 말하지 않는다 |
| **확정(위반)** | 단독 판정 자격이 있는 사전 항목이 이 법의 인용으로 걸렸다 · 근거 조문과 뺄 구간이 붙는다 |
| 근거 없음 | 유형은 잡았는데 인용 좌표를 세우지 못했다(D-224) |
| **보류** | 그 밖의 전부 — 사전의 침묵은 「특이사항 없음」이 아니다(D-269) |

- 인코더 전의 정상 출력은 「사전 적중 = 위반 확정」과 「보류」 둘뿐이다. 사전에 안 걸린 문장을 통과로 내지 않기로 한 판정이다(D-269) — 그래서 지금 평가의 종착은 거의 전부 보류다(테스트 결과 보고서 §3)
- 확정 위반에는 **불가 사유**가 붙는다 — A 자격형(인정 절차를 밟으면 가능) · B 실증형(실증 자료가 있으면 가능) · C 절대형(길이 없다). 「불가합니다」 한 가지로 답하지 않으려는 구분이다(D-59)
- 🚨 **문장이 주장인지 아닌지는 가리지 못한다** — 그것은 인코더의 몫이다(D-275). 의무 고지문이나 부정문에 금지 낱말이 있으면 지금은 걸린다

## 5. 종착 — 검수 그래프

우선순위 **보류 > 증명서 > 지시 > 통과**(D-268 · D-125).

| 종착 | 언제 | 사용자가 받는 것 | 상태 |
|---|---|---|:-:|
| `hold` 보류 | 한 문장이라도 확정이 아니다 · 위험도가 없는 확정 위반이 있다 | 문장별 판정 · 보류 사유 · 분기 | ✅ |
| `certificate` 증명서 | 전 문장 확정이고 자격형 · 절대형이 있다 | 「합법화 불가」 사유 설명 · 자격형이면 자격 안내 | ✅ 10-06 조립기(D-320) |
| `guidance` 지시 | 전 문장 확정이고 실증형만 있다 | 뺄 구간 · 필요한 실증 자료 | ⬜ 실증 분기 재료가 없어 보류로 내려간다 |
| `passed` 통과 | 전 문장 확정이고 위험도가 가장 낮다 | 통과 | ✅ 규칙은 있다 · 인코더 전에는 나오지 않는다 |

- **증명서 사유 문안**은 (법, 위반 유형, 불가 사유)를 열쇠로 꺼낸다 — 전제가 법을 정하므로 같은 유형이라도 식품과 화장품의 글이 다르다(D-320 · `app/reasons.py` · 승인된 일곱 줄). 열쇠에 없는 조합은 글이 없고 증명서도 없다(보류)
- ⚠️ **판정 대기** — 인코더가 붙기 전의 증명서를 그대로 낼지 · 고지를 붙일지 · 끌지(D-320 상태 줄 · 원장 10-03 ㊿-40 보충 1)
- 생성 그래프의 종착(프론티어 · 탐색 실패)은 계약과 라우터만 있다. 노드 여섯(`keyword_screen` · `assemble` · `claim_ledger` · `rejudge` · `frontier` · `search_failed`)은 빈 노드다 — 페르소나 · 세그먼트 · sLLM 은 설계만 하기로 했다(D-270)

## 6. 품목 분기 — 같은 문구가 전제에 따라 갈린다

같은 문구가 일반식품이면 위반이고 인정받은 건강기능식품이면 아닐 수 있다. 품목을 모를 때 한 가지 답을 지어내지 않고 **전제마다의 판정을 처음에 전부 계산해** 응답에 싣는다(D-263 · D-319).

| 상황 | 기록되는 판정 | 분기 |
|---|---|---|
| 품목 미확정 · 모든 전제에서 같은 위반 | 확정 | 전제 여섯 |
| 품목 미확정 · 전제마다 다름 | 보류(`cat_unknown`) | 전제 여섯 |
| 품목이 식품 · 건강기능식품이고 전제마다 다름 | 보류(`premise_unknown`) | 그 품목의 전제 둘 |
| 품목이 주어지고 전제마다 같음 | 종전 그대로 | 없음 |

- 전제는 여섯이고(`app/premise.py`) 전제마다 **기준 문안** 한 줄이 붙는다 — 사용자가 그 글을 읽고 자기 제품의 전제를 고른다. 문안은 승인받은 글자만 코드에 들어간다(승인본 `docs/ohb/기준문안_초안_2026-10-02.md` §10)
- 분기는 다시 판정하지 않는다 — 화면이 미리 계산된 것 중에서 고른다
- 전제가 판정하지 못하는 자리는 통과가 아니라 보류다 — 「서지 않는다」와 「통과」는 다르다(D-319 집행 주석)
- 품목 미확정에는 통과 표시가 없다

## 7. 상태 — 그래프가 나르는 것

| 상태 | 담는 것 | 그래프 |
|---|---|---|
| `CoreState` | 입력(원고 · 제품 정보) · 문장 · 보낼 법 · 누적(검색 근거 · 사전 적중 · 법별 결과 · 문장 판정 · 노드별 시간) · 품목 분기 | 코어 |
| `ReviewState` | 코어 + 종착 · 증명서 — 재생성 키가 없다 | 검수 |
| `GenerateState` | 세그먼트 · 제품 정보 · 키워드 선별 · 후보 · 시도 횟수 · 거부 사유 · 매체 프로파일 · 각색본 | 생성 |
| `ComposeState` | 광고 종류 · 지면 구역 | 조립(그래프 없음 · 범위 밖) |

- 누적 키의 표는 한 곳이다(`STATE_REDUCERS`) — 팬아웃한 노드들이 같은 키에 쓰므로 리듀서가 없으면 마지막 것만 남는다
- **계측** — 노드마다 걸린 시간을 상태에 쌓는다(`timings`). 외부 추적 도구를 쓰지 않아(D-43) 이 칸이 단계별 응답시간의 유일한 경로다
- 응답 계약은 `JudgeResponse`(`app/contracts.py`) — 계약이 조용히 바뀌면 게이트가 잡는다(`tests/test_contract_surface.py`)

## 8. 설계 원칙이 구조에 박힌 자리

| 원칙 | 구조에서의 모양 |
|---|---|
| 없음이 성공으로 집계되지 않는다(D-220) | 사전을 못 훑으면 미판정 · 검색을 못 하면 그 사실을 값으로 남김 · 문안이 없으면 증명서가 아니라 보류 |
| 사전의 침묵은 통과가 아니다(D-269) | 판정의 기본값이 보류 |
| 위반을 확정하면 근거 조문이 붙는다(D-224) | 계약의 검증기가 근거 없는 확정을 거부한다 |
| 검수는 문구를 만들지 않는다(D-265) | 검수 그래프에 루프가 없고 후보 목록은 늘 비어 있다 |
| 같은 로직은 한 곳(D-99) | 검색 코어 하나 · 사전 매칭 하나 · 채점 규칙 하나를 화면 · 그래프 · 평가 도구가 같이 부른다 |
| 판정 문구는 승인받은 글자만 | 기준 문안 · 사유 문안이 문서의 승인본과 글자가 같은지 게이트가 본다 |

## 9. 응답시간 — 구조가 정하는 것

- 판정 목표는 p95 3 초 미만이다(D-77). **원고 10 문장 안팎에서 넘는다** — 문장 10 개 p95 4,350 ms · 20 개 6,547 ms(원장 10-02 ⑧ · 클론 A · 인코더 · 리랭커 없음 · 품목 미확정)
- 시간의 91 ~ 98% 가 `retrieve` 이고 문장 수에 비례한다. 법별 노드 셋의 합은 1% 안팎이다 — **분기를 미리 계산하는 비용은 원인이 아니다**
- 검색 한 번의 73% 가 임베딩 계산이다(원장 10-02 ⑨ · 클론 A · CPU). 줄이는 방법은 판정 대기다
- 🚨 인코더와 리랭커가 붙기 전의 가장 가벼운 상태의 수이고 개발 기기의 수다 — 배포 기기에서는 재지 않았다

## 10. 남은 것

1. **인코더 배선** — 3차 재학습 결과를 받은 뒤 `encode` 노드에 붙인다. 확정 클래스는 8종이다(D-321)
