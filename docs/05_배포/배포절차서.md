### 4-0. 서버에 처음 들어갈 때 — 스크립트를 먼저 올린다

`preflight`(1단계)는 저장소를 받기(`fetch` · 2단계) **전에** 돕니다. 그래서 첫 접속 때는 스크립트를 SFTP 로 올립니다.

1. 내 PC 의 `C:\SKN32-FINAL-3TEAM\docs\ssm\배포\` 에서 `deploy_server.sh` · `load_test.py` · `Caddyfile` 셋을
   MobaXterm 왼쪽 SFTP 패널의 `/home/ubuntu/` 로 끌어다 놓는다
2. 서버에서 `chmod +x ~/deploy_server.sh` · Windows 줄바꿈이 섞였으면 `sed -i 's/\r$//' ~/deploy_server.sh`
3. 이후 스크립트를 고쳤으면 같은 방법으로 덮어쓴다 — 2단계 뒤에는 저장소 안의 사본(`~/SKN32-FINAL-3TEAM/docs/ssm/배포/`)과 같은지 `diff` 로 본다

### 4-1. 파생물 묶음 — 내 PC 에서 만들어 올린다 (요청 ② (가))

서버의 `data-sync` 는 **`<DATA_STORE>/copylane-derived/objects/<sha 앞 2자>/<sha256>`** 구조만 읽습니다(`scripts/data_store.py`). 파일 이름이 곧 내용의 해시라서, 공유 저장소 폴더를 통째로 올리거나 이름을 바꾸면 받지 못합니다. `pack_store.py` 가 **배포 커밋의 원장이 가리키는 객체만** 그 구조로 골라 줍니다.

```bat
:: 내 PC — Google Drive for desktop 이 켜져 있고 .env 의 DATA_STORE 가 공유 저장소를 가리킬 때
cd C:\SKN32-FINAL-3TEAM
git fetch origin && git checkout <배포 커밋>
uv run python docs\ssm\배포\pack_store.py --out C:\CopyLane_upload --check   :: 무엇이 갈지 · 부류별 개수 · 크기
uv run python docs\ssm\배포\pack_store.py --out C:\CopyLane_upload
git checkout ssm                                                              :: 작업 브랜치로 돌아온다
```

| 정상 결과 | 다음 |
|---|---|
| 부류별(원천 · 표본 · 생성물) 개수와 MB · `[OK] … 복사 N` | MobaXterm SFTP 로 `C:\CopyLane_upload\copylane-derived` 폴더째 서버 `/home/ubuntu/CopyLane_store/` 아래에 올린다 → 서버 `.env` 에 `DATA_STORE=/home/ubuntu/CopyLane_store` |

- 🚨 **② 3번(재배포 불가 행을 실을지) 판정 전에는 올리지 않습니다.** `--check` 출력(부류별 개수 · 크기)을 판정 자료로 팀장에게 보냅니다.
- `[중단] 공유 저장소에 없거나 크기가 다른 객체` — 드라이브 동기화가 덜 끝났거나 정본이 아직 `data-publish` 를 안 했습니다. 기다리거나 팀장에게 요청합니다.
- 서버 커밋을 바꾸면 이 묶음도 그 커밋으로 다시 만듭니다(이미 있는 객체는 건너뜁니다).
- 올린 뒤 `C:\CopyLane_upload` 는 지웁니다.
- 인코더 · 어댑터 폴더는 이 묶음과 별개입니다 — `models/<판 이름>/` 째로 올립니다(§4 표).

### 4-2. DB 비밀번호 (컨테이너 DB)

저장소의 compose 와 `.env.example` 은 개발용 기본 비밀번호(`copylane`)를 씁니다. 배포 서버에서는 `env` 단계가 자동으로 바꿉니다.

- `bash deploy_server.sh env` → `.env` 에 `POSTGRES_PASSWORD`(무작위 48자 16진)와 그 비밀번호를 담은 `DATABASE_URL` 을 함께 적습니다. compose 는 같은 폴더의 `.env` 에서 `POSTGRES_PASSWORD` 를 읽습니다.
- 🚨 **첫 `db-up` 전에만 뜻이 있습니다.** DB 볼륨이 한 번 만들어지면 그때 비밀번호로 굳습니다. 이미 만들어진 볼륨이 있고 적재 전이면 `cd ~/SKN32-FINAL-3TEAM && docker compose down -v` 로 지우고 `data` 를 다시 돕니다. **적재 뒤에는 지우지 않습니다** — 가입 계정이 사라집니다.
- `DATABASE_URL` 이 아직 `copylane:copylane@` 이면 `data` 단계가 멈춥니다.

### 4-3. RDS 만들기 — 요청 ① 이 승인됐을 때만

> ⬜ 콘솔 메뉴 이름은 2026-10 화면 기준 일반 절차이고 이 계정에서 해 본 적이 없습니다. 생성 화면의 **월 예상 비용**을 작업기록에 적습니다.

| # | 위치 | 값 |
|:-:|---|---|
| 1 | RDS → 데이터베이스 생성 → 표준 생성 | 엔진 **PostgreSQL 16.x** (가장 최근 마이너) |
| 2 | 템플릿 | 프리 티어가 아니면 「개발/테스트」 · **단일 AZ** |

| 4 | 인스턴스 · 스토리지 | `db.t4g.small` · gp3 20GB · 스토리지 자동 조정 끔 |

#### 5-1. 검색 임베딩 캐시 — 🆕 2026-10-15 (D-344 ⑦ · 미정 항목 「배포 기기의 캐시 준비」)

판정 경로는 이제 검색 임베딩(KURE-v1)을 **이 기기의 캐시에서만** 올립니다(`app/settings.py` `load_kwargs(local_only=True)`). 허브로는 나가지 않습니다(D-77 L4 「판정 경로 외부 요청 0」).
🚨 캐시가 없으면 **오류가 나지 않습니다** — 앱은 뜨고 판정도 같지만, 조문 검색이 어휘만 하고 참고 조문이 줄어듭니다. 그래서 눈으로 확인하고 넘어갑니다.

| 어디서 | 무엇을 본다 | 없으면 |
|---|---|---|
| `model` (#15) | 받은 뒤 `HF_HUB_OFFLINE=1` 로 **판정 경로와 같은 함수**(`app.retrieve.encode`)로 한 문장을 올려 본다 | `[중단]` |
| `embed-cache` | 위와 같은 확인만 다시 (커밋을 바꾼 뒤 · 재부팅 뒤 의심될 때) | `[중단]` |
| `verify` (#17) | 팀 진단 `doctor --env` 의 「검색 임베딩」 줄이 ✅ | `[중단]` |
| `serve` (#22) · `services` (#33) | 띄우기 전에 캐시가 있는가 | `[중단]` — 캐시 없이 띄우지 않는다 |
| `check` (#23) | 캐시 줄 · (서비스일 때) 앱 로그의 「벡터 검색 불가」 줄 수 | `[확인]` |

- 캐시 자리는 스크립트를 돌린 사용자(`ubuntu`)의 `~/.cache/huggingface/hub` — **루트 디스크**입니다. 서비스도 같은 사용자로 돕니다. `HF_HOME` 을 따로 잡지 않습니다(로컬 NVMe 로 잡히면 `model` 이 경고합니다).
- 받는 단계는 `model` 의 `embed --check` 하나입니다. 그 밖의 단계와 서비스는 `HF_HUB_OFFLINE=1` 로 돕니다.
- ⬜ 임베딩 리비전 SHA 는 아직 비어 있습니다(`embed_revision` · D-344 ⬜) — 정해지면 그 판으로 다시 `model` 을 돕니다.

| 34 | 발표 전 예열 | 발표 시작 전 | 고쳐 쓰기를 한 번 돌려 둔다(처음 모델 올림 약 30초) |

> 상시 가동 전에는 tmux 로 띄웁니다 — 작업하며 자주 껐다 켜고, 화면에 오류가 바로 보여서입니다. 서비스로 돌린 뒤 다시 tmux 로 가려면 `bash deploy_server.sh services-off`.

## 6. 다시 켜는 법 (중지 → 서비스 가동)

**서비스로 등록했으면**(5단계 #33) 인스턴스를 시작하고 1 ~ 2분 뒤 `bash deploy_server.sh check` 만 보면 됩니다.

**tmux 로 띄우던 때는** 아래 순서입니다.

```text
EC2 콘솔 → 인스턴스 시작 → 상태 검사 2/2
MobaXterm 접속 (안 되면 보안 그룹 22 를 「내 IP」로 갱신)
tmux new -s deploy
bash deploy_server.sh preflight          # GPU 줄이 안 나오면 §7 「nvidia-smi 실패」
창 1:  bash deploy_server.sh sllm        # 갈래 A 만
창 2:  bash deploy_server.sh serve
창 3:  bash deploy_server.sh check       # 모두 (안쪽만) 이면 끝
```

> 컨테이너 DB 는 `docker` 서비스와 함께 다시 뜹니다. 안 떴으면 `cd ~/SKN32-FINAL-3TEAM && uv run python launcher.py db-up`.
> Caddy 는 systemd 라 자동으로 뜹니다(`systemctl status caddy`).

## 7. 막혔을 때

| 증상 | 먼저 볼 것 | 고치는 법 |
|---|---|---|
| SSH 가 안 붙는다 | 접속 장소가 바뀌었나 | 보안 그룹 22 소스를 「내 IP」로 다시 |
| 인스턴스 시작이 거부된다 (vCPU limit) | GPU 쿼터 | 0단계 #2 — 승인 전이면 m7i 로 되돌려 갈래 B |
| `nvidia-smi` 실패 (재부팅 뒤) | `uname -r` · `dpkg -l \| grep linux-modules-nvidia` · `sudo modprobe nvidia` | 🔄 10-16 서버에서 겪었다 — 모듈 꾸러미가 **이 커널용으로** 깔려 있어야 한다. `bash deploy_server.sh gpu` 를 다시(없는 판이면 이 커널에 있는 판 목록을 보여 주고 멈춘다 → `SLLM_DRIVER=<판> bash deploy_server.sh gpu`) → 재부팅. 손으로는 `sudo apt install -y linux-modules-nvidia-615-server-open-$(uname -r)`. ⛔ `ubuntu-drivers install` 은 맞는 꾸러미가 없을 때 **오류 없이 아무것도 안 깔고 끝난다**. 배포 기간에는 자동 재부팅을 끈다(배포점검 #5) |
| 화면에 「고쳐 쓰기 서버에 연결하지 못했어요」 | `check` 의 sLLM `/health` | 창 1 이 죽었으면 다시 `sllm` · 살아 있는데 뜨면 **시간 초과**(앱 대기 90초) — #21 의 `latency_ms` 를 보고 요청 ⑤ |
| sLLM `/rewrite` 가 500 | `verify` 의 `hf_display_claims.jsonl` 줄 | `data` 단계(`data-sync`)를 다시 |
| `data-sync` 가 멈춘다 | sha 불일치 메시지 | 올린 파생물 판이 커밋의 원장과 다르다 — 공유 저장소에서 다시 올린다 |
| `load` 가 멈춘다 | 「입력이 없다」 메시지 | 정상 동작이다(D-220 · 없음을 성공으로 세지 않는다) — 파생물 폴더 · `DATA_STORE` 경로 확인 |
| `model` 이 「잠금 밖 판」으로 멈춘다 | 폴더 이름 · 파일 5개 | 공유 저장소에서 폴더째 다시 올린다 — 파일을 손으로 고치지 않는다 |
| `serve` 가 안 뜬다 | `.env` 의 `COPYLANE_EDITION` 오타 | 값은 `cloud` · `demo` · `onprem` · `local` 중 하나 |
| `data` 가 「개발용 기본 비밀번호」로 멈춘다 | `.env` 의 `DATABASE_URL` | `POSTGRES_PASSWORD` 줄을 지우고 `env` 를 다시 — 새로 만든다(§4-2) |
| `migrate` 가 비밀번호 인증 실패 (`password authentication failed`) | DB 볼륨이 옛 비밀번호로 먼저 만들어졌다 | 적재 전이면 `docker compose down -v` → `data` · 적재 뒤면 비밀번호를 볼륨 쪽에 맞춘다(`docker exec -it copylane-postgres psql -U copylane -c "\password copylane"` 에 `.env` 값) |
| `data` 가 「copylane-derived/objects 가 없다」로 멈춘다 | `DATA_STORE` 와 올린 폴더 | `~/CopyLane_store/copylane-derived/objects/..` 구조인지 — 한 단계 더 들어가거나 덜 들어가게 올린 경우가 많다(§4-1) |
| RDS 에 접속이 안 된다 (`timeout`) | RDS 보안 그룹 · 퍼블릭 액세스 | 5432 소스가 EC2 보안 그룹인지 · 같은 VPC 인지 · URL 끝에 `?sslmode=require` |
| 서비스가 계속 재시작된다 | `systemctl status copylane-app` · `journalctl -u copylane-app -n 80` | 대개 tmux 에 남은 서버가 포트를 쥐고 있다 → `services-off` → tmux 창 정리 → `services` |
| `/docs` 를 열어야 한다는 판정이 났다 | Caddyfile `@closed` 줄 | `/docs /docs/* /redoc /redoc/* /openapi.json` 을 지우고 `validate` → `reload` |
| HTTPS 인증서가 안 나온다 | DNS 전파(`dig +short <도메인>`) · 80 이 열렸나 | A 레코드가 탄력적 IP 를 가리킬 때까지 기다린다 — 이래서 도메인은 10/20 까지 |
| 디스크가 찬다 | `df -h /` · `du -sh ~/.cache` | `uv cache clean` · 허브 캐시의 안 쓰는 판 삭제 — 🚨 `models--nlpai-lab--KURE-v1` 은 지우지 않는다(지우면 벡터 검색이 꺼진다 · §5-1) |
| `model` · `embed-cache` 가 「캐시에서 못 올렸다」로 멈춘다 | 바로 위 다섯 줄의 오류 | 받기가 중간에 끊겼다 → `bash deploy_server.sh model` 을 다시 · 그래도면 `rm -rf ~/.cache/huggingface/hub/models--nlpai-lab--KURE-v1` 뒤 다시 |
| 검수 결과의 참고 조문이 눈에 띄게 적다 · 앱 로그에 「벡터 검색 불가」 | `bash deploy_server.sh check` 의 캐시 줄 | 캐시가 없거나 다른 사용자로 띄웠다 → `model` → 앱 다시 띄우기(서비스면 `sudo systemctl restart copylane-app`) |
| 메모리 부족(OOM) | `free -h` · `dmesg | tail` | swap 2GB 확인 · 앱과 sLLM 동시 메모리는 **실측 전**이다(§10) |

## 8. 되돌리기 · 작업기록

**되돌리기** — 앞 판으로 돌아가는 길은 하나입니다.

```bash
DEPLOY_REF=<직전에 잘 돌던 커밋 해시> bash deploy_server.sh fetch
bash deploy_server.sh data && bash deploy_server.sh verify
# 창 2 의 serve 를 Ctrl-C 후 다시
```

모델은 잠금의 **되돌림 판**(`models.lock.json` 의 역할별 `rollback`)이 정해져 있습니다. 바꾸는 것은 앱이 아니라 잠금입니다 — 팀장 결정 사항(D-333).

**작업기록** — 서버에서 무엇을 했는지는 날짜마다 `docs/ssm/배포/작업기록_<MMDD>.md` 에 한 줄씩 남깁니다. 최소한 이 다섯 가지를 적습니다.

| 칸 | 예 |
|---|---|
| 배포 커밋 해시 | `fetch` 출력 |
| 인스턴스 유형 · 가동 시작 / 중지 시각 | 비용 대조용 |
| 지문 대조 결과 | `verify` 출력 |
| sLLM 한 문장 시간 · 부하 시험 수 | #21 · #29 |
| 막힌 것과 고친 것 | §7 에 없던 것은 이 문서에 더한다 |

> 🚨 서버 로그 · `.env` · 접속 문자열은 작업기록에 붙이지 않습니다 — 로그에는 재배포 불가 광고 문구가 있을 수 있습니다.
